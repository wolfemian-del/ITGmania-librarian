---

In plain language: the data file everything else in the app reads from — `library_data.py`, the Tk-free module holding the parsing, the search language, the score merge, the course formatting, and the two stores — has grown to 2,109 lines and 81 functions, and it is now the largest single concentration left in the codebase. This proposal splits it into seven smaller modules, one per subject area, following the same pattern as Proposal 0009: pure moves, bodies byte-identical, staged leaf-first so each step is independently green. Nothing the user sees changes. The one real decision is whether the old file survives as a thin re-export shim or is deleted outright (§7, Q1).

## 1. Background and Goal

Proposal 0009 is complete. The app shell is 661 lines, the loader, filter, table, and dialog are standalone components with constructor contracts, and the suite is 613 OK. The remaining concentration is the data layer: `library_data.py` is the one file every component imports from, and it holds nine unrelated subjects in one flat namespace — a reader changing the search matcher has to hold the snapshot store, the course formatter, and the BPM display code in mind to find it. Grok's assessment called it "coherent but wide surface area" and judged further splits "optional polish rather than necessary cleanup"; the owner decided to do it anyway, on the same legibility ground as 0009.

That is why this proposal exists before any code moves. The split creates seven new module boundaries, so it needs a proposal under the workflow rule — and the boundaries need to be decided up front, because the modules import from each other and the wrong extraction order creates a chicken-and-egg. Nothing about the app's appearance or behaviour changes; the goal is seven modules each understandable from its own one-sentence description without holding the rest of the file in mind, as with the four splits before this one. "Done" means `library_data.py` is a thin re-export shim (or gone, if Q1 goes the other way), each new module owns its subject end to end, and the test file has split to match.

This change creates seven new module boundaries. It does not persist a new settings key or file format, and it does not change any public function signature — every moved function keeps its name, its arguments, and its behaviour.

## 3. The Decision: Seven Modules, Leaf-First, with a Re-Export Shim

### Option A (recommended): seven new modules, one per subject, plus a shim

Seven new modules — `library_constants.py`, `library_format.py`, `library_scores.py`, `library_stores.py`, `library_search.py`, `library_course.py`, `library_distribution.py` — each owning one cluster end to end (§4), with `library_data.py` surviving as a thin re-export shim so every existing import keeps working. The modules are Tk-free, like the file they come from; no module imports Tkinter, and no module reaches into a UI component. The staging in §6 extracts them leaf-first, so no module is extracted before a module it imports from, and the shim is the last step.

### Option B: extract only the stores and the search, leave the rest

Move `SnapshotStore`/`SettingsStore` and the search language out, and leave the format helpers, scores, cache, course, geometry, and distribution where they are. Worth doing on its own merits — those two clusters are the most self-contained — but as the whole answer it leaves ~1,100 lines in `library_data.py` across six subjects, and the file stays the place a reader has to hold in mind to change any of them. The split's point is not achieved.

### Option C: delete `library_data.py` outright in one PR

Re-point all eight production import sites and all eleven test files at the new modules in a single PR and delete the file. The end state is the cleanest — no shim to explain to a future reader — but the diff is the whole split at once with no staging, no per-step green check, and no way to bisect a regression to one module. Rejected for the same reason Proposal 0009 staged the app split instead of doing it in one PR. Deletion stays available as a later decision once the shim has proven itself (see Q1).

## 4. Recommended Design in Detail (Option A)

The legibility test, the project's standing guideline: each module must be describable in one sentence that a standalone reader needs first. Each module below carries that sentence, its contents, and what it imports — the imports are the contract, and a module must not reach past them.

**library_constants.py.** One sentence: the shared vocabulary — the column and grade tables every other module and the UI read from. Contents: the 15 shared constants from lines 1–152 (`TECH_FIELDS`, `DIFFICULTY_ORDER`, `DIFFICULTY_RANK`, `RADAR_FIELDS`, `RADAR_COUNT_FIELDS`, `TAP_FIELDS`, `HEADERS`, `NUMERIC_COLUMNS`, `COLUMN_GROUPS`, `DEFAULT_VISIBLE_GROUPS`, `DEFAULT_VISIBLE_COLUMNS`, `GRADE_NAMES`, `GRADE_OPTIONS`, `GRADE_RANK`, `COURSE_UNSAFE_CHARS`), ~130 lines. It imports nothing from the other new modules. The search-specific constants (`SEARCH_FIELD_ALIASES`, `NUMERIC_SEARCH_FIELDS`) do **not** move here — they travel with the search module, since nothing outside search reads them, and `NUMERIC_SEARCH_FIELDS` is built from `RADAR_COUNT_FIELDS` and `TECH_FIELDS`, so the search module imports those two from here.

**library_format.py.** One sentence: how values are displayed and sorted — the formatting and sort-key helpers. Contents: the 12 format/BPM functions from lines 153–299, ~150 lines. It imports the constants it needs from `library_constants.py` (the grade and difficulty tables) and nothing else. Two modules import from it — the scores module (four calls from the scores half, five from the cache half) and the search module (one call, through the dialog half's `format_duration`) — and it imports from no other new module, which is what makes it the shared leaf and the second move after the constants.

**library_scores.py.** One sentence: scores and the cache they are merged into — reading Stats.xml, reading the cache, and joining the two. Contents: the scores cluster (lines 302–492) and the cache/paths cluster (lines 495–650) together, ~345 lines, plus the `_SCORE_FIELDS` constant (line 424), which `merge_scores` reads. They fold into one module because `parse_cache_file` calls `_apply_score_fields` and `_score_for_chart` — the two clusters are one subject, split by an accident of file order, and folding them makes that edge internal instead of a cross-module call. It imports from `library_constants.py` and `library_format.py`. The two snapshot-validation helpers (`_nonnegative_int`, `_normalized_source_path`) stay here for now — they sit in the cache cluster, and the stores move may take `_nonnegative_int` along if that PR finds it is store-only (it is used only by `SnapshotStore.read`); `_normalized_source_path` stays here, since the loader imports it too (`library_loader.py:27`); that is a move-PR judgment, not a proposal decision.

**library_course.py.** One sentence: courses and the geometry they are positioned with — the `.crs` text format and the DPI-aware geometry helpers. Contents: the geometry/DPI cluster (lines 855–954) and the course cluster (lines 957–1136) together, ~280 lines. They fold into one module because they are the two halves of the course feature — the course window's geometry is parsed by `parse_course_geometry`, and the course text is built and validated by the course functions — and because neither cluster calls the other, the fold costs no coupling. It imports one constant, `COURSE_UNSAFE_CHARS`, from `library_constants.py` and nothing from `library_format.py` — no course or geometry function calls a format helper.

**library_search.py.** One sentence: the search language — parsing a query, matching a chart against it, and rewriting its directives. Contents: the search cluster (lines 1139–1686, including the three search-specific constants — `SEARCH_FIELD_ALIASES`, `NUMERIC_SEARCH_FIELDS`, and `CHART_FILTER_FIELDS`, which `get_active_chart_filters` reads and the distribution module's click/clear decisions import from here) and the dialog-query cluster (lines 1983–2107, including its three constants), ~675 lines. They fold into one module because dialog query calls search three times and exists only to translate between the Advanced Search dialog and the search bar — it is the search language's second face, not a separate subject. It imports from `library_constants.py` and `library_format.py`. At ~675 lines it is the largest new module, and the question of whether it should itself split further is Q2.

**library_stores.py.** One sentence: persistence — the snapshot store that owns `library_cache.json` and the settings store that owns `settings.json`. Contents: the stores cluster (lines 654–853), ~200 lines: `SnapshotResult`, `SnapshotStore`, `SettingsStore`, `_settings_file_path`, `_valid_column_width`, `_valid_window_geometry`, plus the `LIBRARY_CACHE_SCHEMA_VERSION` constant (line 616, the snapshot schema version, whose consumers are `SnapshotStore.__init__` and the app, which passes it to the loader). It imports from `library_constants.py`, `library_scores.py` (for `write_file_atomically` and `_nonnegative_int`, unless the move PR takes the latter along — `_normalized_source_path` stays in the scores module, since the loader imports it too), and `library_course.py` (for `parse_course_geometry`, used by `_valid_window_geometry`). Those five edges are why the stores move comes after the scores and course moves in §6 — the stores look like the easiest move, but they are the least leaf-most.

**library_distribution.py.** One sentence: the distribution charts — aggregating the library into the meter, difficulty, and BPM distributions the panel draws. Contents: the distribution cluster (lines 1689–1982), ~295 lines, plus the `BPM_BINS` constant (line 1861), which `aggregate_bpm_distribution` reads. It imports from `library_constants.py` and `library_search.py` (nine calls — it uses the matcher to filter the rows it aggregates, and it imports `CHART_FILTER_FIELDS` from the search module for the click/clear decisions). It must come after the search module, and it is the last content module to move.

**The shim (`library_data.py`).** After the seven moves, `library_data.py` keeps its module docstring and becomes a re-export: one import line per new module, re-exporting every public name the old file exposed, with the same `__all__`. No function body remains in it. The eight production import sites and the eleven test files keep working unchanged; the move PRs re-point import sites to the new modules as they go (each PR re-points the sites for the names it moves), and whatever is left still resolves through the shim. The shim is the 0009 parallel to the app shell staying in place: the old name keeps working while the new structure settles. Whether the shim is later deleted is Q1.

## 5. What Does Not Change

- Everything the user sees: nothing. This is a pure reorganisation of Tk-free code; no window, table, filter, dialog, or panel changes, and no behaviour change of any kind.
- Every public function keeps its name, its arguments, its return value, and its behaviour. `match_chart_query`, `merge_scores`, `parse_cache_file`, `parse_search_query`, `aggregate_meter_distribution`, and all the rest are the same functions in a different file. The only changed lines are import lines.
- The settings keys, the snapshot format (schema version 4), and the `.crs` output. No new settings key, no file-format change.
- The eight production modules and their contracts. The loader, filter, table, panel, Course Builder, and Advanced Search keep calling the same functions; only the module those functions live in changes, and the shim means even that change is invisible to them until their import is re-pointed.
- The test expectations: the tests that exist today assert the same behaviour after the move, from their new files.

## 6. Test Plan (for the implementation PRs)

Eight pull requests, in order. Each is independently green, and the order is the point: the safety net exists before any boundary moves, and no module is extracted before a module it imports from, so each move PR can be judged as a move.

**Step 1 — test hardening (no production code changes).** Write the missing tests against today's `library_data.py`, so they pin current behaviour before anything relocates. The gaps, from the §2 inventory: the cross-module seams — a test asserting the distribution aggregations actually use the search matcher (a distribution that ignored the filter would pass everything today except the panel tests), a test asserting the stores write through `write_file_atomically` (a store that wrote directly would pass the round-trip tests), and a test asserting `_valid_window_geometry` rejects a geometry string `parse_course_geometry` cannot parse. Plus the import-surface pin: a test importing every public name from `library_data` and asserting it resolves, so the shim step cannot silently drop a name.

**Step 2 — constants and format helpers.** `library_constants.py` (~130 lines) and `library_format.py` (~150 lines), as §4 describes. Move purity: the constants move verbatim; the 12 functions move byte-identical, with only the import line changing. The tests for the format helpers move to `tests/test_library_format.py`; the constants need no test file of their own (they are data, asserted by the tests that use them). Each new module defines its own `__all__` for the names it owns, starting here; the shim's `__all__` is the union — the current 74-entry list, unchanged — and `library_data.py` re-exports it. (The `__all__` cannot move whole to the constants module: it lists 74 public names across all nine clusters, most of which the constants module does not define.)

**Step 3 — scores and cache.** `library_scores.py` (~345 lines), as §4 describes. Move purity: the 15 functions move byte-identical, with only the import lines changing; the cache→scores edge is internal to the new module. The tests for the scores and cache functions move to `tests/test_library_scores.py`. The wiring guard: a test asserting `parse_cache_file` still applies the score fields (the `_apply_score_fields` call is the seam the fold exists to protect).

**Step 4 — course and geometry.** `library_course.py` (~280 lines), as §4 describes. Move purity: the 16 functions move byte-identical. The tests for the course and geometry functions move to `tests/test_library_course.py`. The wiring guard: a test asserting the course window's geometry validation still goes through `parse_course_geometry` (the geometry half's only external caller is the stores, which have not moved yet — the pin is written now and re-pointed in Step 6).

**Step 5 — search and dialog query.** `library_search.py` (~675 lines), as §4 describes. Move purity: the 22 functions and the 6 constants (3 search, 3 dialog-query) move byte-identical. The tests for the search and dialog-query functions move to `tests/test_library_search.py`. The wiring guard: a test asserting `split_dialog_query` still round-trips through `parse_search_query` (the dialog-query→search seam), and a test asserting a distribution-style filter still matches through `match_chart_query`.

**Step 6 — the stores.** `library_stores.py` (~200 lines), as §4 describes. Move purity: the two store classes and their four helpers move byte-identical, with the five import edges re-pointed to `library_scores.py` and `library_course.py` (or `_nonnegative_int` travels with the stores — the move PR decides; `_normalized_source_path` stays in the scores module, since the loader imports it too). The existing `tests/test_snapshot_store.py` and `tests/test_settings_store.py` already test the stores separately, so they are re-pointed at the new module rather than rewritten. The wiring guard: a test asserting the stores still write through `write_file_atomically` and still validate geometry through `parse_course_geometry`.

**Step 7 — distribution.** `library_distribution.py` (~295 lines), as §4 describes. Move purity: the 10 functions move byte-identical, with the nine search calls re-pointed to `library_search.py`. The tests for the distribution functions move to `tests/test_library_distribution.py`. **Step 8 — the shim.** `library_data.py` becomes the re-export described in §4: one import line per new module, the same `__all__`, no function bodies. Plus a live smoke after the last step: load the library, type a search, open the distribution panel, build a course, quit and relaunch to confirm the settings and snapshot still round-trip.

## 7. Open Questions for Reviewers

- **Q1. Does `library_data.py` survive as a re-export shim, or is it deleted?** Recommended: the shim, as §4 describes. The old name is imported by eight production modules and eleven test files; the shim lets each move PR re-point its own sites without a flag day, and a future reader can still find the functions by the name they were always imported under. Deletion is cleaner in the end, but it is a separate, later decision — once the shim has proven itself and every import site has been re-pointed, deleting it is a one-line-per-site change. The alternative — deleting in Step 8 instead of shimming — saves one step and leaves no indirection, at the cost of re-pointing all eight production import sites at once.
- **Q2. Should the search module (~675 lines) itself split further — query parsing vs matching vs directive rewriting — or stay whole?** Recommended: stay whole. The three parts call each other constantly (`match_chart_query` calls the bound comparators, `replace_search_directive` calls the parser, the dialog query calls both), so splitting them would trade one 675-line module for three modules with a dense call graph between them — the same shape this proposal is splitting apart. If a future reader finds the module too wide, the split point is visible: `parse_search_query` and friends are the parser, `match_chart_query` and the comparators are the matcher, `replace_search_directive` and `get_active_chart_filters` are the rewriting. The staging gains nothing by deciding that now.
- **Q3. What is the panel review shape for the move PRs?** Recommended: the same pattern as Proposal 0009 — a full four-model panel (Claude, ChatGPT-6, Grok, GLM) on the biggest move, which is Step 5 (search, ~675 lines), and lighter checks on the pure moves (a single focused executed check, or none where the move is verified pure by normalized diff). The pure moves are mechanical in the same sense as 0009's Step 2, which needed no reviewer; the judgment calls are the seam pins in Step 1 and the stores' helper placement in Step 6. The owner decides.
