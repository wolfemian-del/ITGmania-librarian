---

In plain language: the data file everything else in the app reads from — `library_data.py`, the Tk-free module holding the parsing, the search language, the score merge, the course formatting, and the two stores — has grown to 2,109 lines and 81 functions, and it is now the largest single concentration left in the codebase. This proposal splits it into nine smaller modules, one per subject area, following the same pattern as Proposal 0009: pure moves, bodies byte-identical, staged leaf-first so each step is independently green. Nothing the user sees changes. The old file is deleted at the last step, after serving as an interim hybrid from the second step on (§7, Q1).

This proposal was revised after the panel review on PR #169. The owner adopted Claude's findings, which changed the module list (geometry and dialog query split out, the scores module renamed), flipped Q1 from shim to delete, and moved the full panel from Step 5 to Step 1. The decisions are recorded in §7; the measurements in §2 are unchanged.

## 1. Background and Goal

Proposal 0009 is complete. The app shell is 661 lines, the loader, filter, table, and dialog are standalone components with constructor contracts, and the suite is 613 OK. The remaining concentration is the data layer: `library_data.py` is the one file every component imports from, and it holds nine unrelated subjects in one flat namespace — a reader changing the search matcher has to hold the snapshot store, the course formatter, and the BPM display code in mind to find it. Grok's assessment called it "coherent but wide surface area" and judged further splits "optional polish rather than necessary cleanup"; the owner decided to do it anyway, on the same legibility ground as 0009.

That is why this proposal exists before any code moves. The split creates nine new module boundaries, so it needs a proposal under the workflow rule — and the boundaries need to be decided up front, because the modules import from each other and the wrong extraction order creates a chicken-and-egg. Nothing about the app's appearance or behaviour changes; the goal is nine modules each understandable from its own one-sentence description without holding the rest of the file in mind, as with the four splits before this one. "Done" means `library_data.py` is deleted, each new module owns its subject end to end, and the test file has split to match.

This change creates nine new module boundaries. It does not persist a new settings key or file format, and it does not change any public function signature — every moved function keeps its name, its arguments, and its behaviour.

## 3. The Decision: Nine Modules, Leaf-First, with the Old File Deleted

### Option A (recommended): nine new modules, one per subject, with the old file deleted at the last step

Nine new modules — `library_constants.py`, `library_format.py`, `library_sources.py`, `library_geometry.py`, `library_course.py`, `library_search.py`, `library_dialog_query.py`, `library_stores.py`, `library_distribution.py` — each owning one cluster end to end (§4), with `library_data.py` serving as an interim hybrid from Step 2 on and deleted at Step 9, once every import site has been re-pointed. The modules are Tk-free, like the file they come from; no module imports Tkinter, and no module reaches into a UI component. The staging in §6 extracts them leaf-first, so no module is extracted before a module it imports from, and the deletion is the last step.

### Option B: extract only the stores and the search, leave the rest

Move `SnapshotStore`/`SettingsStore` and the search language out, and leave the format helpers, sources, geometry, course, dialog query, and distribution where they are. Worth doing on its own merits — those two clusters are the most self-contained — but as the whole answer it leaves ~1,300 lines in `library_data.py` across seven subjects, and the file stays the place a reader has to hold in mind to change any of them. The split's point is not achieved.

### Option C: keep the old file as a re-export shim (rejected)

Keep `library_data.py` as a thin re-export of the new modules so every existing import keeps working. Rejected for four reasons. First, the shim has no client: every importer is in this repo, and this is a desktop app, not a library. Second, it costs a second import path for every name and a 74-name `__all__` to maintain. Third, the proposal's own staging contradicts it — if each move PR re-points its own import sites, nothing is left to re-point at the last step, so the "all eight sites at once" cost does not exist. Fourth, and decisively, a shim that exposes module attributes turns loud test failures into silent wrong-namespace patches: a test patching `library_data.ctypes` would land on the shim's copy while the moved function reads its own module's, so the mock is silently never called. Deleting makes any missed import site fail loudly at once.

## 4. Recommended Design in Detail (Option A)

The legibility test, the project's standing guideline: each module must be describable in one sentence that a standalone reader needs first. Each module below carries that sentence, its contents, and what it imports — the imports are the contract, and a module must not reach past them.

**library_constants.py.** One sentence: the shared vocabulary — the column and grade tables every other module and the UI read from. Contents: the 15 shared constants from lines 1–152 (`TECH_FIELDS`, `DIFFICULTY_ORDER`, `DIFFICULTY_RANK`, `RADAR_FIELDS`, `RADAR_COUNT_FIELDS`, `TAP_FIELDS`, `HEADERS`, `NUMERIC_COLUMNS`, `COLUMN_GROUPS`, `DEFAULT_VISIBLE_GROUPS`, `DEFAULT_VISIBLE_COLUMNS`, `GRADE_NAMES`, `GRADE_OPTIONS`, `GRADE_RANK`, `COURSE_UNSAFE_CHARS`), ~80 lines. The constants themselves span lines 22–73; the ~130 figure in the first draft included the 76-line `__all__`, which does **not** move whole — each new module defines its own `__all__`. It imports nothing from the other new modules. The search-specific constants (`SEARCH_FIELD_ALIASES`, `NUMERIC_SEARCH_FIELDS`, `CHART_FILTER_FIELDS`) do **not** move here — they travel with the search module, since nothing outside search reads them, and `NUMERIC_SEARCH_FIELDS` is built from `RADAR_COUNT_FIELDS` and `TECH_FIELDS`, so the search module imports those two from here. `COURSE_UNSAFE_CHARS` does **not** move here either — it moves into the course module, since no file outside `library_data.py` references it.

**library_format.py.** One sentence: how values are displayed and sorted — the formatting and sort-key helpers. Contents: the 12 format/BPM functions from lines 153–299, ~150 lines. It imports `DIFFICULTY_ORDER`, `DIFFICULTY_RANK`, `GRADE_RANK` from `library_constants.py` (the grade and difficulty tables) and nothing else. Two modules import from it — the sources module (four calls from the scores half, five from the cache half) and the dialog-query module (one call, `_format_bound_number` → `format_duration`) — and it imports from no other new module, which is what makes it the shared leaf and the second move after the constants.

**library_sources.py.** One sentence: where ITGmania's files are and how they are read and joined — reading Stats.xml, reading the cache, and joining the two. Contents: the scores cluster (lines 302–492) and the cache/paths cluster (lines 495–650) together, ~320 lines, minus `write_file_atomically` and `_nonnegative_int`, which move to the stores now (they are persistence helpers, called only by the stores), plus the `_SCORE_FIELDS` constant (line 424), which `merge_scores` reads. They fold into one module because `parse_cache_file` calls `_apply_score_fields` and `_score_for_chart` — the two clusters are one subject, split by an accident of file order, and folding them makes that edge internal instead of a cross-module call. The four path helpers (`looks_like_song_tree`, `cache_dir_candidates`, `first_existing_directory`, `invalid_paths_note`) stay here too — their consumers are the loader, the app shell, and `data_paths_dialog.py`, and a reader looking for where the files come from looks here. `_normalized_source_path` stays here, since the loader imports it too (`library_loader.py:27`). It imports `GRADE_NAMES`, `TAP_FIELDS`, `RADAR_FIELDS`, `TECH_FIELDS` from `library_constants.py` and the format helpers from `library_format.py`.

**library_geometry.py.** One sentence: window geometry and DPI — parsing a saved geometry string and scaling pixels for the display. Contents: the geometry/DPI cluster (lines 855–954: `parse_course_geometry`, `dpi_scale_factor`, `scale_pixels`, `format_geometry`, `scale_geometry`, `declare_dpi_awareness`), ~100 lines. It imports nothing from the package. Consumers: `advanced_search.py`, `course_builder.py`, `data_paths_dialog.py`, `library_visualizer.py`, and the stores' `_valid_window_geometry` — three of those windows have nothing to do with courses, which is why geometry is its own module rather than folded into course.

**library_course.py.** One sentence: the `.crs` text format. Contents: the course cluster (lines 957–1136) plus `COURSE_UNSAFE_CHARS` moved in from the constants, ~185 lines. It imports nothing — no course function calls a format helper or uses a shared constant (verified by grep: the course functions use only `COURSE_UNSAFE_CHARS`), and it calls nothing outside itself.

**library_search.py.** One sentence: the search language — parsing a query, matching a chart against it, and rewriting its directives. Contents: the search cluster (lines 1139–1686, including the three search-specific constants `SEARCH_FIELD_ALIASES`, `NUMERIC_SEARCH_FIELDS`, `CHART_FILTER_FIELDS`), ~550 lines. It imports `RADAR_COUNT_FIELDS`, `TECH_FIELDS`, `GRADE_NAMES`, `GRADE_RANK` from `library_constants.py` and nothing else. It does **not** import format: the dialog half was the only reason it did. At ~550 lines it is the largest new module, and the question of whether it should itself split further is Q2.

**library_dialog_query.py.** One sentence: the Advanced Search dialog ↔ search-bar text. Contents: the dialog-query cluster (lines 1983–2107: 6 functions + 3 constants `DIALOG_TEXT_FIELDS`, `DIALOG_RANGE_FIELDS`, `_DIALOG_RANGE_TOKEN_NAMES`), ~125 lines. It imports `GRADE_OPTIONS` from `library_constants.py`, `format_duration` from `library_format.py` (via `_format_bound_number`), and three calls from `library_search.py` (`_quote_for_search`, `parse_numeric_bound`, `parse_search_query`). Its only consumer is `advanced_search.py`, whose docstring calls it the "companion".

**library_stores.py.** One sentence: persistence — the snapshot store that owns `library_cache.json` and the settings store that owns `settings.json`. Contents: `SnapshotResult`, `SnapshotStore`, `SettingsStore`, `_settings_file_path`, `_valid_column_width`, `_valid_window_geometry`, `_nonnegative_int`, `write_file_atomically`, `LIBRARY_CACHE_SCHEMA_VERSION`, ~225 lines. The app passes the schema version to `SnapshotStore(...)` (`library_visualizer.py:67–68`), not to the loader. It imports `_normalized_source_path` from `library_sources.py` and `parse_course_geometry` from `library_geometry.py` (used by `_valid_window_geometry`). It does **not** import from `library_constants.py` (the stores use no shared constant) and does **not** import from `library_format.py`. Those two edges are why the stores move comes after the sources and geometry moves in §6 — the stores look like the easiest move, but they are the least leaf-most.

**library_distribution.py.** One sentence: the distribution charts — aggregating the library into the meter, difficulty, and BPM distributions the panel draws. Contents: the distribution cluster (lines 1689–1982: 1 class `ChartBar` + 9 functions), ~295 lines, plus the `BPM_BINS` constant (line 1861), which `aggregate_bpm_distribution` reads. It imports `DIFFICULTY_ORDER` from `library_constants.py` and, from `library_search.py`, nine calls plus `CHART_FILTER_FIELDS` and the private `_compare_bpm_bound`. It does not import format. It must come after the search module, and it is the last content module to move.

**The interim hybrid (`library_data.py`).** From Step 2 on, `library_data.py` is a hybrid: it keeps the not-yet-moved code and re-exports every moved name that unmoved code or import sites still use — including the five private names (`_normalized_source_path`, `_settings_file_path`, `_valid_window_geometry`, `_valid_column_width`, `_quote_for_search`) and the module attributes the tests patch (`ctypes`, `os`, `sys`) — with the caveat that the four namespace-patch tests move in the same PR as the function they patch, with the patch target being the module that reads the name, so the hybrid's attributes do not turn loud failures into silent wrong-namespace patches. One rule governs the interim state: **no new data module imports `library_data`** — that is what keeps it cycle-free. Step 9 deletes the file.

**Cross-module underscore names.** The names below cross a module boundary with an underscore prefix, and they cannot be renamed in a byte-identical move, so the proposal lists them here rather than leaving them to each PR: `_normalized_source_path` (used by the loader and the stores), `_compare_bpm_bound` (used by distribution, from search), `_nonnegative_int` (stores), `_settings_file_path`, `_valid_window_geometry`, `_valid_column_width` (used by the app and the table).

**Naming convention.** The `library_` prefix already mixes Tk modules (`library_loader`, `library_table`, `library_visualizer`) with Tk-free ones (`library_filter`, `library_data`), so `library_search.py` beside `library_filter.py` is confusable. AGENTS.md currently tells LLMs where Tk-free logic lives; after the split it needs a README table of the data modules to point at. The README table and the AGENTS.md rewording are a Step 9 item.

## 5. What Does Not Change

- Everything the user sees: nothing. This is a pure reorganisation of Tk-free code; no window, table, filter, dialog, or panel changes, and no behaviour change of any kind.
- Every public function keeps its name, its arguments, its return value, and its behaviour. `match_chart_query`, `merge_scores`, `parse_cache_file`, `parse_search_query`, `aggregate_meter_distribution`, and all the rest are the same functions in a different file. The only changed lines are import lines — and, at Step 9, the deletion of the old file.
- The settings keys, the snapshot format (schema version 4), and the `.crs` output. No new settings key, no file-format change.
- The eight production modules and their contracts. The loader, filter, table, panel, Course Builder, and Advanced Search keep calling the same functions; only the module those functions live in changes, and the import sites are re-pointed as the moves go, so no step leaves a caller pointing at a name that has moved.
- The test expectations: the tests that exist today assert the same behaviour after the move, from their new files.

## 6. Test Plan (for the implementation PRs)

Nine pull requests, in order. Each is independently green, and the order is the point: the safety net exists before any boundary moves, and no module is extracted before a module it imports from, so each move PR can be judged as a move.

**Step 1 — test hardening (no production code changes).** Write the missing tests against today's `library_data.py`, so they pin current behaviour before anything relocates. The gaps, from the §2 inventory: the cross-module seams — a test asserting the distribution aggregations actually use the search matcher (a distribution that ignored the filter would pass everything today except the panel tests), a test asserting `_valid_window_geometry` rejects a geometry string `parse_course_geometry` cannot parse, and a behavioural pin for the stores' write path (a failed replace leaves the old file intact and no temp file, for both stores — `test_failed_replace_leaves_no_temp_file` already does this for the snapshot store and survives any move, so the settings-store equivalent is the one to add; prefer this over a patch-target pin, which would break when the function moves). Plus the import-surface pin, built from the names consumers **actually** import (production and tests), not from `__all__` — a test importing every such name from `library_data` and asserting it resolves, so no step can silently drop a name. `patch("library_data.os.replace")` is fixed now in this step, before any move. The four namespace-patch tests move in the same PR as the function they patch, with the patch target being the module that reads the name.

**Step 2 — constants and format helpers.** `library_constants.py` (~80 lines) and `library_format.py` (~150 lines), as §4 describes. Move purity: the constants move verbatim; the 12 functions move byte-identical, with only the import line changing — and the purity check compares **every** top-level node, including the bare `GRADE_RANK.update(...)` statement at line 72, not just named definitions. The tests for the format helpers move to `tests/test_library_format.py`; the constants need no test file of their own (they are data, asserted by the tests that use them). Each new module defines its own `__all__` for the names it owns, starting here. Mention in the Step 2 PR description that open branches importing `library_data` will need their imports updated.

**Step 3 — sources.** `library_sources.py` (~320 lines), as §4 describes. ## 7. Open Questions for Reviewers

- **Q1. Does `library_data.py` survive as a re-export shim, or is it deleted?** Decided by the owner on the panel review: **delete, at Step 9, after the interim hybrid.** Claude's reasoning, adopted here: the shim has no client, since every importer is in this repo and this is a desktop app, not a library; it costs a second import path for every name and a 74-name `__all__` to maintain; the proposal's own staging contradicts it, since if each move PR re-points its own import sites, nothing is left to re-point at the last step; and a shim that exposes module attributes turns loud test failures into silent wrong-namespace patches (a test patching `library_data.ctypes` would land on the shim's copy while the moved function reads its own module's, so the mock is silently never called). Deleting makes any missed import site fail loudly at once.
- **Q2. Should the search module (~550 lines) itself split further — query parsing vs matching vs directive rewriting — or stay whole, and what about the dialog half?** Decided by the owner on the panel review: **keep the parser, matcher, and rewriter whole, but take the dialog half out** into `library_dialog_query.py`. The search module drops to ~550 lines importing constants only.
