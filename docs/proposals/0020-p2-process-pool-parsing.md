*Acceptance gate: this proposal is opened for design review now, but it should not be accepted until P5's §6 measurement (proposal 0019, implementation PR #271) has run on the owner's machine — the measurement decomposes the 14 s the end-to-end story leans on, and if it changes that story this proposal takes a Revision 1 first.*

In plain language: after P1, a refresh only re-reads the cache files that changed — but when many files changed, or on the first run when there is no manifest at all, it still reads all 7,499 files one after another, which takes about 29 seconds of number-crunching on the owner's machine. This change spreads that reading across the machine's 8 cores, so a full parse should take roughly 6–9 seconds instead of 29. Nothing about the app looks different, a refresh still shows exactly the same library, and if the pool cannot start for any reason the refresh quietly falls back to reading files one after another, exactly as today. The one real decision in this proposal is how the scores reach the worker processes: once per worker when it starts, not once per file.

## 1. Background and Goal

The faster-refresh order the measurements dictate is P1, then P5, then P2. P1 (proposal 0018, implementation PR #269 merged 2026-11-23) shrinks the parse list: a warm refresh re-parses only changed files and the worker drops to ~1 s. P5 (proposal 0019, accepted and merged 2026-11-23; implementation PR #271 in review) attacks the 14 s table insert. P2 is what remains for the full-parse case — the first run after an upgrade, a missing or corrupt manifest, or a large change set such as a new pack — where the parse is still ~29 s single-threaded on an 8-core machine. The parse is CPU-bound, not I/O-bound, so more processes is the only lever left on it: the file reads are already in the operating system's cache on a warm run, and the work per file is pure Python text processing (regex splits, tag maps, dictionary lookups).

Modularity, up front: this change does not create a new component boundary and does not move one. The parse is already a pure function in `library_sources` (layer 2, Tk-free), and the pool orchestration lives inside the loader's worker as a private path beside the serial loop. It adds no new module, no new settings key, and no constructor input — the worker count, the chunk size, and the engagement threshold are module constants the timing measurement sets, not inputs the shell passes in. It does not change the snapshot format, the manifest format, the delivery contract, or the table insert. Done means: a warm full parse finishes its worker in ~6–9 s [INFERRED] and delivers byte-for-byte the same rows, order, and counts as the serial parse, with the pool never engaged for a small parse list and a serial fallback that always works.

## 2. Current State (measured on main `d97ee89` with the P1 implementation, PR #269, since merged)

The refresh worker is `LibraryLoader._load_worker` [CODE: `itgmania_library/library_loader.py:338-563`]. It takes the Stats.xml stat before reading the scores (`stats_index`, ~0.05 s), walks the cache folder once with `os.scandir`, builds the Edit fallback index once, then loops over the scanned files in walk order: an unchanged file reuses its snapshot rows (P1), every other file is parsed by `parse_cache_file(path, scores, edit_index)` inline, and a file that raises is counted in `skipped_files` and skipped (issue #205). The loop checks the generation before each file (a superseded scan stops quietly) and reports progress every 25 files and on the last one. After the loop a changed Stats.xml re-derives scores with `merge_scores` over all rows, then the snapshot and the manifest are written under the one `_snapshot_lock`, snapshot first, and the worker delivers one `("loaded", ...)` message carrying the rows, the counts, and the `reparsed_files` kwarg; the main thread's `_poll_load_results` [CODE: `library_loader.py:758-785`] drains the queue every 75 ms and calls `_loaded`. The worker runs in a daemon thread started by `load_data` [CODE: `library_loader.py:335`]; Tk calls from workers are unsafe, so the worker only ever puts tuples on the queue.

`parse_cache_file` [CODE: `itgmania_library/library_sources.py:248-349`] is a pure function of three inputs — a `Path`, the scores dict, and the Edit fallback index — returning `(rows, skipped_blocks)`. It reads the whole file as text, splits it on `#NOTEDATA:`, drops chart blocks that lack `#STEPSTYPE` or `#DIFFICULTY`, looks each chart's score up in the dicts, and builds plain row dicts (strings, ints, and `""` — all JSON-serializable and therefore picklable). It reads no globals, holds no state, and is deterministic: the same file with the same scores gives the same rows. Its only production call site is the worker loop [CODE: `library_loader.py:457`]; the timing script is the other caller. The scores dict is `dict[tuple, dict]` with string values [CODE: `library_sources.py:24-69`]; the Edit index is derived from it in one pass [CODE: `library_sources.py:70-88`]. The scores sync (`_sync_scores_worker`) never parses a cache file, so P2 does not touch it.

The numbers are the owner's, measured 2026-11-22 on his machine (Ryzen 9 4900HS, 8 cores / 16 threads, Python 3.14.7; timing script `tools/time_refresh_parse.py`): 7,499 files, 42,375 chart rows; worker 29.82/29.99 s, parse 29.00/29.11 s (97% of the worker); cold full cache read 106 s; end-to-end warm ~40 s (26 s cache + a further 14 s insert/render). That is ~3.9 ms per file [INFERRED: 29.0 s / 7,499 files]. The serial parts of the worker are small: `stats_index` ~0.05 s, discovery 0.08 s, snapshot write ~0.7 s, `merge_scores` 0.27 s at this scale (sandbox-measured). The cold 106 s is disk-bound — the roadmap records that most of the cold time is disk reads — so the pool's win on a cold read is not the 29 s parse win; it is whatever the disk allows, which is unmeasured.

Sandbox measurements ground the design's fixed costs [RAN: Python 3.12.3, 1.5 shared CPUs, 6 fixture cache files, 11 rows, `/tmp/p2_measure.py`]. The parse profile shows the work is CPU-bound: `parse_cache_file` itself dominates tottime, followed by `tag_map`, `number`, and dict lookups, while the file `open` is ~7% of the parse's time. Serial parse of the fixtures runs 0.10 ms/file (tiny files — not comparable to the owner's 3.9 ms/file, only the shape transfers). The scores dict pickles at 173 B/entry and a file's result at ~632 B/row, so the return trip for the owner's library is ~27 MB of pickled rows [INFERRED: 632 B × 42,375 rows] — well under a second of pickle traffic against a 29 s parse. Starting a 4-worker pool under the spawn context costs ~459 ms (~115 ms per worker) [RAN], so at fixture scale the pool is ~50× slower than the serial parse — the fixed spawn cost dwarfs tiny work, which is exactly why the pool needs an engagement threshold (§4.5). Pickling the scores dict 96 times costs 0.8 ms at fixture scale, which says nothing about the owner's scale and is the reason the scores travel once per worker instead (§3, D2). One behaviour was measured rather than assumed: a parent that exits without shutting its pool down waits for the longest running task (10.2 s measured) and leaves no orphan processes [RAN: `/tmp/p2_orphan.py`] — the interpreter's exit handler joins the pool, so the pool must be shut down deterministically in a `finally`, never left to exit handling. `library_sources` imports in 20 ms and has no Tk and no import-time side effects beyond constants [RAN], so a spawn child re-importing it is cheap.

Coupling inventory. The worker loop is the only production caller of the parse; the timing script's `run_pass` re-implements the same loop for measurement (passes 1–2) and `run_incremental_pass` runs the real worker (pass 3). The delivery dict's keys (`skipped_files`, `files_without_charts`, `skipped_blocks`, `nested_song_tree`, `refreshed_at`, `cache_error`, `manifest_error`, `source_paths`, `generation`, plus `reparsed_files` when incremental) are consumed by `_poll_load_results` and `_loaded` positionally-by-keyword; the progress tuple is `("progress", done, total, generation)` and the ETA in `_show_load_progress` is a straight line from `done / total`. The manifest's `new_entries` is a dict keyed by file name, and `ManifestStore.write` sorts it on write, so its build order carries no meaning. The layer table puts `library_loader` at layer 3 and `library_sources` at layer 2, so the loader may import from the sources module but not the other way round; the layer test (`tests/test_layer_enforcement.py`) fails any same-layer or upward import and any new Tkinter importer. Tests that touch the loop: `tests/test_library_loader.py` (worker tests, including three that patch `loader.parse_cache_file` with a counting or failing wrapper), `tests/test_manifest_refresh.py` (which counts real parses through the same patch), `tests/test_library_sources.py`, and `tests/test_end_to_end.py`. The full suite at this base is 1000 tests OK, 74 skipped headless [RAN: Python 3.12.3, fresh worktree off main `823e8ea`]. No `multiprocessing` exists anywhere in the repo today. `launch.py` already has the `if __name__ == "__main__": main()` guard a spawn child needs.

## 3. The Decisions

Seven real choices, each with a recommendation.

**D1. Mechanism: `concurrent.futures.ProcessPoolExecutor` with the spawn context, explicit.** The executor is the maintained surface for process pools, its Future API fits the chunk-collection loop (collect as chunks complete, cancel the rest on staleness), and passing `mp_context=multiprocessing.get_context("spawn")` makes Linux CI exercise the same start method Windows uses — the platform default would silently be fork on Linux and spawn on Windows, and the two do not behave the same. The alternative is `multiprocessing.Pool`, the older API over the same engine, with `imap`/`map` instead of Futures; it is equally capable but its staleness handling (terminate the whole pool) is coarser than cancelling pending futures. Threads are not an alternative at all: the parse is CPU-bound pure Python, and the GIL caps threads at one core's worth of it. `ProcessPoolExecutor` is the recommendation.

**D2. Scores travel once per worker, through the pool initializer, into a module global in `library_sources`.** Each worker receives the scores dict once at start-up, builds its Edit index from it once, and keeps both in module globals the task function reads. The alternative is passing the scores with every task: at the fixture scale that costs nothing measurable (0.8 ms for 96 pickles), but at the owner's scale it would pickle the whole scores dict once per chunk — ~235 times at a chunksize of 32 — for no reason. A third alternative, a shared-memory block or a side-channel file the workers read, adds a second scores path for a saving the initializer already gives. The initializer is the recommendation; the globals are confined to worker processes, set exactly once per worker, and named so.

**D3. Results arrive unordered, tagged by file index, and the worker re-sorts into file order before delivery.** `imap_unordered` (or `submit` + `as_completed`) keeps every worker busy — a slow file cannot stall the stream behind it — and each result carries its position in the scanned list, so the merge step sorts by index and the delivered rows, counts, and manifest entries are exactly the serial ones. The alternative is ordered `imap`, which preserves file order for free but head-of-line blocks: one pathological file holds up every result behind it, and the progress bar stalls with it. The single ordered delivery is unchanged either way; unordered plus a re-sort is the recommendation.

**D4. Pool lifetime: created per refresh inside `_load_worker`, shut down in a `finally`.** A fresh pool per full parse means the scores are always current, no process outlives its scan, and there is no exit-time lifecycle to manage — the cost is one spawn per worker per full parse, amortized over a ~29 s parse. The alternative is a long-lived pool kept across refreshes, which saves the spawn cost but holds eight processes and a stale scores copy between scans, needs an explicit shutdown on window close, and couples the pool's lifetime to the app's. The per-refresh pool is the recommendation; the long-lived pool is Q4's follow-up if the spawn cost ever dominates.

**D5. Engagement rule: the pool runs only when the parse list is at least T files; below T the serial loop runs exactly as today.** The pool's fixed cost is the spawn (~115 ms per worker on Linux [RAN]; Windows unmeasured) plus the pickled results' return trip, and a warm refresh after P1 usually has a parse list of zero to a handful — pooling that would be pure overhead. T is a module constant set by the pass-4 measurement (§4.5), starting estimate in the low hundreds: the break-even arithmetic is pool cost ≈ spawn + N×3.9/8 ms against serial N×3.9 ms, so N ≈ spawn / 3.4 ms — about 300 files for a 1 s spawn, about 1,200 for a 4 s one [INFERRED]. The alternative is always pooling, which is simpler and wrong for the common case. The threshold is the recommendation.

**D6. Failure rule: any pool failure falls back to the serial loop; per-file parse failures keep today's counting.** If the pool cannot start, a worker crashes (`BrokenProcessPool`), or a future raises outside a per-file parse, the worker shuts the pool down and re-parses the remaining files serially, where the existing per-file try/except counts failures into `skipped_files` exactly as today. A pool problem must never lose the library or fail the load. The alternative — failing the load on a pool error — would make a new mechanism a new way to lose a refresh. The fallback is the recommendation.

**D7. Worker count: `os.cpu_count()`, no settings key, settled finally by the pass-4 measurement over 4/8/16.** The count is a module constant, not a constructor input and not a settings key: a new persisted key for a number the measurement can settle would be a second proposal's worth of surface for a constant. On the owner's machine `os.cpu_count()` is 16 (8 cores / 16 threads); pure-Python regex work gains little from hyperthreading, so the measurement may well land on 8, and the implementation PR sets the constant from what it measures rather than from this proposal's guess. The alternatives are a fixed 8 (a magic number that misfires on any other machine) and a settings key (deferred — if the measurement shows a real need for user control, that is a follow-up, not this proposal). `os.cpu_count()` with a measurement-settled constant is the recommendation.

## 4. Recommended Design in Detail

**4.1 The pool task function (layer 2, `library_sources.py`, beside `parse_cache_file`).** One-sentence description: given a file path as a string, it parses that one cache file with the scores the pool initializer handed its worker, and returns the file's index, rows, and skipped-blocks count — or raises, exactly as `parse_cache_file` does today.

It is a module-level function, because only module-level functions cross the spawn boundary — a lambda, a closure, or a method cannot be pickled, which the sandbox measurement confirmed by failing on a lambda [RAN]. It takes the path as a string (cheap, unambiguous across processes) and returns `(index, rows, skipped_blocks)`; the index is the file's position in the scanned list, which is what the merge sorts on. It calls `parse_cache_file` with the worker's module globals and nothing else, so the parse itself is untouched — the pool is a calling convention around it, not a second parse. The initializer sets two module globals, `_worker_scores` and `_worker_edit_index`, built from the scores dict the parent passes once per worker; the globals are documented as worker-process-only and are never read on the parent side. No Tkinter enters the picture: the child re-imports `library_sources`, `library_format`, and `library_constants` only, which import in 20 ms with no Tk [RAN].

**4.2 The worker loop (`_load_worker`).** The loop as P1 leaves it stays the decision loop: the scandir walk, the manifest comparison, and the per-file reuse-or-parse decision do not move. What changes is the parse branch. After the walk, the worker builds the parse list — the scanned files the decision loop would parse, in walk order, each with its index — and counts it. If the list is shorter than T (§4.5), the existing serial loop runs untouched. Otherwise the worker creates the pool (`ProcessPoolExecutor`, `max_workers` from §4.5, `mp_context` spawn, initializer from §4.1) and submits the list in chunks of 32 (§4.5). As each chunk's results arrive, the worker: records completed files for progress (reported on the same every-25 cadence the loop uses today, so the bar and the ETA behave identically); checks the generation, and on staleness cancels pending futures, shuts the pool down without waiting, and returns without delivering — staleness is noticed at chunk granularity, so the overshoot is at most one chunk's duration (~125 ms at 32 × 3.9 ms [INFERRED]); on a per-file exception, counts `skipped_files` and records no manifest entry, exactly as the serial branch does. When all results are in, the worker sorts them by index and runs the existing merge code over them — the rows extend in file order, `skipped_blocks` sums, `files_without_charts` counts the zero-row results, `new_entries` is built per file from the results' rows and the walk's stats, and `reparsed_files` counts the files submitted to the pool plus any serial fallbacks. The merge, the `merge_scores` step, the snapshot-then-manifest write under the one lock, and the single `("loaded", ...)` delivery are all unchanged. The pool's shutdown sits in a `finally` around the whole parse section, so every exit path — normal completion, staleness, exception, pool failure — closes it; the sandbox measurement is why this is not left to exit handling [RAN: an un-shut-down pool delays parent exit by the longest running task].

**4.3 Failure handling.** Three levels, innermost first. A per-file parse failure raises inside the task function, surfaces as a failed future for that one file, and is counted in `skipped_files` with no manifest entry — the same outcome as the serial branch, and the same test pins it. A worker crash kills the pool (`BrokenProcessPool` on the next result read): the worker shuts the pool down and re-parses the remaining files serially, so one poison file cannot lose the library — and the fallback does not re-submit the crashed file to the pool, so a file that kills workers cannot loop. A pool that cannot start at all (spawn error, frozen-executable packaging without `freeze_support()`) is caught at creation and the whole list goes serial. `freeze_support()` itself is not called: the app runs as `python launch.py`, where it is unnecessary, and it is recorded here as a packaging precondition for the day the app is ever frozen, not as a code change in this proposal.

**4.4 The constants (worker count, chunksize, threshold).** All three are module constants in the loader, set from the pass-4 measurement (§6) before the implementation PR lands: worker count from trying 4/8/16 on the owner's machine, chunksize starting at 32 (DeepSeek's 32–128 range, low end: 7,499 files at 32 is 235 chunks over 8 workers, enough for balance and for progress to move smoothly), threshold T from the break-even arithmetic in D5 with the measured spawn cost. None of the three is a settings key and none is a constructor input; the loader's constructor is untouched. If the measurement shows the count wants to vary by machine in a way a constant cannot express, that is a follow-up proposal, not a silent settings key added here.

**4.5 The timing script (pass 4).** `tools/time_refresh_parse.py` gains a fourth pass: a full parse through the pool over the same cache folder, at worker counts 4, 8, and 16, reporting pool startup, parse wall time, files/s, and the peak RSS of the parent process, for both the warm case (pass 2's conditions) and the cold case (OS cache dropped, where the disk dominates). Pass 4 runs the real worker path, not a re-implementation — the same way pass 3 runs the real incremental worker — so its number is the worker's own. The pass also prints the scores dict's entry count and pickle size, which is the number §2 could not state without the owner's Stats.xml.

## 5. What Does Not Change

- The snapshot format, the manifest format, and the manifest's invalidation rules (proposal 0018, D2): the pool only reads cache files and writes the same manifest entries the serial loop writes.
- The delivery contract: one `("loaded", ...)` message with the rows in file order and the same kwargs; `reparsed_files` counts pool-parsed files exactly as serial-parsed ones, and the status line is untouched.
- The scores sync: it never parses, so it is untouched, and it still refuses to start while a scan is in flight.
- The table insert (P5's target): P2 keeps the single-delivery contract, so P5's streaming is neither built nor blocked — the pool's chunk stream is the natural source for it if P5 wants it, and that choice stays P5's.
- The parse itself, the scores lookup, and the Edit fallback: `parse_cache_file` is called, not rewritten.
- No new module, no new settings key, no constructor change, no layer-table change; `launch.py`'s `__main__` guard already satisfies the spawn child.
- Ground-clearing for later themes: theme 2's Pack.ini read is a post-scan step over the same walk P2 leaves alone; theme 3's song page and GrooveStats read rows whose shape P2 does not change; theme 5's library writing will write cache files, and the pool only reads them — a future writer invalidates the manifest by P1's rules, which P2 does not weaken; the read-only cache-cleanup candidate's walk and per-file records are the ones P2 uses, not ones it replaces.

## 6. Test Plan (for the implementation PR)

- **Differential tests** (loader tests, on fixture folders): the pool path and the serial path deliver identical rows, row order, counts (`skipped_files`, `files_without_charts`, `skipped_blocks`), and manifest entries on a fixture library with a changed file, a new file, a deleted file, a failed file, and a duplicate-song pair. These assert on delivered rows and counts, not on parse call counts: a parent-side patch of `parse_cache_file` does not reach the workers, so the existing counting wrappers cannot see pool parses — the differential assertion is the seam that replaces them.
- **Threshold test:** a parse list below T never creates a pool (assert by patching the pool constructor to raise — the load still delivers, serially).
- **Staleness test:** a second Load started while the pool is parsing supersedes the first; the first delivers nothing, its pool is shut down, and the second's rows are the ones shown.
- **Fallback tests:** pool creation raising delivers the full library serially; a worker crash (`BrokenProcessPool`, simulated) falls back to the serial loop for the remaining files, including the file whose task crashed.
- **Pool task tests** (sources tests): the task function parses one file with initializer-set globals and returns the index, rows, and skipped-blocks count; a malformed file raises.
- **Wiring guard:** the constants exist, the threshold is honoured, and the loader's constructor signature is unchanged (the existing construction test pins the input list).
- **Timing:** pass 4 of `tools/time_refresh_parse.py` runs on the owner's machine before the constants are set — worker counts 4/8/16, warm and cold, with the spawn cost, the parse wall time, and the peak RSS printed. The sandbox cannot show the win (1.5 shared CPUs, 6 fixture files); the implementation PR's numbers come from the owner's machine.
- **Full suite:** `python -m unittest discover -s tests` green (1000 tests, 74 skipped headless, at the base). The pool tests force the spawn context on every platform, so Linux CI exercises the same start method Windows uses.
- **Windows smoke (owner):** a real full refresh on the library, then closing the window mid-parse and confirming in Task Manager that no `python.exe` workers remain.

## 7. Open Questions for Reviewers

- **Q1.** Worker count: `os.cpu_count()` (16 on the owner's machine) or a cap at the physical core count (8)? Recommendation: `os.cpu_count()` as the constant, with pass 4 trying 4/8/16 and the implementation PR setting the number from what it measures — hyperthreading gains little for pure-Python regex work, so the measurement may well land on 8, but the proposal does not guess it.
- **Q2.** Threshold shape: a fixed file count T, or a threshold that scales with the list — pool when the estimated serial time (files × 3.9 ms) exceeds the measured spawn cost? Recommendation: a fixed T from the break-even arithmetic, because the spawn cost is a constant and the per-file cost is stable; a scaling rule adds a second constant to tune for no measured benefit.
- **Q3.** Should pass 4 measure the cold read (OS cache dropped) as well as the warm full parse? Recommendation: yes — the cold 106 s is disk-bound, and the proposal's claimed win is the warm full parse; measuring cold keeps the claim honest and tells the owner what the first run after a reboot actually costs. The design does not change either way.
- **Q4.** If the spawn cost dominates on the owner's machine, should a long-lived pool across refreshes be built now instead of per-refresh? Recommendation: no — build per-refresh, measure, and revisit only if the spawn cost is a visible fraction of a full parse; the long-lived pool's lifetime and stale-scores problems are real, and the spawn cost is amortized over ~29 s of parsing.
- **Q5.** Memory: eight workers each hold a copy of the scores dict plus an interpreter — is the transient peak acceptable on a normal Windows desktop, and what ceiling should stop the pool from engaging? Recommendation: pass 4 measures peak RSS and the implementation PR reports it; if it exceeds ~1 GB the threshold or the worker count is revisited. The scores dict's entry count and pickle size on the owner's machine are the numbers §2 could not state — pass 4 prints them.
