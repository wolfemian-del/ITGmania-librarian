The library gains a pack and series view: a tree that shows series as parent rows, packs under them, and songs under the packs, with pack and series banners. The view reads `Pack.ini` from each pack's real folder (the cache carries no Series), finds the game's install Songs folder that the app cannot reach today, and takes Pillow as the shared image layer so JPEG and BMP banners and song art display instead of showing placeholders. The one real decision is the shape: a tree view mode switched from the flat table, built on a separate post-scan Pack.ini read that leaves the snapshot alone.

## 1. Background and Goal

Theme 2 of the roadmap, after the faster-refresh suite and the main-window geometry work. The game organises songs by pack and series; the app today shows only a flat table with a Pack column and a pack dropdown. A pack/series view lets the owner browse the library the way the game presents it, and it is the surface the theme-3 song-page overhaul and multi-select work will build on.

Done means: the view shows every pack under its series (or under "No series"), with the pack's display title, a distinct-song count, and its banner; a series row shows its banner and its song count; packs whose folder cannot be found are labelled "Series unknown", not "No series"; the unsorted/load-order state of the flat table is untouched; and the whole thing works for a typical ITGmania user, not just the owner's own library — the owner has no packs in the install Songs folder, but that is an accident of his installs, and a typical user would use that directory.

This is a theme, not a single change, so it gets one proposal that settles the design and stages the work. It creates a new component boundary (the Pack.ini read), persists a new settings key (the install Songs folder), adds a dependency (Pillow), and has several two-or-more-defensible-design choices — every one of the proposal triggers in `AGENTS.md`.

## 2. Current State (measured on main `4bbe911`)

**The data the view needs is not in the cache.** The cache carries no Series, and the engine's cache code never touches it [CODE: `docs/research/pack_series_view_research.md` §1.4, verified against v1.3.0]. `parse_cache_file` derives `Pack` from `#SONGFILENAME` as the first path segment after `Songs`/`AdditionalSongs` — the pack's folder name, not a display name [CODE: `itgmania_library/library_sources.py:264-267`]. Rows are charts, not songs, and the snapshot schema is version 6 (`LIBRARY_CACHE_SCHEMA_VERSION = 6`, `itgmania_library/library_stores.py:22`). There is no Pack.ini, Series, or pack-banner code anywhere in `itgmania_library/` [CODE: grep].

**The Songs folders the app knows.** `library_media.song_roots(cache_dir)` (`itgmania_library/library_media.py:94-139`) builds the ordered roots from `<user-data>/Save/Preferences.ini` (`AdditionalSongFolders*`, `AdditionalFolders*`) plus `<user-data>/Songs`. Its docstring states the install Songs root cannot be derived from the cache dir and is not supplied, and that `Data/Static.ini` can override `Preferences.ini` and is not read. The only caller is the song page (`library_librarian.py:882`). The Data paths dialog asks only for "Cache / Songs" and "Player Stats.xml" (`itgmania_library/data_paths_dialog.py:109-110`); there is no setting for a Songs folder.

**The scan.** `LibraryLoader._load_worker` (`itgmania_library/library_loader.py:424`) lists the flat cache folder and parses each file, then writes a snapshot. The README states the Songs tree is not scanned recursively.

**Images today.** `song_page.py` `SongPage._load_image` (`:427`) loads PNG only via `tk.PhotoImage`; anything else returns `None` and takes the placeholder path, and a corrupt PNG becomes a placeholder through `TclError`. `_BANNER_MAX_WIDTH = 700`, `_SMALL_IMAGE_MAX_WIDTH = 220` (`:37-38`). `requirements.txt` lists `matplotlib` and `pygame-ce>=2.5.8` and no Pillow; its comment says the app runs on the standard library alone. Proposal 0011 explicitly deferred Pillow until format counts justified it.

**The table and filter.** The main window holds one table (`LibraryTable`, `library_librarian.py:596`) and one filter (`LibraryFilter`, `:540`); there is no Notebook or tab mechanism, so a view mode is a new switch. The filter's pack dropdown lists the sorted distinct `Pack` values with "All packs" first (`library_filter.py:132`) and filters on exact Pack equality (`:199`). There is no display-order accessor yet — the song-page Previous/Next navigation (issue #263) has not been built — so the view must not invent its own ordering that a later accessor cannot serve.

**The owner's library, measured 2026-11-28** (corpus scan, script `scan_pack_series_corpus.py`, run on his Windows machine over `C:\Games\OutFox 0.5.0 Alpha Win64\Songs` and `C:\Games\Shared Songs`, both `AdditionalSongFoldersWritable` in `Preferences.ini`): 207 packs; 185 (89%) have a `Series=`; 10 distinct series; 1 one-pack series. Pack.ini is present on 172/175 packs in the first root and 14/32 in the second; every Pack.ini with a `Version=` has one. **No pack anywhere sets `SeriesBanner=`** — every series banner in his library comes from the fallback (the alphabetically-first pack's ordinary banner). Pack banners: 193 PNG, 5 JPG, 1 BMP (97% PNG); 8 packs have no banner; explicit `Banner=` is rare (9 total), the extension search is the workhorse. Pack banner dimensions: median 256×80, max 3483×1368, which is 18.2 MB decoded as RGBA. Song media (20,204 image files): 19,235 PNG, 201 JPG, 3 JPEG, 764 BMP, 1 GIF — about 969 files (~5%) are non-PNG and invisible on the song page today, with the BMPs all in Shared Songs.

**The surveys, and what each settled.** Grok (Pack.ini + Series, against v1.3.0) verified the parsing rules — a non-empty `[Group]` `Version=` gates the whole file and any non-empty string counts; keys are exact and case-sensitive, values are trimmed of `\r\n\t `, duplicate keys are last-wins; Series is the exact trimmed string, byte-exact and case-sensitive — and the banner rules: `SeriesBanner` resolves by directory listing only (a matching folder counts, no image or extension check, no automatic extension search), the first pack in byte-order of folder name whose value resolves wins, and the fallback is the alphabetically-first pack's ordinary banner without skipping a bannerless first pack. A one-pack series gets a parent row in v1.3.0; beta suppresses it. Codex (image loading) established that the engine accepts PNG, GIF, JPG, JPEG and BMP for banners, that Tk `PhotoImage` is PNG/GIF only, and recommended Pillow as the single decode/resize layer with lazy visible-row loading and a bounded LRU cache of display-sized images (40–60 MB starting budget), contain/letterbox scaling, no stretch or crop. Gemini 4 Hydrogen (Songs-folder discovery) established that the official installer defaults to `C:\Games\ITGmania` (not Program Files) and writes the registry key `Software\ITGmania Developers\ITGmania` (HKLM or HKCU), that ITGmania is not on Steam, and the engine's mount logic (executable path → parent = install root → `<root>\Songs`, with `Portable.ini` keeping everything inside the install and `%APPDATA%\ITGmania` otherwise). All three surveys were read and their load-bearing claims checked against the code where the code could speak; the app-side claims all hold on main.

## 3. The Decisions

**D1. The view is a tree — series parent rows expand to pack rows, which expand to song rows — as a view mode switched from the flat table.** The hierarchy is a tree by nature and it mirrors the game's wheel. The rejected alternatives are grouping headers on the existing table (which would tangle the flat table's sorting with the hierarchy) and a separate side panel (which would split the user's attention between two views of the same library).

**D2. The view shows pack and series banners.** Banners are the visual identity of a pack and a series, and the paths come free with the Pack.ini read. The rejected alternative is text-only rows, which would leave the banner data unread and the view indistinguishable from a grouped table.

**D3. The pack label is DisplayTitle for display; the folder name is the join key.** DisplayTitle is what the game shows and it falls back to the folder name when empty; the folder name stays the identity everywhere it already is (`Pack` in rows, `Course path`, `.crs` files). The rejected alternative is showing the folder name in the view, which would discard a display name the read already provides.

**D4. Counts are distinct songs.** The game's wheel counts songs, and the view is about packs and series, not charts. The rejected alternative is chart-row counts, which would inflate every number by the charts-per-song ratio and disagree with the game. (The app's rows are charts, so the count needs a distinct-song dedup.)

**D5. Take Pillow (`Pillow>=12,<14`) as the shared image layer.** The corpus scan justifies it in numbers: ~969 of 20,204 song images (~5%) are non-PNG and invisible today, and the shared loader closes the song-page JPEG gap with the same code that serves the view. The pin preserves the Python 3.10 minimum (Pillow 12 supports 3.10–3.14; 13 drops 3.10). The rejected alternative is staying PNG-only with Tk, which would leave those ~969 images as placeholders and limit pack banners to PNG/GIF for no reason other than avoiding a dependency. This ends the app's "stdlib alone" stance; `requirements.txt` and `README.md` gain the entry, per `AGENTS.md`.

**D6. The install Songs folder is a new settings key (`install_songs_dir`), set via Data paths, found by Gemini's discovery order.** Saved setting first, then the portable check via `cache_dir`, then the Windows registry (`Software\ITGmania Developers\ITGmania`, then the Uninstall entry, then the `.smzip` association), then common paths starting with `C:\Games\ITGmania`, then a file-dialog fallback accepting either `ITGmania.exe` (under `Program/`) or a `Songs` folder directly. Every candidate is accepted only if its `Songs` folder exists on disk. The owner has no packs in the install Songs folder, but that is an accident of his installs and a typical user would use that directory, so the discovery belongs in the theme on its merits. The rejected alternatives are deriving it at runtime each launch without persisting (which would re-run the registry and path probes on every start) and accepting the gap (which would silently report install-only packs as having no series).

**D7. The `Data/Static.ini` gap is fixed in the theme.** `song_roots` reads `AdditionalSongFolders*` from `Preferences.ini` only, but `Data/Static.ini` overrides `Preferences.ini`, so a user who overrides only there is missed. It is the same `song_roots` code the theme depends on for complete roots, and the fix is small. The rejected alternative is filing it separately, which would leave the theme building on a known-incomplete root list.

**D8. The Pack.ini read is a separate step after the scan, not snapshotted (Claude's Option B).** A small Tk-free data function takes the set of `Pack` values and the roots and returns the pack → fields mapping; it runs on the worker thread after a scan and also when the view opens after a snapshot restore. No schema change (the snapshot stays version 6), and Pack.ini is read fresh each time, matching how the game only reads it at load/reload. The rejected alternatives are inside the scan worker (which would bump the snapshot to version 7 and mix a second file source into `_load_worker`) and lazy-only-on-view-open (which is the same function called later, so the choice can be made at implementation time without changing the design).

**D9. Mirror the game exactly on case-sensitive grouping.** `"ITL Online"` and `"ITL online"` are separate series, and case variants can yield repeated parent rows — that is what the game shows. The rejected alternative is folding case for grouping, which would hide a Pack.ini typo instead of showing what the game will show. A near-duplicate warning is a possible later addition, not a grouping rule.

**D10. One-pack series follow v1.3.0: always show the parent row.** That is the pinned version's behaviour; beta suppresses it, but beta is unverified at head. The data model carries the pack count per series so the UI can change later without a rework. In the owner's library this affects one series out of ten.

## 4. Recommended Design in Detail

**Component boundaries.** Three new pieces, each behind a clear boundary:

- **The pack data module** (new `itgmania_library/library_packs.py`, Tk-free, tested). It owns the Pack.ini read: given the set of `Pack` values from the loaded rows and the ordered song roots, it returns a pack → fields mapping (`Series`, `DisplayTitle`, `SortTitle`, `Banner`, `SeriesBanner`, `Year`, plus whether a Pack.ini was found and whether its `Version=` was valid). The parser copies the engine's rules from §2 and Grok's survey: exact `[Group]`, case-sensitive keys, trim only `\r\n\t `, first `=` splits, last duplicate wins, comments and line-continuation as the engine has them. It resolves the pack banner (explicit `Banner=` first, then `*.png` / `*.jpg` / `*.jpeg` / `*.gif` / `*.bmp` in the pack folder, then beside it) and the series banner (explicit `SeriesBanner` only, by directory listing; first pack in byte-order of folder name whose value resolves wins, else the alphabetically-first pack's ordinary banner, without skipping a bannerless first pack). It does not touch the snapshot, the table, or the filter. The one-sentence description a standalone reader needs: given pack names and song roots, it returns what each pack's Pack.ini says and which banner the game would choose.
- **The song-roots extension** (in `library_media.py`, where `song_roots` already lives). It gains the install Songs folder as one more root, found by D6's discovery order, and the `Data/Static.ini` override (D7). The registry read is Windows-only (`winreg`) and is guarded so other platforms skip it. The Data paths dialog gains a Songs-folder row beside "Cache / Songs" and "Player Stats.xml", and the new `install_songs_dir` settings key is persisted the way the existing keys are.
- **The image layer** (new Tk-free helper, e.g. `itgmania_library/library_images.py`, plus the Tk-specific `ImageTk.PhotoImage` construction in the UI layer). Pillow decodes and resizes; the UI layer turns the result into a Tk image. Images load lazily as rows become visible, are resized to their display size before being handed to Tk, and are kept in a bounded LRU cache of display-sized images keyed by canonical path, modification time, file size, and target box — starting budget 40–60 MB decoded, tuned from measurements. The largest pack banner in the owner's library decodes to 18.2 MB, so resize-before-caching is load-bearing, not an optimisation. The same loader and cache serve the song page, which closes its JPEG gap. Scaling is contain/letterbox by default: never stretch, never crop. Missing, unsupported, or corrupt files take the existing placeholder path.

**The tree view.** A view mode on the main window, switched from the flat table (the switch itself is a new UI element, e.g. a View-menu item; the exact control is for the implementation PR's mockup, since the owner approves look and feel). Its rows are series parents, then pack rows, then song rows. A series row shows the Series text (via the game's shortening only if the view adopts it — DisplayTitle rules are for packs, and the series label is the exact string), its banner, and its distinct-song count. A pack row shows its DisplayTitle, its banner, and its distinct-song count. A song row is the song (not a chart row — the tree groups by song, and the chart detail stays on the flat table and the song page). Packs with no Series sit under "No series"; packs whose folder is not found in any known Songs root sit under "Series unknown", never silently as "No series". The tree shares the filter (pack, type, difficulty, search) — it does not invent a second filter — and its row order follows the same ordering the table uses: series by Series text, packs inside a series by SortTitle, standalone packs interleaved by SortTitle, per the engine's `MakeSortString` rules.

**Ground-clearing (themes 3 and 6).** The view must not foreclose the later themes. Its row order goes through the same ordering the table uses, so that when the song-page Previous/Next navigation (issue #263) builds its display-order accessor, that accessor serves both the table and the tree instead of the tree having grown its own ordering. The filter contract is shared, not duplicated. Pack identity stays the folder name everywhere. And the data model carries the per-series pack count (D10) so the one-pack rule can change without a rework.

**Staging (implementation PRs, in order).** (1) The data layer: the pack-data module, the song-roots extension with the new settings key and the `Static.ini` fix, and the Data paths row — no UI, proved by tests and the corpus numbers. (2) The tree view: the view mode, the tree, the labels, counts, and the "Series unknown" distinction — proved by tests and a live smoke. (3) Images: Pillow, the shared loader and cache, pack/series banners in the view, and the song-page JPEG gap closed by the same loader — proved by tests, the corpus numbers, and a live smoke. Each stage lands as its own PR; the proposal's design is settled now so the stages do not re-litigate it.

## 5. What Does Not Change

- The snapshot schema stays version 6; the cache format is untouched, and Series is never written into the cache.
- The flat table, its sorting, its filters, and the saved `sort_keys` / `column_order` / `column_widths` are untouched. The unsorted/load-order state is untouched.
- The song page's layout and behaviour are untouched except that its image loader becomes the shared one (so JPEG and BMP art displays instead of taking the placeholder path).
- The course builder, the distribution panel, and the filter dropdowns are untouched.
- The first-launch defaults are untouched: the Pack dropdown still defaults to "All packs", and the table still defaults to Pack ascending.
- The settings format is unchanged except for the one new key, `install_songs_dir`.
- No new file format is introduced, and no existing settings key changes meaning.

## 6. Test Plan (for the implementation PRs)

- **Stage 1 (data layer).** Tests for the Pack.ini parser against the engine's rules (exact `[Group]`, case-sensitive keys, trim, last-duplicate-wins, the `Version=` gate, comments and line continuation); tests for pack-banner and series-banner resolution (explicit value, extension order, beside-the-folder fallback, the byte-order first-pack rule, the no-skip fallback, a folder counting as a resolution); tests for the discovery order (saved setting, portable check, registry, common paths, file dialog) with the registry step skipped off Windows; tests that `Static.ini` overrides `Preferences.ini`; tests that a pack in no known root reports "Series unknown" and not "No series". The corpus numbers from §2 are the acceptance data: 207 packs, 185 with a Series, 10 distinct series, 0 `SeriesBanner=` values.
- **Stage 2 (tree view).** Tests for the tree structure (series parents, pack rows, song rows, "No series" and "Series unknown" groups), the DisplayTitle label with the folder-name fallback, distinct-song counts, and the shared filter. A live smoke on Windows: open the view, expand a series, open a song page from a song row.
- **Stage 3 (images).** Tests for the loader (all five formats, corrupt and missing files taking the placeholder path, resize-before-cache, the LRU bound); the corpus numbers are the acceptance data (pack banners 97% PNG; ~969 non-PNG song images; largest pack banner 18.2 MB decoded). A live smoke: the view's banners display, and a JPEG song banner displays on the song page.
- **Suite.** Full suite green at each stage (`python -m unittest discover -s tests`); README gains the Pillow entry and the view's description; `requirements.txt` gains `Pillow>=12,<14`.

## 7. Open Questions for Reviewers

- **Q1.** Is the tree-as-a-view-mode the right shape, or should the hierarchy live in the flat table as grouping headers? The recommendation is the tree (D1).
- **Q2.** Is Pillow the right call now, with the corpus numbers as the justification (~969 non-PNG song images, ~5%), or should the theme stay PNG-only and leave the song-page JPEG gap for later? The recommendation is to take Pillow (D5).
- **Q3.** Is the staging right — data layer, then tree, then images — or should banners land with the tree in one PR? The recommendation is the three stages in §4.
- **Q4.** Should the "Series unknown" vs "No series" distinction also surface in the flat table (e.g. a marker), or only in the tree view? The recommendation is the tree view only.
