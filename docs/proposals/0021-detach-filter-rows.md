---

In plain language: applying a difficulty filter and then removing it rebuilds the entire table today, with a considerable load time. The rows do not come back for free — every one of the 42,375 is re-created through a fresh insert. This proposal keeps the hidden rows instead of throwing them away: a row the filter hides is detached, not deleted, so it stays inside the widget with its values and tags, invisible, and removing the filter puts it back without an insert. The table still shows exactly the same rows in exactly the same order, and nothing about the app looks different. The only visible change is that a filter toggle gets fast. The one real decision in this proposal is how the hidden rows come back: the first draft said one move per row to its index, and the owner's trial refuted that — each returning row is moved back cheaply, to "end" on a large restore, and the final `set_children` call puts the whole level in order.

## 1. Background and Goal

P5 (proposal 0019, accepted; implementation PR #271 merged 2026-11-23) stops the table throwing all its rows away on every refresh: `refresh_table` now diffs the new visible set against the tree and only inserts, deletes, or updates what actually changed. That fixes the refresh, the sort click, and the sync — all cases where most rows survive. A filter toggle is the case it does not fix. Applying a difficulty filter narrows the visible set, so the diff deletes the rows that leave it; removing the filter puts them all back, and every returning row pays a fresh `tree.insert` through the time-boxed batch walk. The owner's smoke of PR #271 (2026-11-23) saw the reload case look good — the table stays put when nothing changes — but the filter round-trip still rebuilds the table, because the rows are gone by the time the filter is removed. Proposal 0022 (accepted; PR #277 merged 2026-11-24) then removed the other half of the toggle's cost, rebuilding display tuples only for rows the loader says changed; the two proposals sequence because both touch `_apply_diff`, and 0022 is now landed, so this one is next.

The goal is to make the filter round-trip cheap the same way P5 made the refresh cheap: keep what you have, change only what differs, one step further — a row that leaves the visible set is not necessarily gone, only hidden. Done means: applying a filter and then removing it restores the table by reattaching the hidden rows, with item ids stable across the round-trip; no visible behavior change except speed; the full suite green; and a driver re-run on the owner's machine that times the filter-toggle round trip after the change against the 12.30 s widen it costs today, so the win is measured, not asserted. This change creates no new component boundary and moves none: it adds a third fate for a row inside `_apply_diff` and a branch inside `_apply_diff_batch`, both in `library_table.py`, and one small operation on the tint tracker in `row_tints.py`. The filter stays the single holder of the rows, the loader's delivery contract does not change, and no settings key or file format is involved.

## 2. Current State (measured on main `4320424`)

The delete path is `_apply_diff` [CODE: `itgmania_library/library_table.py:563`]: for every item whose key is not in the new visible set (or whose song collides), the diff calls `self.tree.delete(item)` and discards the item from `_tree_item_rows` and `_tree_item_display` [CODE: `library_table.py:594-600`]. Once deleted, the item id is gone — there is nothing to restore, so the next refresh that needs the row must `tree.insert` it fresh in `_apply_diff_batch` [CODE: `library_table.py:727-732`], under the same 12 ms time-boxed walk as a first load (`ROW_INSERT_BUDGET_SECONDS = 0.012` [CODE: `library_table.py:40`]).

The refresh callers are a sort click (`preserve_selection=True`) [CODE: `library_table.py:464`], a scores sync (`preserve_selection=True`) [CODE: `library_librarian.py:801`], a load (through `set_rows`, which notifies the subscription) and the filter subscription itself, which calls `refresh_on_filter_change` [CODE: `library_librarian.py:449`]. That subscription method is new since the first draft of this proposal (Proposal 0022, §4.4): a filter edit refreshes with `changed_keys=set()`, so no display tuple is rebuilt, while a load refreshes with `changed_keys=None`, so every tuple is rebuilt [CODE: `library_table.py:548-561`]. Either way the subscription calls `refresh_table()` with `preserve_selection=False`, so a filter change clears the selection today. The diff itself does not know *why* a row left the visible set: a filter hid it, the library lost it, or a load replaced it all look the same from inside `_apply_diff`.

The numbers are the owner's (42,375 chart rows), measured on the owner's machine 2026-11-23 with the §6 driver, after Proposal 0022 landed: narrowing to one difficulty takes 0.62 s (was 10.01 s before 0022) and widening back takes 12.30 s (was 358.55 s). The remaining widen cost is re-inserting 31,591 rows — the rows the narrow dropped — and the restore is expected to take a few tenths of a second at that scale [INFERRED from the bare-Tk measurement below and Claude's arm table in §6], which is this proposal's case, measured not asserted. The per-item insert cost end to end is roughly 0.31 ms/row [INFERRED], never measured in isolation — which is why a filter round-trip costs on the order of 13 seconds of insert-path work. That figure is the app's whole insert path (tuple building, the batch walk, the panel redraw), not the bare Tk call: Codex's probe measured a bare `tree.insert` at about 15 µs/row on Windows (Tk 9.0, Python 3.14.7) and Muse re-ran the same script under Xvfb (Tk 8.6, Python 3.12.3) at about 5 µs/row — the gap between the bare call and the app's end-to-end cost is app overhead that detach does not remove, so the probe's ratios are a ceiling on the toggle's win, not the win itself. The Tk semantics are now [RAN] on both environments (Codex's report and Muse's Xvfb run agree on every behavior): `move` reattaches a detached item at the requested index; a detached item cannot be selected (`selection_set` leaves `selection()` empty) and detaching a selected row drops it from `selection()`; detaching fires zero `<<TreeviewSelect>>` events; `exists()` returns True and `index()` returns 0 for a detached item (a misleading 0, not an error — the reattach arm must never read a detached item's position from `index()`); values and tags survive; focus stays on the detached item's id; and `delete()` with no arguments deletes nothing. Grok's docs/source check (landed 2026-11-23, man page + ttkTreeview.c + treeview.test) agrees on every behavior and adds two details: `selection_add` on a detached item does not raise and may set the selected bit invisibly (so the detach path must clear it explicitly, not rely on the call failing), and there is no portable way to list detached items (a `detached` subcommand exists only in newer/TIP-enhanced builds), which is why D3 keeps a Python-side set. It diverges from the probe on two points, and the executed probe wins on both: Grok's reading of the regression tests says detaching the focused item clears focus, but both probe runs (Tk 9.0 win32, Tk 8.6 Xvfb) show focus retained — the probe's window was withdrawn, so the real-app behavior is uncertain. That uncertainty now matters: `_invoke_open_row` resolves the focused row through `_tree_item_rows` with no visibility check [CODE: `library_table.py:419-426`], so if focus stays on a detached item, Enter opens a filter-hidden row. The design handles it explicitly either way (D4: relocate focus on detach and gate the open path on visibility), so the divergence changes the design's work, not its validity. Grok calls `delete()` with no arguments invalid, but both probe runs show it executing as a no-op with no error; the design consequence of that divergence is nil. (Muse verified one of Grok's binding claims directly: `Treeview.reattach is Treeview.move` is True in Python 3.12's tkinter.) The timings agree too: reattach beats insert by a paired median of 5.8x at 5,000 rows and 6.2x at 10,000 on Windows, 5.6x at both counts under Xvfb; the full detach-plus-reattach refresh beats delete-plus-insert by 3.1x and 3.2x on Windows, 3.1x and 3.0x under Xvfb. Every paired run favored reattachment, though the spread is real (the paired refresh speedup ranged 1.1x–6.6x at 5,000 rows under Xvfb — one slow detach outlier — against a median of 3.1x). Those ratios measured reattachment to "end" in order, while the app's reattach moves to a computed index — and the owner's trial (D5) has since shown that difference is decisive: move-to-index is O(position) and, at the owner's scale, ~39x slower than delete-plus-insert, so the probe's ratios do not carry over to a per-item reattach arm. The probe script and report are at `~/workspace/user/files/tk_treeview_probe.py` and `tk_treeview_probe_report.md`; Muse's Xvfb run log is at `~/workspace/overnight/tk_treeview_probe_xvfb.log`.

Two facts the design leans on are already settled in the code. First, the filter is the single holder of the rows inside the UI [CODE: `itgmania_library/library_filter.py:112`, `library_rows()`], and the table already reads it — so the diff can ask the filter whether a key is in the library at all, which is the distinction D2 needs. Second, the headless FakeTreeview models insert/delete/move/index/item/selection and `set_children` [CODE: `tests/test_library_table.py:141`, `set_children` at `:189-196` — its docstring already notes that items omitted from a `set_children` list are detached, not destroyed]; `detach` itself is not among the operations it models, so the implementation extends it — the new tests cannot run headless until it does — and its `focus()` returns `""` unconditionally [CODE: `tests/test_library_table.py:229`], so a focus test needs that extended too. Third, the large-placement arm the first draft of this proposal waited on is landed: PR #271 Revision 2 added it (`b44aeab`, "Revision 2: large-placement arm, order rebuild, first-paint fix"), and it is in current main — a placement larger than `SET_CHILDREN_PLACEMENT_THRESHOLD = 50` [CODE: `library_table.py:52`] goes through one `set_children` call instead of per-item moves and inserts [CODE: `library_table.py:673-674`, `:774`], triggered on total placements (displaced plus inserts), not displaced rows alone. The dependency the first draft recorded is closed, and §4.3 builds on that arm directly.

## 3. The Decisions

Eight real choices, each with a recommendation. D7 is a process question for the owner, not a design choice.

**D1. Mechanism: detach instead of delete for rows that leave the visible set.** `tree.detach(item)` removes the item from display but keeps it — its id, values, and tags — inside the widget; `tree.move(item, "", index)` puts it back at a position [RAN: the probe confirms the reattach at the requested index on Windows Tk 9.0 and under Xvfb on Tk 8.6], and one `set_children` call reorders a whole level at once [CODE: `library_table.py:774`, and the FakeTreeview's model of it at `tests/test_library_table.py:189-196`]. The recommendation is detach. The alternatives are the status quo (keep deleting, and pay the full re-insert on every un-filter) and caching the deleted rows' display tuples (which saves the tuple build, not the per-row widget write — and a `tree.item` write costs about as much as an insert, 25 µs against 25 µs [RAN, Muse, Xvfb], so the cache would not remove the load time the owner sees).

**D2. When to detach vs. delete: ask the filter whether the key is in the library.** A row that leaves the visible set is detached when its key is still in the library's rows, and deleted when it is not. The filter already holds the library [CODE: `library_filter.py:112`], so the diff checks membership against a set of library keys — built only when `changed_keys is None`, which is what a load passes; a sort, a sync, and a filter edit all pass a set, and none of them can change library membership (`library_filter.py:98` is the only assignment of `_rows`), so on those refreshes every leaving item is detached and no set is built. No new parameter on `refresh_table`, no caller changes, and the distinction is exact: a filter hides a row that is still in the library, while a load is the only path that removes a song from the library (a sync re-scores in place and never changes the row list [CODE: `library_librarian.py:801` comment]). The build itself is O(N) pure Python over 42,375 rows, tens of milliseconds (35 ms cold / 29 ms warm on Muse's run; 62 ms on Claude's), which is why it is gated on loads rather than paid on every sort click; the `refresh_table` docstring should say a set means "membership unchanged". The alternatives are threading a reason through `refresh_table` (a contract change for a distinction the filter already knows) and detach-always with lazy eviction (which leaves songs deleted from the library detached until a cap evicts them — a second mechanism for a case the membership check already settles).

**D3. Bookkeeping: one owned map plus a detached subset.** `_tree_item_rows` keeps its meaning — every item the table owns, visible or detached — and a new `_tree_item_detached` set holds the detached items. `_tree_item_order` stays visible-only, since a detached item has no tree position. The diff's `key_to_item` is built from all owned items, and the batch walk reattaches a detached item instead of inserting when its key is in the detached subset; on detach, the key leaves `_tree_item_order` and the item joins the subset; on reattach, the reverse. The alternative is split visible/detached maps, which is two sources of truth for one ownership question.

**D4. Selection, tint, and focus: detaching a row drops it from the selection, forgets it in the tint tracker, and relocates focus — all explicitly, in the detach step.** A detached item cannot be displayed, so it cannot be selected: the detach path removes it from `selected_items` (and from the tree's selection if it is there) and tells the tint tracker the item is gone, in the same step — it must not rely on the queued `<<TreeviewSelect>>` event to do the cleanup, because that is exactly the race issue #273 recorded (`reset` running before the event fires). Issue #273 is closed now (2026-11-24, fixed in PR #271 Revision 1 by forcing a rewrite of every item the tint tracker or the selection touches [CODE: `library_table.py:633-638`]), but the lesson stands: the detach step syncs the tracker explicitly rather than relying on the queued select event. The probe answered it: detaching a selected row fires zero `<<TreeviewSelect>>` events [RAN, both environments] — so the explicit sync in the detach step is required, not defensive. The sync needs a named operation the tracker does not have today: `SelectedRowTint` has `on_select`, `note_selected`, and `reset` [CODE: `row_tints.py:41-88`], but no per-item forget that removes the white tag — `reset` replaces the tracked set without touching tags, and `on_select` never runs for a detach. The implementation adds one (e.g. `forget(item)`: remove `SELECTED_ROW_TAG` from the item and discard it from `items`) and calls it in the detach step while the iid is still addressable. `selection_add` on a detached item does not raise and may set the selected bit invisibly (Grok), so the selection sync loop must iterate visible-owned items only and never `selection_add` a detached iid. Focus is a third state, separate from selection: the probe shows focus stays on a detached item, and `_invoke_open_row` resolves the focused row through `_tree_item_rows` with no visibility check [CODE: `library_table.py:419-426`], so Enter after filtering out the focused row would open the hidden song. The detach step relocates focus (to an attached selected or neighbor row, or clears it — deterministic either way) and `_invoke_open_row` is gated on the focused item not being detached, as defense even when focus is normally relocated. `selected_rows()` reads `tree.selection()`, so it stays correct — only visible items can be selected. (An earlier version of this draft claimed a selected colliding row filtered out and back keeps its exact item id; that was wrong — see D8. The Revision 1 carry-the-item policy covers non-colliding rows across filter toggles — the item id survives the toggle, not the selection, which the filter change clears (see Q6); colliding songs keep the delete-and-reinsert fallback.)

**D5. Reattach mechanics: the batch walk gains a reattach arm that is self-contained per item on a large restore.** The first draft of this proposal wrote the reattach arm as a per-item `tree.move(item, "", index)` under the same 12 ms deadline. The owner's trial refuted it (2026-11-23, §6, 42,375 rows): raw detach-plus-reattach 4.25 s (detach 0.04 s, reattach 4.21 s) against delete-plus-insert 0.11 s (delete 0.02 s, insert 0.09 s), so detach-plus-reattach is ~39x slower than delete-plus-insert. The probe's reattach win was move-to-"end" (O(1)); move-to-index is O(position) — Muse's Xvfb micro-benchmark: 114.8 µs/row at 20,000 rows against 4.6 µs/row for insert-at-"end", scaling ~N² — which is Claude's finding 2 in the same clothes. The first version of this section then fed the `set_children` placed list directly: on a large restore, a reattached item was appended to `placed` and the final `set_children` put it in place, with no tree call of its own. That version is also wrong, for a different reason: it discards the item from `_tree_item_detached` per item but attaches nothing until the last batch, so a superseding refresh between batches leaves items marked visible that are still detached, and the next refresh's move branch reads the misleading `tree.index()` 0 and pops the wrong key from `_tree_item_order` (Claude's finding 2, Greptile's P1). The reattach arm is therefore self-contained per iteration: discard from the subset, `tree.move(item, "", "end")`, `order.append(key)`, `placed.append(item)` — all in one iteration — and the final `set_children` only orders [CODE: `library_table.py:774`]. Its subset discard, rebind, and tuple recompute still run per item (§4.3), with the tuple compared before it is written (finding 1). Detach still wins that way: Claude's arm table (Xvfb Tk 8.6, 31,782 restored rows) puts move-to-"end" plus `set_children` at 0.19 s against 4.90 s for the widen today, and the bare-Tk detach plus one `set_children` at 0.026 s against delete-plus-insert 0.104 s at 20,000 rows (4x). The per-item move-to-index survives only for a small restore: when total placements are at or under `SET_CHILDREN_PLACEMENT_THRESHOLD` (50), the walk already takes the per-item arm, and a move-to-index there costs 0.6–1.7 ms each at 42,375 rows, so 50 moves cost 37–85 ms against 13 ms for one `set_children` [RAN, Claude] — the existing threshold still stands, but the cost is milliseconds per move, not microseconds. The trigger must count reattaches, not just inserts and displaced rows: as written, `large_reorder` is `displaced + inserts > SET_CHILDREN_PLACEMENT_THRESHOLD` [CODE: `library_table.py:673-674`], and a pure reattach widen has `inserts = 0` (every returning row is owned) and, under the pinned definitions in §4.2 (`displaced` over attached survivors only), `displaced = 0` on every pure widen under an unchanged sort — the attached survivors are already in the right relative order — so without the term every pure restore would fall through to per-item moves, the refuted case, at full scale. The design adds a third term, `reattaches`, counting the visible rows whose key is owned-but-detached, so the trigger is `displaced + inserts + reattaches > SET_CHILDREN_PLACEMENT_THRESHOLD`. The progress flag takes the same term, so a large restore shows "Loading…" while the walk is still running even when no row is newly inserted and no survivor is displaced. The dependency the first draft recorded — a large-placement arm in PR #271 Revision 2 — is closed: Revision 2 landed it (`b44aeab`), and it is in current main.

**D6. Accumulation: no cap is needed under D2.** The detached set is bounded by "rows in the library but hidden by the current filter" — at most the library itself, which the widget already holds when unfiltered — and it empties on load, since a load's row list will not contain a deleted song's key and D2 then deletes it. The alternative is an explicit cap with eviction, which is an unnecessary mechanism under D2; if D2's membership check ever proves too costly, the cap is the fallback, not the design.

**D7. Measurement: the §6 driver already carries the detach trial, and the implementation PR re-runs it.** The trial has two parts, both in `tools/time_table_refresh.py`: the filter-toggle round trip through the production table (`time_filter_toggle` [CODE: `:118`]), and the raw detach/reattach against delete/insert in a disposable Treeview (`time_raw_detach_reattach` [CODE: `:140`]). Ian's call 2026-11-23 09:36 was yes, it rides in PR #271's Revision 1 — it did, and it ran on the owner's machine the same day, producing the verdict in D5 and the §6 numbers. What remains for this proposal is the re-run on the implementation branch: the toggle round trip is the deciding number, and the raw trial's reattach arm still measures the refuted per-item move-to-index, so the implementation PR adds a raw variant (detach-all, then move-to-"end" per item plus one `set_children` restore) to time the arm this design actually uses.

**D8. Collisions keep P5's delete-and-reinsert fallback; detach applies to non-colliding rows only.** A colliding song's rows cannot be matched key-to-item (a flat `key_to_item` cannot represent duplicate owned keys), and the current code deletes the song's items as a block and re-inserts them fresh [CODE: `library_table.py:594-600`]. On an un-filter, a colliding song's detached items would be deleted by that branch, not reattached — so the draft's earlier claim that a selected colliding row keeps its exact iid across a filter round trip was wrong, and is withdrawn here. The alternative (detach colliding items too, with a key-to-list reattach lookup) buys nothing: the two detached items sharing a key cannot be matched to the two visible rows sharing it without guessing, and guessing wrong swaps their display tuples — so the block re-insert would still be needed, and detach would have saved nothing for them. The tree-side collision scan is restricted to visible-owned items only: as written it scans `_tree_item_rows.values()` [CODE: `library_table.py:587-593`], so two detached rows sharing a key would keep their song colliding and delete the song's visible rows too. The visible-side scan (from the new visible set) is unchanged. Recommendation: keep the fallback; the collision rules otherwise do not change. One follow-on is viable and worth recording: on a non-load refresh the bound row dicts are the same objects (`set_rows` is the only replacement, `merge_scores` works in place), so matching by `id(row)` within a colliding song is exact, with no guessing — only a load, which brings fresh dicts, needs the block re-insert. Whether it is worth building depends on how many songs collide in the owner's library, which nobody has measured, so the driver should print the count of colliding songs and rows (one line) and settle Q8 on data.

## 4. Recommended Design in Detail

**4.1 The new state.** One set, `_tree_item_detached`, holding the item ids the table owns but is not showing. It lives beside `_tree_item_rows` (all owned items), `_tree_item_order` (visible keys in tree order), and `_tree_item_display` (saved display tuple per item, visible or detached — a detached item's tuple stays saved, so a reattach that finds the row changed can still update it in place). The state is initialized with the other maps in `__init__` [CODE: `library_table.py:182-188`]. The empty-tree check in `refresh_table` [CODE: `library_table.py:531`, `if not self._tree_item_rows`] keeps its meaning: nothing owned at all means a full insert. A table that owns only detached items is not empty — it has something to reattach — and the diff path handles it. (The check is an ownership-empty test, not a "tree empty" test; its comment and tests should say so.) The implementation states and holds these invariants: `set(_tree_item_rows) == set(_tree_item_display)` for all owned items; `_tree_item_detached` is a subset of `_tree_item_rows`; the visible owned items are `set(_tree_item_rows) - _tree_item_detached`; `_tree_item_order` holds exactly the keys of the visible owned items, in `get_children("")` order; `set(tree.get_children("")) == set(_tree_item_rows) - _tree_item_detached`; every iid in `tree.selection()` is visible and owned; `SelectedRowTint.items == set(tree.selection())`, and detached items do not retain `SELECTED_ROW_TAG`; any focused iid used to open a row is visible and owned; and a generation's completion signal describes completion of its diff walk, not "all owned rows are children."

**4.2 The delete arm becomes detach-or-delete — and the rest of `_apply_diff` must split visible-owned from detached-owned.** In `_apply_diff`, where the code today deletes every item whose key is not in the new visible set [CODE: `library_table.py:594-600`], it first decides the library key set (D2): when `changed_keys is None` — what a load passes — it builds the set from `self._filter.library_rows()`; otherwise every leaving item is detached and no set is built. Then, per item: if the song collides → delete as today (D8); else if the key is not in the new visible set → detach if the key is in the library, delete if it is not. Detach means `tree.detach(item)`, remove the key from `_tree_item_order`, add the item to `_tree_item_detached`, and keep its row and display tuple. True deletion drops the iid from all maps, the detached subset, and the selection/tint tracking. The key-set build is O(N) pure Python over 42,375 rows, tens of milliseconds (35 ms cold / 29 ms warm on Muse's run; 62 ms on Claude's), which is why it is gated on loads rather than paid on every sort click; the `refresh_table` docstring should say a set means "membership unchanged". The detach-or-delete change alone is not enough: the rest of `_apply_diff` treats every survivor of the delete loop as visible, and a detached survivor breaks it in three places. First, the tree-side collision scan iterates `_tree_item_rows.values()` [CODE: `library_table.py:587-593`] — it must scan visible-owned items only (D8), or two hidden rows sharing a key keep their song colliding and delete the song's visible rows. Second, the selection sync loop iterates all of `_tree_item_rows` and calls `selection_add` for keys in `selected_keys` [CODE: `library_table.py:615-623`] — it must iterate visible-owned items only, and never `selection_add` a detached iid (D4). (The current callers happen not to trigger this — every visibility-changing refresh uses `preserve_selection=False` — but the loop as written would do it, so the restriction is an invariant, not a caller accident.) Third, and most seriously, the update loop does `row = new_by_key[key]` for every item left in `_tree_item_rows` [CODE: `library_table.py:639-648`, the lookup at `:641`] — `new_by_key` holds only the new visible rows, so a detached item's key raises `KeyError` on the first filter application under this design. The update loop must iterate visible-owned items only; a detached item keeps its saved display tuple and its old row binding until it is reattached, when it is rebound to the current row object and its tuple is recomputed (§4.3). The order list is rebuilt in one pass from the survivors [CODE: `library_table.py:601-612`] — Proposal 0022 replaced the per-item remove the first draft described — and under detach that rebuild must filter on visible-survivor keys, not all survivor keys: a detached item stays in `_tree_item_rows`, so its key would otherwise remain in the visible-only order list. The rebuild's existing comment (a narrow that drops 31,591 rows spends 10 s on `list.remove` alone) is the reason the rebuild exists; the detach change keeps the one-pass shape and narrows its key set. Two sets pin the trigger's terms (Claude's finding 3). Owned keys are the keys of every item in `_tree_item_rows`, detached or visible; attached keys are the keys of the visible owned items. Then `inserts` are the visible keys not owned; `reattaches` are the visible keys in the detached subset; `displaced` counts attached survivors out of place against their order in the target — the current code's pairwise comparison against the full target order must be narrowed to attached survivors, or an interleaved widen would inflate it with every position the reattached rows shift. With those definitions `displaced` is 0 on every pure widen under an unchanged sort, which is why the `reattaches` term is load-bearing (D5).

**4.3 The batch walk gains a reattach arm — a distinct branch, checked before the move branch, that is self-contained per item on a large restore.** In `_apply_diff_batch`, the position loop keeps its cases and gains a reattach branch checked before the move branch: when the key at a position is missing from the visible order and its item is in `_tree_item_detached`, the walk discards the item from the subset, rebinds it to the row at that position (`visible[index]` — a load replaces row dicts, so the detached binding is stale), and recomputes its display tuple — comparing it with the saved tuple and writing only if different, force-writing the tint and selection items exactly as the update loop does. An unconditional write would keep most of today's cost: a `tree.item` write costs about as much as an insert (25.2 µs against 24.9 µs per call on 40-column rows [RAN, Muse, Xvfb]), and Claude's arm table puts the arm as first worded at 3.77 s against 0.29 s for compare-then-write on 31,782 restored rows. The recompute itself must not be dropped: theme 3 changes hidden rows' values while a filter is on and the update loop never visits detached items, so reattach is where staleness is caught (see Q7). If the driver shows the 0.29 s matters, a follow-on is to mark a detached item dirty in the update loop when its key is in `changed_keys` (or `changed_keys is None`), so clean ones reattach by placement alone — not a requirement for this proposal. Then, for placement: on a large restore it moves the item to `"end"` (`tree.move(item, "", "end")`, O(1)), appends the key to `_tree_item_order`, and appends the item to `placed` in visible order — all in the same iteration — and the final `set_children` only orders [CODE: `library_table.py:774`]; on a small restore (total placements at or under `SET_CHILDREN_PLACEMENT_THRESHOLD`, 50) it calls `tree.move(item, "", index)` and inserts the key into `_tree_item_order` at the index. It must not be folded into the existing move branch: that branch reads the item's current position with `tree.index(item)` and pops it from `_tree_item_order` [CODE: `library_table.py:756-758`], but a detached item has no visible position — `index()` returns a misleading 0 — so the pop would remove the wrong key and corrupt the order list. `key_to_item` is built from all owned items [CODE: `library_table.py:649-652`], so a detached item's key is in it and the move branch would otherwise take it; the reattach branch must be checked first, keyed on subset membership. Each per-item transition (subset discard + rebind + tuple compare-and-write, plus the move-to-"end", the order append, and the placed append) completes synchronously within one iteration before the deadline check, so a mid-walk generation cancellation cannot leave an item attached while still marked detached, or detached while already in the visible order — and because the large arm moves the item and updates the order in the same iteration, the §4.1 invariant `set(tree.get_children("")) == set(_tree_item_rows) - _tree_item_detached` holds at every batch boundary, not only at the end of the walk. The first version of this section deferred the tree call to the final `set_children` and discarded the subset flag per item; a superseding refresh between batches then left items marked visible that were still detached, and the next refresh's move branch read the misleading `tree.index()` 0 and popped the wrong key (Claude's finding 2, Greptile's P1). The alternative the reviewers offered — keep the flags until `set_children` succeeds — also works, but the self-contained arm is taken: it is the simplest to reason about, it does not depend on the `set_children` reattach semantic, and it is the §6 fallback promoted to the primary design. The generation guard, the deadline, the rescheduling, the count label, and the tint reset at completion are all unchanged. Two details the large arm must hold. First, the placement trigger: `large_reorder` is `displaced + inserts > SET_CHILDREN_PLACEMENT_THRESHOLD` [CODE: `library_table.py:673-674`], and a pure reattach widen has `inserts = 0`, so the design adds a `reattaches` term — the visible rows whose key is owned-but-detached — and the trigger becomes `displaced + inserts + reattaches > SET_CHILDREN_PLACEMENT_THRESHOLD` (D5), with the three terms defined as in §4.2. Second, the `placed` invariant: the final `set_children` detaches every item not in the list, so `placed` must contain exactly one entry per visible row, in visible order; a reattach branch that forgets to append would silently detach a visible row. The walk already appends in every other branch (insert, move, already-there [CODE: `library_table.py:730`, `:754`, `:761`]), and the reattach branch appends in the large arm the same way. Reattached items join `placed` in visible order, and the final `set_children` is the sole order-setting call on the large arm: the per-item move-to-"end" only attaches, it never places (Grok's nit, reconciled with the self-contained arm). One verification, carried in §6, is now answered on Tk 8.6: Claude ran the probe under Xvfb and `set_children` reattaches a detached item included in the placed list, including shuffled; an attached item omitted from the list is detached, not destroyed; `move(detached, "", "end")` reattaches; `tree.item()` writes on a detached item persist; `index()` of a detached item is 0 and `exists()` is True. Windows Tk 9.0 is still open, and Claude's review on PR #282 carries a short script for it. The large arm no longer depends on that semantic — it moves each item to `"end"` first anyway — but the fake's model of it [CODE: `tests/test_library_table.py:189-196`] is now confirmed on Tk 8.6 rather than assumed.

**4.4 The load path needs no caller branch — but the driver reset must delete owned detached items too.** A load delivers a fresh rows list; the diff's membership check (D2) deletes the detached items whose songs are gone and reattaches the ones that are back, and the reattach rebinds them to the fresh row dicts (§4.3). The full-insert path (`_insert_batch`, taken when the table owns nothing [CODE: `library_table.py:789`]) is unchanged — a first load still streams in. The one place that needs a look is any code that deletes "everything" by enumerating `get_children()`: detached items are not children, so a `delete(*get_children())` would silently leave them behind. The load path in this design never does that (it goes through the diff, which knows the owned set) — but the timing driver has three such calls [CODE: `tools/time_table_refresh.py:66`, `:162`, `:232`]. The first, inside `reset_table_state` [CODE: `:58`], is the table reset the first draft asked for — it landed in PR #271 Revision 1 and clears the maps, the tint, and the focus together — but under detach its `delete(*get_children())` leaves detached items in the widget while the maps are cleared, orphaning them invisibly. The reset must also delete the owned detached items (enumerate `_tree_item_detached`, delete them, clear the set) or the table must expose a reset method the driver calls. The second, in the raw trial's disposable Treeview [CODE: `:162`], is fine as written: no `LibraryTable` bookkeeping exists there. The third, the "tree.delete of every item" timing in `main` [CODE: `:232`], runs on the production table and is followed by a reset that clears the maps, so the stale-map hazard is handled — but under detach the detached items would survive the delete and be orphaned the same way, so it goes through the same reset. The same widening applies to `tools/probe_changed_keys.py` (lines 258, 286, 353), which enumerates `table._tree_item_rows` — under D3 that set includes detached items, so its lookups must not assume every item is visible. The detach trial (D7) must not use raw deletes on the production table.

**4.5 What the user sees.** A filter toggle restores the table without the re-insert load time. Selection still clears on a filter change (the subscription calls `refresh_table()` with `preserve_selection=False`, unchanged — see Q6). Select-all still selects exactly what is shown, because `get_children()` returns the visible items only [CODE: `library_table.py:436`]. The count label shows "Loading…" while a large restore is still running (a reattach counts toward the progress flag, so the Revision 1 suppression shows it), then settles on the final count as today. Focus follows the same rule: detaching the focused row relocates focus (to an attached selected or neighbor row, or clears it), and Enter on a hidden row cannot open it because `_invoke_open_row` is gated on visibility (D4).

## 5. What Does Not Change

- The snapshot format, the manifest format, and the delivery contract: the pool of rows the loader delivers is unchanged, and the filter still decides which rows pass.
- The diff's key rules and the collision fallback (proposal 0019, plus Revision 1's carry-the-exact-item policy): colliding songs are still deleted and re-inserted as a block, and the Revision 1 policy still carries the exact item when it survives — for non-colliding rows — meaning the item id survives the toggle; the selection does not (see D4). What changes is the tree-side collision scan, which becomes visible-only (D8): a hidden collision must not destroy visible rows. Detach adds a third fate for a non-colliding row that leaves the visible set.
- The theme 3 seams: the Previous/Next display-order accessor (#263) does not exist on main yet, so this is a forward constraint — the accessor will read the visible order list, which stays visible-only, and the list meets it as long as it mirrors the tree at every step, which the self-contained large arm keeps true; multi-select exploration reads the tree's selection, which stays visible-only. The course builder reads `selected_rows()` and `library_rows()` through the filter, both unchanged in meaning. The existing Enter-to-open path is gated on visibility (D4) — the song page itself needs no change, since it receives the row the table's focus-open callback supplies.
- Issue #273 is closed (2026-11-24, fixed in PR #271 Revision 1): the tint tracker's stale-tag bug is settled, and this design must not repeat its race — the detach step syncs the tracker explicitly (D4) rather than relying on the queued select event.
- Ground-clearing for later themes: theme 2's Pack.ini read is a post-scan step over the loader's walk, untouched; theme 5's library writing writes cache files, and the pool of owned items only reads them — a writer invalidates the manifest by P1's rules, which this proposal does not weaken; the read-only cache-cleanup candidate's walk and per-file records are the ones the table already uses, not ones this replaces. The detached subset forecloses nothing theme 3 or theme 6 needs: selection and the visible order stay visible-only (see Q7), and detach takes no "detached tuples never go stale" shortcut — reattach re-derives and compares the tuple, because theme 3's profile switch, favorites, and machine-score columns change hidden rows' values through `changed_keys` events the update loop never delivers to detached items.

## 6. Test Plan (for the implementation PR)

- **FakeTreeview gains detach/reattach.** The headless fake in `tests/test_library_table.py` [CODE: `:141`] must model `detach` (removes the item from the children list, keeps values/tags, keeps the item addressable by id) and reattach-by-move, plus `exists`/`index` behavior for detached items as the probe establishes it (§7) — and `focus()` must stop returning `""` unconditionally [CODE: `:229`] so the focus test can run headless. It already models `set_children` [CODE: `:189-196`], including the detach semantics of an omitted item. Without the detach model, the new tests cannot run headless — and the fake's detach model is itself a claim the real-Treeview probe must verify. Its `index()` must return 0 for a detached item, or the fake will not catch the wrong pop in the cancellation test below.
- **Real-Treeview probe: `set_children` reattaches a detached item.** [RAN, Claude, Tk 8.6 under Xvfb]: confirmed — a detached item included in a `set_children` placed list comes back as a child in that position, including shuffled; an attached item omitted from the list is detached, not destroyed; `move(detached, "", "end")` reattaches; `tree.item()` writes on a detached item persist; `index()` of a detached item is 0 and `exists()` is True. Windows Tk 9.0 is still open; Claude's review on PR #282 carries a short script for it. The probe asserts final child membership and order, not just that the call does not raise. The large arm no longer depends on this semantic, since it moves each item to `"end"` first.
- **Differential tests** (loader-style, on fixture folders, through the real `refresh_table`): apply a filter and remove it; assert the tree ends with the same item ids, the same order, and the same values/tags as before the toggle — not merely the same rows. A second case with a changed filter value in between (narrow, then narrow differently, then clear) pins that reattaches track the current visible set, not the first one.
- **Delete-vs-detach test:** a load whose rows list drops a song asserts the song's items are really deleted (no longer owned, no longer reattachable), while a filter that hides the same song asserts its items are detached (still owned, reattachable).
- **Selection/tint tests:** detach a selected row and assert it leaves `tree.selection()` and the tint tracker's set, with no white tag left on it when it is reattached unselected; reattach a non-colliding row that was selected before the toggle and assert the same item returns unselected — `refresh_table` builds `selected_keys` from `tree.selection()` when each refresh starts, and a detached row is not selected at the widen, so nothing remembers it; and assert a row that stays visible keeps its selection across a `preserve_selection=True` refresh (the Revision 1 policy); and assert a colliding song's rows are deleted and re-inserted fresh across the same round trip.
- **Focus test:** detach the focused row and assert Enter does not open it (focus relocated or the open path gated); the row is still openable once reattached.
- **Only-detached test:** a filter that hides every row asserts the table takes the diff path (not `_insert_batch`) and the detached set holds all owned items.
- **Sync-while-detached and load-while-detached tests:** sync with rows detached, then clear the filter — the reattached rows show the new scores; load with rows detached — surviving songs reattach with fresh row bindings, gone songs are deleted.
- **Generation-cancellation test:** a second refresh arriving mid-reattach — cancelled during a large restore — leaves no item attached-while-detached or detached-while-in-visible-order, and the §4.1 invariants hold at every batch boundary: no item marked visible while still detached.
- **Trigger test:** a widen that restores more than `SET_CHILDREN_PLACEMENT_THRESHOLD` rows with zero new inserts asserts the walk took the `set_children` path (one `set_children` call, no per-item moves) — the case D5's `reattaches` term exists for. Use an ordinary interleaved widen as well as the tail case, so the pinned definitions in §4.2 are exercised both ways.
- **Driver test:** the timing driver's reset no longer leaves detached items behind; assert the owned maps and the detached set are empty after a reset.
- **Static acceptance checklist:** no loop over `_tree_item_rows` assumes all entries have keys in the visible lookup; no selection restoration or `tree.index()` call can target a detached iid; detach clears the selection tint synchronously and handles focus; reattach updates the iid's row binding and recomputes its display tuple from current data, writing only on a difference; true deletion removes the iid from every owned/detached/display/order/tint structure; duplicate-key behavior is explicitly preserved (D8); `get_children()` is used only for visible children, never as an ownership inventory; tools do not mutate the widget behind `LibraryTable`'s bookkeeping.
- **Load-after-detach test:** detach a set of rows, then load a fresh library; assert the detached items for surviving songs reattach and the ones for gone songs are deleted.
- **Count-label test:** an unchanged refresh shows no "Loading…" text (Revision 1's suppression); a large restore shows it while the walk is still running and settles on the final count.
- **Timing:** the §6 driver's detach trial (D7) re-runs on the owner's machine — the filter-toggle round trip through the production table is the deciding number, and the raw trial gains a raw variant (detach-all, then move-to-"end" per item plus one `set_children` restore) to time the arm this design actually uses. The sandbox cannot show the win (1.5 shared CPUs, 6 fixture files); the implementation PR's numbers come from the owner's machine. ## 7. Open Questions for Reviewers

- **Q1. Tk semantics — ANSWERED by three independent sources:** Codex's probe (Windows, Tk 9.0), Muse's Xvfb re-run (Tk 8.6), and Grok's docs/source check (man page + ttkTreeview.c + treeview.test, landed 2026-11-23). They agree on every behavior that matters for the design; the two divergences (focus cleared vs. retained, `delete()` no-args invalid vs. no-op) are noted in §2, the executed probe wins on both, and neither changes the design. One semantic sub-question is now answered on Tk 8.6: Claude ran the probe under Xvfb and `set_children` reattaches a detached item included in the placed list, including shuffled — see §6. Windows Tk 9.0 is still open; Claude's review on PR #282 carries a short script for it.
- **Q2. Is the reattach actually cheaper? — ANSWERED for the raw ops; the end-to-end part still needs the driver re-run on the implementation branch.** The per-item move-to-index reattach the first draft proposed is refuted: raw detach-plus-reattach 4.25 s against delete-plus-insert 0.11 s at 42,375 rows on the owner's machine (2026-11-23), and 114.8 µs/row at 20,000 rows against 4.6 µs/row for insert-at-"end" under Xvfb. The design in §4.3 rests instead on compare-then-write plus a move to `"end"` per item plus one `set_children`: Claude's arm table (Xvfb Tk 8.6, 31,782 restored rows) puts compare-then-write at 0.29 s, move-to-"end" plus `set_children` at 0.19 s, and placement-only at 0.05 s, against 4.90 s for the widen today and 3.77 s for the arm as first worded; the bare-Tk detach plus one `set_children` is 0.026 s against delete-plus-insert 0.104 s at 20,000 rows (4x). The end-to-end restore is expected to take a few tenths of a second at the owner's scale; the toggle win after implementation is for the §6 driver re-run to measure.
- **Q3. D7 — should the driver trial ride in PR #271's Revision 1? — ANSWERED: yes (Ian, 2026-11-23 09:36), and it ran.** The trial has two parts, both in `tools/time_table_refresh.py`: the filter-toggle round trip through the production table (`time_filter_toggle`), and the raw detach/reattach vs. delete/insert comparison in a disposable Treeview (`time_raw_detach_reattach`). It produced the D5 verdict and the §6 numbers. The remaining trial work is the re-run on the implementation branch, plus a raw variant (detach-all, then move-to-"end" per item plus one `set_children` restore), since the existing raw trial measures the refuted per-item move.
- **Q4. The library key set: build per refresh, or cache it? — ANSWERED: build it only when `changed_keys is None`.** Neither the per-refresh build nor an identity cache: the build is O(N) pure Python over 42,375 rows, tens of milliseconds (35 ms cold / 29 ms warm on Muse's run; 62 ms on Claude's), and it would run on every sort click for nothing. Gate it on the signal that already exists: `changed_keys is None` ("unknown") is what a load passes, and a sort, a sync, and a filter edit all pass a set, none of which can change membership (`library_filter.py:98` is the only assignment of `_rows`; a sync re-scores in place). When `changed_keys is None`, build the key set and decide detach-or-delete per item; otherwise every leaving item is detached. The `refresh_table` docstring should say a set means "membership unchanged".
- **Q5. The reattach budget: share the 12 ms walk, or its own? — ANSWERED: share it.** Keep the shared 12 ms walk and add no constant. The stated premise was wrong, though: "the wall time is the `set_children` cost" is false for the arm as first worded (101 batches, 3.77 s) and true only after the compare-then-write fix (1–19 batches); `set_children` itself is 13 ms in Claude's run, and the code comment at `library_table.py:47` records 28.7 ms at 42,375 rows, kept here as the expected one-call pause. The driver already times 12/50/200 ms budgets; let that data decide on the owner's machine, and if a 19-batch restore still shows batch overhead there, a larger budget for a reattach-only walk is a one-line follow-up.
- **Q6. Should a filter change carry the selection? — ANSWERED: leave it out.** Today the subscription calls `refresh_table()` with `preserve_selection=False`, so a filter change clears the selection. The draft's reason was incomplete: detach does not make carrying a selection possible, because a hidden row cannot be selected — carrying it would need the table to remember the keys of rows selected-then-hidden, which is new state and a UX call for Ian (does filtering away and back bring the selection back?). Changing it is a behavior change outside this proposal's scope; a follow-on can take it, with its own decision and tests.
- **Q7. Ground-clearing: does the detached subset foreclose anything theme 3 or theme 6 needs? — ANSWERED: no, with one condition.** Selection and the visible order stay visible-only, and theme 6's recommendations read rows through the filter, so neither is foreclosed — but only if reattach keeps re-deriving (comparing) the tuple: theme 3's profile switch, favorites, and machine-score columns change hidden rows' values through `changed_keys` events the update loop never delivers to detached items, so a "detached tuples never go stale" shortcut would break theme 3. The Previous/Next accessor (#263) does not exist on main yet, so §5's sentence about it is a forward constraint.
- **Q8. Collisions: keep the delete-and-reinsert fallback (D8), or extend detach to colliding songs? — ANSWERED: keep the fallback, with a follow-on recorded.** A key-to-list reattach lookup cannot match two detached items sharing a key to two visible rows sharing it without guessing, and guessing wrong swaps their display tuples. The cost is that colliding songs pay a full re-insert on a filter round trip, as they do on every refresh today. One follow-on is viable: on a non-load refresh the bound row dicts are the same objects, so matching by `id(row)` within a colliding song is exact, with no guessing — only a load needs the block re-insert. Whether it is worth building depends on how many songs collide in the owner's library, which nobody has measured; the driver should print the count of colliding songs and rows so the question is settled on data.
