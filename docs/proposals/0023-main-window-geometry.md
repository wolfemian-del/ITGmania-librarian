---

In plain language: the library window itself is the one window the app never places. It opens at whatever size the theme sets and wherever Windows puts it, and on the owner's machine Windows puts it low enough that its bottom sits under the taskbar. It also forgets everything when it closes: move it, resize it, maximize it, and the next launch opens it at the default size in the window manager's place again. This proposal makes the library window remember where it was and whether it was maximized, the way the dialogs already remember their places, and makes its first open land centered in the screen's usable area instead of wherever Windows drops it. The owner will notice the window opens where he left it, maximized if he left it maximized, and never under the taskbar. The two real decisions are what is remembered (D1) and how the app knows the normal size behind a maximized window (D4).

## 1. Background and Goal

The faster-refresh suite is complete (P1, P5, P2, Proposal 0022, Proposal 0021 — the last merged as PR #283 on 2026-11-27), and the owner staged this as the next scoped step: a 0016 follow-on, after the faster-refresh suite and before theme 2 (the pack and series view), decided 2026-11-24. The problem is the owner's own smoke finding: the main window opens below the taskbar so its bottom is cut off, and the cause is the window manager's default placement, not the size. His calls are already taken: the fix must be general — any Windows user, not a kludge to his machine — and the window should remember its place across restarts, especially maximized.

This change creates no new component boundary and moves none: the opening decision is the pure `opening_geometry` Proposal 0016 already built, the work-area lookup is the `work_area_of` it already measured, and the save follows the dialogs' close-time pattern. It persists two new settings keys, which is a proposal trigger under AGENTS.md, and it amends Proposal 0016 §1 (see §5). Done means: the window opens with its whole frame inside the work area on every launch; a move, resize, or maximize is remembered across restarts; un-maximizing returns to the size and place the window had before it was maximized; and a saved place that is no longer on any monitor falls back to a centered open instead of opening off screen.

## 2. Current State (measured on main `e9526fd`)

**The main window sets its size and leaves its position to Windows.** [CODE] `LibraryApp._init_window` (`itgmania_library/library_librarian.py:103–114`) sets the title, the DPI scale, then `self.root.geometry(scale_geometry(theme.WINDOW_DEFAULT_GEOMETRY, self._dpi_scale))` and the minimum size. `theme.WINDOW_DEFAULT_GEOMETRY` is `"1500x850"` and `theme.WINDOW_MIN_SIZE` is `(900, 550)` (`itgmania_library/theme.py:120–121`). The geometry string carries a size only, so the window manager chooses the position. [TESTED] On the owner's machine (Windows 11, 1920×1080 at 100% scaling, Python 3.14.7, Tk 9.0) that placement puts the bottom under the taskbar. The window is never repositioned after that, and nothing about its place is ever written down: there is no `main_window_geometry` key, and no code reads the root's geometry at exit.

**The dialogs already remember their places, and the pattern is fixed.** [CODE] Three keys — `course_geometry`, `advanced_search_geometry`, `song_page_geometry` — are read through `_valid_*_geometry` wrappers (`library_librarian.py:574–595`) over `_valid_window_geometry(value, min_size)` (`itgmania_library/library_stores.py:363`), which accepts only a full `WxH+X+Y` at or above the window's minimum size (the song page also accepts a position-only `+X+Y`). `_save_settings` (`library_librarian.py:613`) writes a fixed set of keys, and each geometry key joins the file only once the owner has actually placed that window. `_close_app` (`library_librarian.py:460`), the app's single exit path, captures each open dialog's geometry before the root is destroyed (lines 472–476). A boolean setting already exists in the same file — `show_distribution`, read as `bool(self.saved_settings.get("show_distribution", False))` (line 181) — so a boolean key needs no new machinery.

**The placement rule already exists and is measured.** [CODE] `opening_geometry(saved, size, desktop, scale, *, anchor=None, work=None, frame=WINDOW_FRAME, min_size=(1, 1))` (`itgmania_library/library_geometry.py:164`) decides an opening geometry from a saved value, a default size, the virtual desktop, and the work area: a saved full-form box that passes the visibility test is restored as it is (rule 2); otherwise the window is centered and clamped so its whole outer box, frame included, lies inside the work area (rule 4). `work_area_of(hwnd=None)` (line 246) returns the primary monitor's work area, or None off Windows and on any failure, in which case the caller falls back to the virtual desktop. [RAN] (Codex, Proposal 0016, Windows 11, Python 3.14.7, 100%, one 1920×1080 monitor) the work area is 1920×1032 under a 48 px taskbar, and the same lookup works for a normal, maximized, and minimized root. The two-monitor work area is still unmeasured.

**The maximized case is the one the existing helper refuses.** [CODE] `WindowPlacement.save` (`itgmania_library/window_placement.py`) returns without saving when the window's state is not `"normal"`, because a maximized window "reports a parked or full-screen geometry the owner did not choose". So the dialogs never record a maximized state, and the main window cannot reuse that save as it stands. [RAN] (Codex, Proposal 0016) For a maximized window the `winfo_x/y/width/height` readings are the maximized box — correct for centering dialogs over it — while `geometry()` is stale: it still reports the pre-maximize `+150+100` against a client area at (0, 23). That stale value happens to be the normal geometry, but it is Tk's bookkeeping, not a contract (D4).

**The dialogs' anchor is unaffected.** [CODE] `WindowPlacement._surroundings` reads the main window's box through `winfo_*` whether it is normal or maximized, so a main window that restores maximized still anchors the dialogs exactly as a maximized window does today. Nothing in this proposal touches the dialogs' opening or save paths.

**Tests.** [RAN] The full suite at the base is 1116 tests OK, 74 skipped (the live-window tests, which need Tkinter), run as `python -m unittest discover -s tests` under Python 3.12.3. The geometry rule is pinned by `tests/test_library_geometry.py` and the helper by `tests/test_window_placement.py`; no test covers the main window's own geometry.

## 3. The Decisions

**D1. What is remembered: the normal geometry and the maximized flag, as two keys. Recommended.** `main_window_geometry` holds the full `WxH+X+Y` of the window in its normal state, validated by `_valid_window_geometry` against `theme.WINDOW_MIN_SIZE` (900×550), exactly as the dialog keys are. `main_window_maximized` is a boolean, read as `bool(saved_settings.get("main_window_maximized", False))`, the `show_distribution` pattern. Both join `settings.json` only once the owner has placed the window (moved, resized, or maximized it), on the same terms as the dialog keys. A maximized window's normal geometry is the size and place it returns to when un-maximized, so the two values are recorded together: maximizing and closing records the flag with the normal geometry behind it, and un-maximizing and closing records the flag as false with the geometry the window now has.

The rejected alternative is one key with the state encoded in it, for example `WxH+X+Y` plus a suffix, or a dict value. It would need a new validator and a new format for one window, while the two-key shape reuses the geometry validator and the boolean pattern unchanged. A second rejected shape is a position-only form for the main window (D4 B of Proposal 0016): the main window has no content sizing to preserve, so a move always stores the full geometry, and there is nothing a position-only form would save.

**D2. The first open: center the default size in the primary monitor's work area. Recommended.** When nothing usable is saved, `_init_window` calls `opening_geometry` with no saved value, the default size, the virtual desktop, and `work_area_of(None)` — the primary monitor's work area — and no anchor. Rule 4 then centers the 1500×850 window in the work area and clamps it there, so its whole frame is inside the usable area on any screen, including one smaller than the default size (the cap floors at the 900×550 minimum). This is the same rule the dialogs already open by, applied to the window that anchors them.

The rejected alternative is to let the window manager place the window and then clamp it into the work area afterward. It would preserve the window manager's placement when that placement is good, but it is non-deterministic — the app would have to map the window, read where Windows put it, and then move it — and harder to test than a geometry computed before the window is shown. Centering is deterministic, testable headless through `opening_geometry`, and it fixes the reported bug by construction rather than by repair.

**D3. A saved geometry: restore it through the existing rule, unchanged. Recommended.** The saved value goes through the same `opening_geometry` call as the first open: if the saved box passes the visibility test against the virtual desktop it is restored as it is (rule 2), so a place on a second monitor comes back on that monitor; if it is no longer visible — a monitor unplugged, a smaller resolution — the window opens centered in the primary work area at the saved size, capped (rule 4). No new geometry logic is introduced, and the multi-monitor fallback is the primary monitor because the fallback only fires when the saved monitor is gone. Q2 asks whether the cap should instead use the monitor holding the saved position.

**D4. How the normal geometry behind a maximized window is known: track the last normal geometry on every move and resize. Recommended.** The shell keeps one attribute, the last geometry the root had while its state was `"normal"`, updated by a `<Configure>` binding on the root. No `<Configure>` binding on the root exists today, so there is nothing to compose with. When the window is maximized, `<Configure>` still fires but the state is `"zoomed"`, so the attribute keeps the pre-maximize geometry; when it is restored, the next `<Configure>` records the geometry it comes back to. At exit the save reads that attribute, not the window's live geometry, so it never has to ask what a maximized window's "geometry" means.

The rejected alternative is to read `root.geometry()` at exit and rely on its stale pre-maximize value, which Codex measured on Tk 8.6 and 9.0. It would need no binding and no attribute, but it builds a persisted setting on Tk's internal bookkeeping: if a Tk version ever updated the stored geometry when maximizing, the app would save the maximized box as the normal geometry and later restore a normal window at full-screen size. The tracked value does not depend on that behavior, and the cost is one binding and one attribute. The saved maximized flag comes from `root.state() == "zoomed"` at exit, read the same way the dialogs' anchor already reads state.

**D5. When it is saved: at exit only, and only on a deliberate change. Recommended.** The save runs in `_close_app`, before the root is destroyed, alongside the three dialog saves that already live there. It compares the last normal geometry against the opening baseline — the geometry the window actually opened with, captured by an `after_idle` callback after `_init_window` sets it, the same pattern as `WindowPlacement.record_opening` — and records nothing when they are equal, so a session in which the owner never moved the window writes no new geometry. The maximized flag is recorded when it differs from the saved one, so opening normal and closing maximized records the change even though the normal geometry did not move. A crash or a killed process loses the latest move, the same as the dialogs lose an un-closed dialog's move today; that is accepted, and it is the same trade the close-time save already makes.

## 4. Recommended Design in Detail

This change does not touch a component boundary or a constructor contract: the shell owns the main window's place, as it owns the dialogs' wiring, and the geometry decision stays in the pure `opening_geometry`. The legibility test, applied to what changes: the main window opens where it was left, or centered in the usable screen if it was never placed, and remembers whether it was maximized. That sentence is the whole design.

- **Settings keys.** `main_window_geometry`: a full `WxH+X+Y` string in canonical 100% units, read through a new `_valid_main_window_geometry` wrapper over `_valid_window_geometry(value, theme.WINDOW_MIN_SIZE)`; anything else is dropped at startup, as an invalid value is for the other keys. `main_window_maximized`: a boolean, default false. Both join `settings.json` on the same terms as the dialog geometries — only once the owner has placed the window — so a settings file from an earlier version simply has neither key, and a file written by this version and read by an earlier one loses both keys on that earlier version's next save, the same accepted cost as `song_page_geometry` in Proposal 0016 D5.
- **Opening (`_init_window`).** After the DPI scale is known, the shell reads the saved geometry and flag, builds the desktop box from the root's `winfo_vroot*` readings, and calls `opening_geometry(saved, scaled_default_size, desktop, scale, anchor=None, work=work_area_of(None) or desktop, min_size=theme.WINDOW_MIN_SIZE)`. It sets the returned geometry on the root, then applies the maximized state: if the saved flag is true, `root.state("zoomed")` after the geometry is set, so the restored normal geometry is the one behind the maximized window. The opening baseline is captured by an `after_idle` callback once the window has been placed, the `WindowPlacement.record_opening` pattern, so the exit comparison is against what the window actually opened at rather than what was requested.
- **Tracking (the shell, one attribute and one binding).** A `<Configure>` binding on the root updates the last-normal-geometry attribute whenever `root.state() == "normal"`, storing the canonical form of `root.geometry()` (the dialogs' `_canonical` conversion, scaled to 100% units). It records nothing while maximized or minimized, and it writes no settings — it only keeps the attribute current, so a resize drag costs one assignment per event and no I/O.
- **Saving (`_close_app`).** Before the root is destroyed, after the three dialog saves, the shell compares the last normal geometry with the opening baseline and the current maximized flag with the saved one. If neither changed, it writes nothing. Otherwise it stores the last normal geometry (when it changed) and the flag, and calls `_save_settings`, which gains the two keys on the same conditional terms as the dialog geometries. The save runs only on the normal exit path; there is no save on minimize, and no save while the window is open.
- **What the dialogs see.** Nothing changes: the main window remains their anchor, read through `winfo_*` in both states, and a restored maximized window anchors them exactly as a maximized window does today.

## 5. What Does Not Change, and What Does on Purpose

Does not change:

- The dialogs' opening and save paths, their keys, their validators, and the `opening_geometry` rule itself — this proposal is a new caller of that rule, not a change to it.
- The theme defaults: `WINDOW_DEFAULT_GEOMETRY` stays `"1500x850"` and `WINDOW_MIN_SIZE` stays `(900, 550)`. A first open is the same size, in a chosen place rather than the window manager's.
- The song page, the course builder, Advanced Search, the data paths dialog, and About — their geometry behavior is exactly as Proposal 0016 left it.
- Settings files written by earlier versions: both new keys are absent, which reads as the default size centered in the work area, not maximized.
- The minimum-size validation and the 100%-unit storage shared by every geometry key.

Deliberately changed, and the earlier text each supersedes:

- Proposal 0016 §1: "The main window's own opening position stays under the window manager; only its size is set (`LibraryApp._init_window`)". The position is now chosen by the app through `opening_geometry`, and remembered. This is the follow-on Proposal 0016's staging left open, not a reversal of its rule — the rule itself is reused unchanged.
- Proposal 0003 §4's session-only geometry, as Proposal 0016 already amended it for the dialogs: the amendment now extends to the main window, which is the last window whose place was session-only by omission rather than by decision.
- The main window's first-open position: centered in the primary work area instead of the window manager's choice (D2).
- The roadmap: no departure. The roadmap's order is unchanged — this is the scoped 0016 follow-on the owner staged between the faster-refresh suite and theme 2 on 2026-11-24, and it fills that slot. The roadmap file's "immediate steps" paragraph is stale (it still lists the font update and faster refresh as next); the implementation PR updates it to name this step as done in its turn, rather than this proposal carrying a roadmap edit.

## 6. Test Plan (for the implementation PR)

One implementation PR, naming this proposal and saying it does not depart from it. Full suite: `python -m unittest discover -s tests` must pass (1116 passed, 74 skipped at the base).

- **Unit tests, headless.** The validator: a full geometry at and above the 900×550 minimum is accepted, a smaller one is dropped, a position-only value and garbage are dropped. The save decision, driven through a Tk-free stand-in root (the `WindowPlacement` pattern — the shell's save takes the root, so a stand-in with `geometry()`, `state()`, and `winfo_exists()` drives it): an untouched window records nothing; a moved window records its new geometry; a maximized window records the flag with the pre-maximize geometry; a minimized window records nothing; a window dragged back to exactly its opening place records nothing. The opening call: with no saved value the computed geometry is centered in the given work area with its whole frame inside it, at the default size; with a saved value on a second monitor it is restored; with a saved value off every monitor it is centered on the primary.
- **Live tests under Xvfb** (the existing live suites' pattern): open the app with no saved geometry and assert the whole frame is inside the desktop; move the window, restart, assert it reopens at the moved place; maximize, restart, assert it reopens maximized; un-maximize, assert the size and place are the pre-maximize ones. Off Windows `work_area_of` returns None, so these assert against the virtual desktop, not a real taskbar.
- **A mutation check:** the `<Configure>` tracking not updating the attribute, and the exit save not comparing against the baseline, must each fail a test.
- **Docs:** README.md, `docs/ARCHITECTURE.md`, and CHANGELOG.md (Unreleased) updated for the remembered place and the centered first open; `docs/ROADMAP.md` updated for the staged slot.
- **Windows smoke (owner):** first launch opens centered, clear of the taskbar; move and restart restores the place; maximize and restart restores maximized; un-maximize returns to the saved size and place; and the two-monitor work area — whether a place on the second monitor restores there, and where the fallback centers when that monitor is gone.

## 7. Open Questions for Reviewers

- **Q1.** The first open centers the window in the primary monitor's work area. Should it instead keep the window manager's placement and only clamp it into the work area when it would run under the taskbar? The recommendation is centering (D2): it is deterministic and testable, and it fixes the reported bug by construction.
- **Q2.** When a saved place is gone, the fallback centers on the primary monitor, and the size cap reads the primary work area. Should the cap and the fallback instead use the work area of the monitor holding the saved position (via a `MonitorFromPoint` lookup)? The recommendation is the primary: the fallback only fires when the saved monitor is gone, and a saved place that is still visible is restored as it is.
- **Q3.** The maximized state is a separate boolean key. Should it instead be encoded in the geometry string? The recommendation is the separate key (D1): it reuses the geometry validator and the boolean pattern unchanged.
- **Q4.** The place is saved at exit only. Should it instead be written on every move and resize, so a crash keeps the latest place? The recommendation is exit only (D5): it matches the dialogs' close-time save, and the cost of a write per drag event is not worth the crash case.
