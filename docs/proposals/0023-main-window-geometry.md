---

In plain language: the library window itself is the one window the app never places. It opens at whatever size the theme sets and wherever Windows puts it, and on the owner's machine Windows puts it low enough that its bottom sits under the taskbar. It also forgets everything when it closes: move it, resize it, maximize it, and the next launch opens it at the default size in the window manager's place again. This proposal makes the library window remember where it was and whether it was maximized, the way the dialogs already remember their places, and makes its first open land centered in the screen's usable area instead of wherever Windows drops it. The owner will notice the window opens where he left it, maximized if he left it maximized, and never under the taskbar. The two real decisions are what is remembered (D1) and how the app knows the normal size behind a maximized window (D4).

## 1. Background and Goal

The faster-refresh suite is complete (P1, P5, P2, Proposal 0022, Proposal 0021 — the last merged as PR #283 on 2026-11-27), and the owner staged this as the next scoped step: a 0016 follow-on, after the faster-refresh suite and before theme 2 (the pack and series view), decided 2026-11-24. The problem is the owner's own smoke finding: the main window opens below the taskbar so its bottom is cut off, and the cause is the window manager's default placement, not the size. His calls are already taken: the fix must be general — any Windows user, not a kludge to his machine — and the window should remember its place across restarts, especially maximized.

This change creates no new component boundary and moves none: the opening decision is the pure `opening_geometry` Proposal 0016 already built, the work-area lookup is the `work_area_of` it already measured, and the save follows the dialogs' close-time pattern. It persists two new settings keys, which is a proposal trigger under AGENTS.md, and it amends Proposal 0016 §1 (see §5). Done means: a first open lands with its whole frame inside the work area; a move, resize, or maximize is remembered across restarts; un-maximizing returns to the size and place the window had before it was maximized; a place the owner chose is kept as chosen when it is still visible; and a saved place that is no longer on any monitor falls back to a centered open instead of opening off screen.

## 2. Current State (measured on main `e9526fd`)

**The main window sets its size and leaves its position to Windows.** [CODE] `LibraryApp._init_window` (`itgmania_library/library_librarian.py:103–117`) sets the title, the DPI scale, then `self.root.geometry(scale_geometry(theme.WINDOW_DEFAULT_GEOMETRY, self._dpi_scale))` and the minimum size. `theme.WINDOW_DEFAULT_GEOMETRY` is `"1500x850"` and `theme.WINDOW_MIN_SIZE` is `(900, 550)` (`itgmania_library/theme.py:120–121`). The geometry string carries a size only, so the window manager chooses the position. `__init__` calls `_init_window()` before `_init_stores()` (lines 94–95), so the window is set up before `saved_settings` exists — a placement step that needs the saved geometry cannot run in `_init_window` (D4). [TESTED] On the owner's machine (Windows 11, 1920×1080 at 100% scaling, Python 3.14.7, Tk 9.0) that placement puts the bottom under the taskbar. The window is never repositioned after that, and nothing about its place is ever written down: there is no `main_window_geometry` key, and no code reads the root's geometry at exit.

**The dialogs already remember their places, and the pattern is fixed.** [CODE] Three keys — `course_geometry`, `advanced_search_geometry`, `song_page_geometry` — are read through `_valid_*_geometry` wrappers (`library_librarian.py:574–592`) over `_valid_window_geometry(value, min_size)` (`itgmania_library/library_stores.py:363`), which accepts only a full `WxH+X+Y` at or above the window's minimum size (the song page also accepts a position-only `+X+Y`). `_save_settings` (`library_librarian.py:613`) writes a fixed set of keys, and each geometry key joins the file only once the owner has actually placed that window. `_close_app` (`library_librarian.py:460`), the app's single exit path, captures each open dialog's geometry before the root is destroyed (lines 472–476). A boolean setting already exists in the same file — `show_distribution`, read as `bool(self.saved_settings.get("show_distribution", False))` (line 181) — so a boolean key needs no new machinery.

**The placement rule already exists and is measured.** [CODE] `opening_geometry(saved, size, desktop, scale, *, anchor=None, work=None, frame=WINDOW_FRAME, min_size=(1, 1))` (`itgmania_library/library_geometry.py:164`) decides an opening geometry from a saved value, a default size, the virtual desktop, and the work area: a saved full-form box that passes the visibility test is restored as it is (rule 2); otherwise the window is centered and clamped so its whole outer box, frame included, lies inside the work area (rule 4). `work_area_of(hwnd=None)` (line 246) returns the primary monitor's work area, or None off Windows and on any failure, in which case the caller falls back to the virtual desktop. [RAN] (Codex, Proposal 0016, Windows 11, Python 3.14.7, 100%, one 1920×1080 monitor) the work area is 1920×1032 under a 48 px taskbar, and the same lookup works for a normal, maximized, and minimized root. The two-monitor work area is still unmeasured.

**The maximized case is the one the existing helper refuses.** [CODE] `WindowPlacement.save` (`itgmania_library/window_placement.py`) returns without saving when the window's state is not `"normal"`, because a maximized window "reports a parked or full-screen geometry the owner did not choose". So the dialogs never record a maximized state, and the main window cannot reuse that save as it stands. `WindowPlacement` cannot host the main window at all: its `save` refuses a non-normal state, and its anchor is the main window itself. [RAN] (Codex, Proposal 0016) For a maximized window the `winfo_x/y/width/height` readings are the maximized box — correct for centering dialogs over it — while `geometry()` is stale: it still reports the pre-maximize `+150+100` against a client area at (0, 23). That stale value happens to be the normal geometry, but it is Tk's bookkeeping, not a contract (D4).

**The dialogs' anchor is unaffected.** [CODE] `WindowPlacement._surroundings` reads the main window's box through `winfo_*` whether it is normal or maximized, so a main window that restores maximized still anchors the dialogs exactly as a maximized window does today. Nothing in this proposal touches the dialogs' opening or save paths.

**Tests.** [RAN] The full suite at the base is 1116 tests OK, 74 skipped (the live-window tests, which need Tkinter), run as `python -m unittest discover -s tests` under Python 3.12.3. The geometry rule is pinned by `tests/test_library_geometry.py` and the helper by `tests/test_window_placement.py`; no test covers the main window's own geometry.

## 3. The Decisions

**D1. What is remembered: the normal geometry and the maximized flag, as two keys. Recommended.** `main_window_geometry` holds the full `WxH+X+Y` of the window in its normal state, validated by `_valid_window_geometry` against `theme.WINDOW_MIN_SIZE` (900×550), exactly as the dialog keys are. `main_window_maximized` is a boolean, read as `bool(saved_settings.get("main_window_maximized", False))`, the `show_distribution` pattern. Both join `settings.json` only once the owner has placed the window (moved, resized, or maximized it), on the same terms as the dialog keys. A maximized window's normal geometry is the size and place it returns to when un-maximized. The two values are written together only when both changed: maximizing and closing records the flag, and the normal geometry behind it only if it moved from the opening baseline — with no move in between, the geometry equals the baseline, so only the flag is written and the saved geometry stays as it was. Un-maximizing and closing likewise records the flag as false, and the geometry only if the window was moved after un-maximizing.

The rejected alternative is one key with the state encoded in it, for example `WxH+X+Y` plus a suffix, or a dict value. It would need a new validator and a new format for one window, while the two-key shape reuses the geometry validator and the boolean pattern unchanged. A second rejected shape is a position-only form for the main window (D4 B of Proposal 0016): the main window has no content sizing to preserve, so a move always stores the full geometry, and there is nothing a position-only form would save. An older version reading a file written by this version loses both keys at its next save (§4).

**D2. The first open: center the default size in the primary monitor's work area. Recommended.** When nothing usable is saved, the placement step calls `opening_geometry` with no saved value, the default size, the virtual desktop, and `work_area_of(None)` — the primary monitor's work area — and no anchor. Rule 4 then centers the 1500×850 window in the work area and clamps it there, so its whole frame is inside the usable area on any screen that fits the minimum size (the cap floors at the 900×550 minimum; below roughly a 916×640 work area the floored minimum plus the frame no longer fits, so that screen is out of scope). This is the same rule the dialogs already open by, applied to the window that anchors them.

The rejected alternative is to let the window manager place the window and then clamp it into the work area afterward. It would preserve the window manager's placement when that placement is good, but moving a mapped window is visible — the app would have to map the window, read where Windows put it, and then move it, and the owner would see the jump — while a geometry computed before the window is shown is never seen moving. It is also harder to test than a geometry computed before the window is shown. Centering is deterministic, testable headless through `opening_geometry`, and it fixes the reported bug by construction rather than by repair.

**D3. A saved geometry: restore it through the existing rule, with the work area chosen by the saved position and the fallback on the primary. Recommended.** The saved value goes through the same `opening_geometry` call as the first open, with two small additions. First, the work area for the size cap is the monitor holding the saved top-left, not always the primary: `work_area_of` gains an optional point and returns the work area of the monitor nearest that point (`MonitorFromPoint` with `MONITOR_DEFAULTTONEAREST`), or the primary when no point is given. The saved point is stored in canonical 100% units while `MonitorFromPoint` takes physical pixels, so the point is scaled by the display scale first (`scale_pixels` on each coordinate, the same helpers the geometry scaling uses) — unscaled, at 150% a saved `+1500+100` would look up the wrong monitor. If the saved box passes the visibility test against the virtual desktop it is restored as it is (rule 2), so a place on a second monitor comes back on that monitor at its saved size — the cap reads that monitor's work area, not the primary's, which would have shrunk it. Second, the fallback centers on the primary, not on the monitor nearest the saved point: the shell decides visibility before choosing `work`, through a small Tk-free helper in `library_geometry`, `saved_geometry_visible(saved, desktop, scale, work)`, which returns whether a saved full-form geometry, capped to the given work area, is visible enough on the virtual desktop — the same parse, scale, cap, and `_visible_enough` the rule itself uses; a missing, position-only, or unparsable value is not visible. The shell asks it about the saved-point monitor's work area: visible, and that work area is passed to `opening_geometry`; not visible — a monitor unplugged, a smaller resolution — and the primary's work area is passed instead, so the window opens centered in the primary work area at the saved size, capped (rule 4). The pure rule is unchanged: the helper reuses the rule's own test, and `opening_geometry` still makes the opening decision; the only new geometry logic is the optional point on `work_area_of` and the visibility helper. `MonitorFromPoint` takes a `POINT` by value, so `argtypes` is set on the private `WinDLL` handle as the function already does for `MonitorFromWindow`. The rejected alternative is the nearest-monitor fallback, which the single-`work` call gives for free — when the saved monitor is gone but two others remain, the fallback would center on the nearest remaining monitor instead of the primary. It behaves acceptably, and is arguably the better default, but the owner chose the primary, so the shell decides visibility first.

**D4. How the normal geometry behind a maximized window is known: track the last normal geometry and the last shown state on every move and resize. Recommended.** The shell keeps two attributes: the last geometry the root had while its state was `"normal"`, and the last state the window was shown in — `"normal"` or `"zoomed"`, ignoring `"iconic"` — both updated by a `<Configure>` binding on the root. No `<Configure>` binding on the root exists today, so there is nothing to compose with. The handler ignores events from descendant widgets (`event.widget is self.root`): a binding on the root also receives the Configure events of every child, and without the guard the attributes would move on table and panel layout events. When the window is maximized, `<Configure>` still fires but the state is `"zoomed"`, so the geometry attribute keeps the pre-maximize geometry while the shown-state attribute records `"zoomed"`; when it is restored, the next `<Configure>` records the geometry it comes back to and the shown state returns to `"normal"`. A window minimized from maximized reports `"iconic"`, so the shown-state attribute keeps `"zoomed"` — minimizing does not clear a saved maximized flag. The last-normal-geometry attribute and the opening baseline are seeded at placement, from the canonical form of the `opening_geometry` string the placement step returns; the last-shown-state attribute is seeded from the saved flag (`"zoomed"` if the flag is true, else `"normal"`). The baseline is refined at first idle only if the state is `"normal"`, since the `geometry()` reading of a zoomed root is the stale bookkeeping this design refuses to trust. Seeding the state from the flag — not from the geometry string, which carries no state — also makes the result independent of whether the first `<Configure>` events after `state("zoomed")` on an unmapped root report `normal` or `zoomed`: a launch that restores maximized and is closed before any `<Configure>` reports `zoomed` still writes the flag as true. Closing untouched while maximized therefore writes nothing, and both saved keys are preserved. At exit the save reads those attributes, not the window's live geometry or `state()`, so it never has to ask what a maximized or minimized window's "geometry" means.

The rejected alternative is to read `root.geometry()` at exit and rely on its stale pre-maximize value, which Codex measured on Tk 8.6 and 9.0. It would need no binding and no attribute, but it builds a persisted setting on Tk's internal bookkeeping: if a Tk version ever updated the stored geometry when maximizing, the app would save the maximized box as the normal geometry and later restore a normal window at full-screen size. The tracked value does not depend on that behavior, and the cost is one binding and two attributes. A second rejected alternative is asking Windows for the normal rectangle (`GetWindowPlacement`, `rcNormalPosition`). It is authoritative, but it is Windows-only, needs ctypes, and reports workspace coordinates — offset by a taskbar at the top or left — so the tracked value, which is portable and already in the app's canonical units, is the better fit. The saved maximized flag comes from the tracked last shown state at exit, not from `root.state()`: a minimized window reports `"iconic"`, so reading the live state would clear a saved maximized flag.

**D5. When it is saved: at exit only, and only on a deliberate change. Recommended.** The save runs in `_close_app`, before the root is destroyed, alongside the three dialog saves that already live there. It compares the last normal geometry against the opening baseline — the geometry the window actually opened with, seeded from the placement geometry and refined at first idle only when the state is normal — and records nothing when they are equal, so a session in which the owner never moved the window writes no new geometry. The maximized flag is recorded when the last shown state differs from the saved one, so opening normal and closing maximized records the change even though the normal geometry did not move. The two keys live in attributes loaded at startup and are re-emitted by every later `_save_settings` — a filter change mid-session, for example — or the first settings write after launch would drop them. A crash or a killed process loses the latest move, the same as the dialogs lose an un-closed dialog's move today; that is accepted, and it is the same trade the close-time save already makes. A cancelled exit writes nothing: a declined discard prompt returns before any save.

## 4. Recommended Design in Detail

This change does not touch a component boundary or a constructor contract: the shell owns the main window's place, as it owns the dialogs' wiring, and the geometry decision stays in the pure `opening_geometry`. The legibility test, applied to what changes: the main window opens where it was left, or centered in the usable screen if it was never placed, and remembers whether it was maximized. That sentence is the whole design.

- **Settings keys.** `main_window_geometry`: a full `WxH+X+Y` string in canonical 100% units, read through a new `_valid_main_window_geometry` wrapper over `_valid_window_geometry(value, theme.WINDOW_MIN_SIZE)`; anything else is dropped at startup, as an invalid value is for the other keys. `main_window_maximized`: a boolean, default false. Both join `settings.json` on the same terms as the dialog geometries — only once the owner has placed the window — so a settings file from an earlier version simply has neither key, and a file written by this version and read by an earlier one loses both keys on that earlier version's next save, the same accepted cost as `song_page_geometry` in Proposal 0016 D5. The two keys live in attributes loaded at startup and are re-emitted by every later `_save_settings`, so a settings write mid-session (a filter change, for example) never drops them. The canonical conversion is a new public Tk-free `canonical_geometry(geometry, scale)` in `library_geometry.py`, which already holds `scale_geometry`; the dialogs' `_canonical` is a private method of `WindowPlacement` and cannot be called without one.
- **Opening (a placement step immediately after `_init_stores`).** `_init_window` keeps what it already provides — the title, the DPI scale, the minimum size and the background — and no longer sets the opening geometry itself. A placement step runs immediately after `_init_stores`, before `_init_variables`, once `saved_settings` exists: it cannot run in `_init_window`, because `__init__` calls `_init_window` before `_init_stores` and there is nothing to read yet, and it runs before any widget is built, so the geometry is set first. The placement step reads the saved geometry and flag, builds the desktop box from the root's `winfo_vroot*` readings, and chooses the work area: when a geometry is saved it asks `saved_geometry_visible` whether the saved place is visible when capped to the work area of the monitor holding the saved top-left — the point scaled from canonical 100% units to physical pixels first — and uses that monitor's work area when it is, the primary's when it is not; when nothing is saved the work area is the primary's. It then calls `opening_geometry(saved, scaled_default_size, desktop, scale, anchor=None, work=work_area or desktop, min_size=theme.WINDOW_MIN_SIZE)`. It sets the returned geometry on the root, then applies the maximized state: if the saved flag is true, `root.state("zoomed")` after the geometry is set, so the restored normal geometry is the one behind the maximized window. The root is not mapped until `mainloop`, so placing it here shows no flash. The opening baseline and the last-normal-geometry attribute are seeded from the canonical form of the returned geometry string; the last-shown-state attribute is seeded from the saved flag (`"zoomed"` if true, else `"normal"`); the baseline is refined by an `after_idle` callback once the window has been placed, the `WindowPlacement.record_opening` pattern, but only if the state is `"normal"` — for a window that opens maximized the seeded value stands.
- **Tracking (the shell, two attributes and one binding).** A `<Configure>` binding on the root updates the two tracked attributes: the last-normal-geometry attribute, whenever `root.state() == "normal"` and `event.widget is self.root`, storing the canonical form of `root.geometry()`; and the last-shown-state attribute, whenever the state is `"normal"` or `"zoomed"`, ignoring `"iconic"`. It records nothing while minimized, and it writes no settings — it only keeps the attributes current, so a resize drag costs one assignment per event and no I/O.
- **Saving (`_close_app`).** Before the root is destroyed, after the three dialog saves, the shell compares the last normal geometry with the opening baseline and the last shown maximized state with the saved flag. If neither changed, it writes nothing — so closing untouched while maximized writes nothing and both saved keys are preserved. Otherwise it stores the last normal geometry (when it changed) and the flag, and calls `_save_settings`, which gains the two keys on the same conditional terms as the dialog geometries and re-emits them on every later save. The save runs only on the normal exit path; a declined discard prompt returns before any save, so a cancelled exit writes nothing; there is no save on minimize, and no save while the window is open.
- **Save decision (truth table).** The save writes the geometry exactly when the last normal geometry differs from the opening baseline, and writes the flag exactly when the last shown maximized state differs from the saved flag. So: both unchanged → nothing; geometry changed, flag unchanged → geometry only; geometry unchanged, flag changed → flag only; both changed → geometry and flag. Minimizing alone changes neither input — the shown-state attribute keeps its last shown value — so a minimized window writes nothing on its own; closing untouched while maximized writes nothing and both saved keys are preserved.
- **What the dialogs see.** Nothing changes: the main window remains their anchor, read through `winfo_*` in both states, and a restored maximized window anchors them exactly as a maximized window does today.

## 5. What Does Not Change, and What Does on Purpose

Does not change:

- The dialogs' opening and save paths, their keys, their validators, and the `opening_geometry` rule itself — this proposal is a new caller of that rule, not a change to it.
- The theme defaults: `WINDOW_DEFAULT_GEOMETRY` stays `"1500x850"` and `WINDOW_MIN_SIZE` stays `(900, 550)`. A first open is the same size, in a chosen place rather than the window manager's.
- The song page, the course builder, Advanced Search, the data paths dialog, and About — their geometry behavior is exactly as Proposal 0016 left it.
- Settings files written by earlier versions: both new keys are absent, which reads as the default size centered in the work area, not maximized.
- The minimum-size validation and the 100%-unit storage shared by every geometry key.

Deliberately changed, and the earlier text each supersedes:

- Proposal 0016 §1: "The main window's own opening position stays under the window manager; only its size is set (`LibraryApp._init_window`)". The position is now chosen by the app through `opening_geometry`, and remembered. This is the follow-on Proposal 0016's staging left open, not a reversal of its rule — the rule itself is reused unchanged.
- Proposal 0003 §2 (lines 96–98): "The main window does **not** remember its own geometry; it opens at `theme.WINDOW_DEFAULT_GEOMETRY` every time. Remembering the *main* window's geometry is not part of issue #25 and is not proposed here." This proposal supersedes that statement: the main window now remembers its geometry. (The draft had cited §4, which is the dialog restore design and says nothing about the main window.)
- Proposal 0016 §5, "Does not change" (line 249): "The main window's own position (left to the window manager; only its size is set)". The position is now chosen by the app and remembered, so that line is superseded alongside §1.
- The `__init__` step order (ARCHITECTURE line 198, "eight steps in a fixed order", and Proposal 0014's step list): a placement step runs immediately after `_init_stores`, before `_init_variables`, so the order gains a step and the geometry is set before any widget is built. This is a deliberate change, not drift — the placement cannot run earlier, because `saved_settings` does not exist until `_init_stores`. The implementation PR updates Proposal 0014's numbered list accordingly.
- The main window's first-open position: centered in the primary work area instead of the window manager's choice (D2).
- The roadmap: no departure from the order — this is the scoped 0016 follow-on the owner staged between the faster-refresh suite and theme 2 on 2026-11-24, and it fills that slot. Two things the roadmap file does not record: the slot itself (its "immediate steps" paragraph is stale — it still lists the font update and faster refresh as next), and the widening of its "Settled decisions" line "A deliberate move or resize is remembered; anything else is not (0016, D3/D4)" to "a move, a resize or a maximize", since a maximized flag is a state, not a move or resize. The second is a departure in the roadmap's own terms (a proposal that overturns the document says so in its §5); the implementation PR records both, as it already promises for the stale paragraph.
- Known limits: the visibility test reads the bounding box of the virtual desktop, not the union of monitors, so a saved place can land on no monitor after the monitors are rearranged (existing 0016 behavior; worse for the main window than for a dialog, which has an anchor to fall back to). And a screen smaller than roughly a 916×640 work area cannot fit the floored 900×550 minimum plus the frame.
- The docs update changes ARCHITECTURE line 198 (the step order), line 183 (the three persisted geometry attributes become four), and README line 69 (the list of remembered windows).

## 6. Test Plan (for the implementation PR)

One implementation PR, naming this proposal and saying it does not depart from it. Full suite: `python -m unittest discover -s tests` must pass (1116 passed, 74 skipped at the base).

- **Unit tests, headless.** The validator: a full geometry at and above the 900×550 minimum is accepted, a smaller one is dropped, a position-only value and garbage are dropped. The save decision, as a Tk-free pure function in `library_geometry.py` returning the dict of keys to write (or None), driven by a table of cases: (1) an untouched normal session writes nothing; (2) a moved window writes the geometry, flag unchanged; (3) a window dragged back to exactly its opening place writes nothing; (4) opened normal, maximized, closed with no move in between: flag true only — the last normal geometry is the opening geometry, so it equals the baseline and the saved geometry stays as it was (a move in the same session adds the geometry, per the §4 table); (5) opened maximized, closed untouched: nothing written, both saved keys preserved; (6) opened maximized, un-maximized, closed with no move in between: flag false only — the window returns to the opening geometry, so it equals the baseline and the saved geometry stays as it was (a move after un-maximizing adds the geometry); (7) maximized then minimized, closed: flag true; normal then minimized, closed: flag false; (8) a cancelled exit writes nothing; (9) a later `_save_settings` re-emits both keys unchanged; (10) wiring (the `LibraryAppExitTests` `attach_mock` pattern): `geometry(...)` is called before `state("zoomed")`, and the save runs before `root.destroy`. The opening call: with no saved value the computed geometry is centered in the given work area with its whole frame inside it, at the default size; with a saved value on a second monitor it is restored at its saved size; with a saved value off every monitor it is centered on the primary. The visibility helper: a saved place visible when capped to the saved-point monitor's work area selects that work area, and one that is not selects the primary; a missing, position-only, or unparsable value is not visible. The saved point is scaled from canonical units before the lookup — the scaling itself is tested headless through `scale_pixels`, since the real `MonitorFromPoint` call is Windows-only — and a point is accepted and ignored off Windows, where `work_area_of` returns None (the existing `WorkAreaTests` cover only the off-Windows and failure fallbacks).
- **Live tests under Xvfb** (the existing live suites' pattern), in `test_library_librarian.py` so Windows CI runs them: open the app with no saved geometry and assert the whole frame is inside the desktop; move the window, restart, assert it reopens at the moved place. Off Windows `work_area_of` returns None, so these assert against the virtual desktop, not a real taskbar. Maximize and un-maximize cannot run under bare Xvfb — the `windows-ui` CI job runs only `test_ui_distribution.py` and `test_library_librarian.py`, and there is no Xvfb anywhere in `.github/` — so those move to the owner's Windows smoke.
- **A mutation check:** the `<Configure>` tracking not updating the attribute, and the exit save not comparing against the baseline, must each fail a test. Add two more: the flag read from `state()` instead of the tracked shown state, and the `<Configure>` handler without the `event.widget is root` guard.
- **Docs:** README.md, `docs/ARCHITECTURE.md`, and CHANGELOG.md (Unreleased) updated for the remembered place and the centered first open; `docs/ROADMAP.md` updated for the staged slot, and Proposal 0014's numbered step list updated for the new placement step. The ARCHITECTURE sentences that change are line 198 (the step order), line 183 (the three persisted geometry attributes become four), and README line 69 (the list of remembered windows).
- **Windows smoke (owner):** first launch opens centered, clear of the taskbar; move and restart restores the place; maximize and restart restores maximized; un-maximize returns to the saved size and place; Win+Up, a title-bar double-click, and Aero Snap to a half screen; and the two-monitor work area — whether a place on the second monitor restores there at its saved size, where the fallback centers (on the primary) when that monitor is gone, and a rearranged-monitors case (a saved place that lands on no monitor).

## 7. Open Questions for Reviewers

- **Q1.** The first open centers the window in the primary monitor's work area. Should it instead keep the window manager's placement and only clamp it into the work area when it would run under the taskbar? The recommendation is centering (D2): it is deterministic and testable, and it fixes the reported bug by construction. The stronger reason against clamping is that moving a mapped window is visible — the owner would see the jump — while a geometry set before the first map is never seen moving.
- **Q2.** When a saved place is gone, the fallback centers on the primary monitor, and the size cap reads the monitor holding the saved position. Should the fallback instead center on the monitor nearest the saved point, and should the cap stay on the primary? The recommendation is the split: the cap reads the work area by the saved position — give `work_area_of` an optional point and use `MonitorFromPoint` with `MONITOR_DEFAULTTONEAREST` for the saved top-left, scaled to physical pixels first — so a place on a second monitor comes back on that monitor at its saved size; the fallback centers on the primary, so the shell decides visibility before choosing `work` (D3). The pure rule is unchanged. The acceptable alternative is the nearest-monitor fallback, which the single-`work` call gives for free and which behaves acceptably, but the owner chose the primary.
- **Q3.** The maximized state is a separate boolean key. Should it instead be encoded in the geometry string? The recommendation is the separate key (D1): it reuses the geometry validator and the boolean pattern unchanged.
- **Q4.** The place is saved at exit only. Should it instead be written on every move and resize, so a crash keeps the latest place? The recommendation is exit only (D5): it matches the dialogs' close-time save, and the cost of a write per drag event is not worth the crash case. A cancelled exit must write nothing: a declined discard prompt returns before any save.
