---

In plain language: after P1 lands, a warm refresh spends about 1 second re-reading the library and about 14 seconds filling the table — and every sort click and filter change pays the same 14 seconds, because the table today throws all 42,375 rows away and re-inserts every one. This proposal stops throwing them away: on a refresh the table compares the new rows against the ones already showing and only inserts, deletes, or updates what actually changed. A warm refresh with a few changed files should then fill the table in a second or two instead of 14, and sort clicks should stop re-inserting rows that only moved. Nothing about the app looks different, and the table still shows exactly the same rows in exactly the same order. The one real decision is which of four ways to attack the insert, and the evidence says the streaming option DeepSeek proposed is spent now that P1 made the worker fast — the lever left is the insert itself.

## 1. Background and Goal

The roadmap stages faster refresh as the next scoped item after the font update, in the order the measurements dictate: P1 first, then P5, then P2. P1 (Proposal 0018, accepted, implementation PR #269 merged 2026-11-23) takes the worker from ~30 s to ~1 s on a warm refresh. What is left is the other half of the end-to-end warm refresh: ~14 s between the worker finishing and the table being usable again. P2 (process-pool parsing) stays for the full-parse case, where the worker is still ~29 s single-threaded; P5 is the warm case only: on startup the tree starts empty, so the first fill still inserts every row at today's cost, and startup-to-usable time does not change (§4).

Modularity, up front: the recommended design changes `refresh_table`'s internals only. It creates no new component boundary, moves none, adds no constructor input, persists nothing, and adds no settings key. The delivery contract between the loader and the table (one `("loaded", ...)` message, consumed by `_loaded`) is unchanged — the diff sits downstream of it, inside the table. The reason this is a proposal rather than an issue is the choice in §3: four defensible ways to attack the insert, and the choice constrains later work (theme 3's Previous/Next display-order seam, theme 5's library writing). Done means: a warm refresh with few changed files fills the table in ~1–2 s, a sort click no longer re-inserts unchanged rows, and the full suite is green — with the measurement in §2 confirming the split before the implementation is judged.

## 2. Current State (measured on main `d97ee89`, plus PR #269 — now merged as `48d7a5b`; the merge changes nothing in the measured path)

The chain after the worker finishes: the worker delivers one `("loaded", ...)` message; `_poll_load_results` hands it to `_loaded` on the main thread [CODE: `itgmania_library/library_loader.py:767`]; `_loaded` records the snapshot summary and calls `on_library_changed(rows, preserve_selection=False)`, which the shell implements as `_on_library_changed` [CODE: `itgmania_library/library_librarian.py:768-800`] — close the song page, then `with self._filter.batch(): set_rows(rows); set_choices(rows)`, and the batch's single notification calls `table.refresh_table`. `refresh_table` [CODE: `itgmania_library/library_table.py:406-437`] then does, in order: `filter_rows()`; a sort pass per sort key; `tree.delete(*tree.get_children())`; clears `_tree_item_rows` and the tint tracking; `_insert_batch(visible, 0, generation, selected_rows)`; and `_show_rows(visible)`, which pushes the visible rows to the distribution panel for its re-aggregation and matplotlib redraw [CODE: `itgmania_library/distribution_panel.py:262`]. `_insert_batch` [CODE: `itgmania_library/library_table.py:439-476`] inserts rows until a 12 ms deadline (`ROW_INSERT_BUDGET_SECONDS = 0.012`), then reschedules itself with `after(1, ...)`, always inserting at least one row per batch. Per row it builds the 40 display values (`HEADERS` has 40 columns [CODE: `itgmania_library/library_constants.py:34`]), formats Time and floats, takes the difficulty tint from `row_tints.row_tags`, and calls `tree.insert`.

The numbers are the owner's, measured 2026-11-22 on his machine (Ryzen 9 4900HS, Python 3.14.7; 7,499 files, 42,375 chart rows): worker 29.82/29.99 s, parse 29.00/29.11 s (97%), end-to-end warm ~40 s = ~26 s cache worker + a further ~14 s insert/render. **The 14 s is a residual, not a measured insert time** — it is everything after the worker: `_loaded`, the filter batch and dropdown rebuild, the filter, the sorts, the delete, the inserts, the batch scheduling, and the distribution redraw. It has never been decomposed, and that is the gap this proposal is built around.

The pure-Python phases were measured in this sandbox at Ian's scale [RAN: Python 3.12.3, `/tmp/measure_p5.py`, 42,375 synthetic rows built from the real fixture rows with distinct titles, packs, difficulties and meters; medians of 3 runs, two runs shown because the shared sandbox is noisy]:

| Phase | Time |
|---|---|
| `filter_rows`, all-pass filters | 0.005–0.008 s |
| Sort, 1 key (Pack, the default) | 0.015–0.080 s |
| Sort, 3 keys (Pack, Difficulty, Meter) | 0.113–0.243 s |
| Per-row display values + tags, no Tk | 0.47–0.51 s |
| `set_choices` sets and sorts | 0.009–0.011 s |
| Distribution summary stats (Meter) | 0.021 s |
| `filter_rows` with a search query | ~0.10–0.13 s |

Total Python-side work: **≈0.5–0.9 s** — roughly 5% of the 14 s, and the sandbox's shared vCPUs are slower per core than the owner's Ryzen 9, so these are likely upper bounds. [INFERRED] The remaining ~13 s over 42,375 rows is ≈0.31 ms per row, which is consistent with per-item `tree.insert` cost dominating — but that is arithmetic on a residual, not a measurement. What cannot be measured here, and must be measured on the owner's machine before the design is judged: `tree.delete` of 42,375 items, `tree.insert` per row, the `after(1, ...)` scheduling overhead across ~1,000 batches (42,375 rows at ~40 rows per 12 ms batch), and the distribution canvas redraw. §6 gives the harness: a Tk driver script modelled on `tools/mockup_driver.py` that times each phase separately on the real library, and varies `ROW_INSERT_BUDGET_SECONDS`, so the split is a measurement, not an inference.

Coupling inventory. `refresh_table` is called from four places: the filter's change notification (every search keystroke after its delay, every dropdown change) [CODE: `itgmania_library/library_librarian.py:449`], `sort_by` on every sort click [CODE: `itgmania_library/library_table.py:374-390`], `_on_library_changed` on every load and sync [CODE: `itgmania_library/library_librarian.py:792,804`], and the empty-table repaint. So the 14 s is paid on every one of those, not only on refresh — a sort click on the owner's library re-inserts all visible rows today. `_tree_item_rows` (item id → row dict) is read by the focused-row opener [CODE: `library_table.py:352`], the selection keeper [CODE: `:410`], and `selected_rows()` for the course builder [CODE: `:478-481`]; the diff must keep it exact. The table reads rows only through the filter (option C, PR #168) and pushes the visible rows to the distribution panel through the injected `show_rows` callable [CODE: `library_table.py:110,437`]. The layer table puts `library_table` at layer 4, `library_filter` at layer 2, `row_tints` at layer 0; the table already imports downward only. Tests: `tests/test_library_table.py` (headless, the Treeview is a Mock; `_insert_batch` batching, tags, and the count label are pinned there, including the 12 ms budget tests at `:528-581`), plus two live-Tk selection tests in `tests/test_library_librarian.py`. Full suite at the merged head: 1000 tests OK, 74 skipped.

## 3. The Decisions

**D1. The target is the insert, not the worker — DeepSeek's P5 as written is spent.** P5 was "chunked result streaming to the queue": the worker delivers rows in chunks so the table starts inserting while the worker still parses. Its promised payoff was earlier first paint while the worker ran for ~30 s. After P1 the worker runs for ~1 s, so there is almost nothing left to overlap: streaming would save at most ~1 s of overlap and would complicate the delivery contract (multiple `("loaded", ...)` messages, a completion signal, generation handling for a load superseded mid-stream, the status line and snapshot summary waiting for the last chunk, the filter not publishing a partial library to the course builder or the song page). The roadmap's "earlier first paint is certain" was written when the worker was 30 s; with a 1 s worker the first paint is ~1 s earlier at best. Recommendation: do not build streaming. The table-side batching DeepSeek's P5 resembles already exists (`_insert_batch`, predating the package move) — what does not exist is any avoidance of the inserts themselves. Table-side batching already provides progressive paint on a full insert (the 12 ms budget, `after(1, ...)` rescheduling); rejecting streaming is rejecting worker-side chunked delivery, not progressive paint.

**D2. The table updates by diff, not by rebuild (recommendation).** On a refresh, compare the new visible list against the rows already in the tree and only insert, delete, or update what changed; unchanged rows stay where they are. A warm refresh with few changed files then inserts only the changed files' rows, and a sort click moves rows instead of re-inserting them. The alternatives: **(a)** streaming (D1 — rejected: the overlap is gone, the contract cost is real); **(b)** tuning the insert — a larger `ROW_INSERT_BUDGET_SECONDS` (fewer batches, less `after()` overhead, at the cost of responsiveness), precomputing the display values once per row (saves the ~0.5 s values loop, but puts display state on the row dicts the filter owns), or inserting with the tree hidden (a known Tk trick, [UNVERIFIED] on this tree, and it shows an empty table until the insert finishes — the opposite of today's streaming paint). These are measurements to try on the owner's machine, not the design: at most they shave a second or two off a 14 s insert, and (b) as a whole does not change the linear-in-rows cost; **(c)** a virtualized table that inserts only the ~50 rows in view — the total insert would collapse, but it rebuilds the component (selection across pages, keyboard navigation, the `_tree_item_rows` map the course builder and song page read through, the distribution push, the display-order seam) and changes what the user sees (scrollbar and Ctrl+A behaviour). Rejected for P5; it stays the option if the diff ever proves insufficient. The diff is the only option whose cost is proportional to what changed, which is exactly what P1 made small.

**D3. A row is identified by its chart key, and the key's uniqueness is verified, not assumed.** The loader builds fresh row dicts on every refresh (even reused rows come from the snapshot read), so identity cannot be `id(row)`. The recommended key is `("Course path", "Type", "Difficulty", "Chart")` — the scores join key plus the chart description, which is what distinguishes two Edit charts of the same type and difficulty in one song. [UNVERIFIED] Whether the engine guarantees at most one chart per (StepsType, Difficulty) except Edits distinguished by description: that needs the notes/engine check in §7 Q1. If the key is not unique, the diff re-inserts the colliding song's visible rows as a block — never a guessed match, and no positional matching across a collision (two Edits swapping description text between refreshes would mis-associate). That is still O(charts in song), not O(library), and the fallback is part of the design, not an afterthought.

**D4. One diff path for every refresh_table caller.** Loads, syncs, sort clicks, and filter changes all go through the same diff. A sync changes only scored cells, so the diff updates those items' values in place (`tree.item(item, values=...)`) instead of re-inserting them; a sort click re-orders by key, so the diff moves items instead of re-inserting them — subject to §7 Q2 (whether `tree.move` is actually cheaper than delete+insert, which is unmeasured). No caller gets a separate fast path, because two paths would drift.

## 4. Recommended Design in Detail

**The diff (`refresh_table`, `library_table.py`, layer 4 — no boundary moved, no constructor change).** One-sentence description: given the visible rows the filter and sort produce, `refresh_table` makes the Treeview show exactly those rows by changing only what differs from what is already showing.

The shape, in order:

1. `refresh_table` computes `visible` exactly as today (`filter_rows`, then the per-key sorts) — the display order still comes from this list, never from reading the Treeview, so the theme-3 Previous/Next seam (a shared display-order accessor over this list) is untouched.
2. Build the new key→row map with the D3 key, and the current key→item map from `_tree_item_rows`. The diff also keeps, per item, the display tuple it last showed — the 40 values plus the tag list, as returned by the shared helper below — and detects a content change by comparing the newly computed tuple against the saved one, never by comparing row dicts: `merge_scores` re-derives score fields in place [CODE: `itgmania_library/library_sources.py:216`], mutating the same dicts the table already holds, so on a sync the old and new dicts are the same objects and a dict comparison would see no change. Walk both maps: keys in the tree but not in `visible` are deleted; keys in `visible` but not in the tree are inserted at their position (`tree.insert` with an index, not only `"end"`); keys in both whose saved tuple differs from the newly computed one (scores after a sync, a re-parse that changed a chart's values) have their values updated in place and their saved tuple replaced; keys in both whose position changed are moved (`tree.move`), subject to Q2. A move keeps the item id (`tree.move` does not re-create the item), so `_tree_item_rows` and the saved display tuples travel with it unchanged.
3. Selection is carried by key, not by item id: record the selected keys before the diff (from `_tree_item_rows`, as today) and re-apply them after, through the existing tint bookkeeping (`note_selected`).
4. The apply phase keeps the existing time-budgeted batching: inserts and moves run under the same 12 ms deadline and `after(1, ...)` rescheduling with the same generation guard, reusing `_insert_batch`'s shape — the first load, when the tree starts empty, is still a full insert and still streams in. Deletes and in-place value updates are cheap Tcl calls and run synchronously inside `refresh_table`; if the measurement shows otherwise, they join the batched phase.
5. The count label and the `_show_rows` push to the distribution panel run once at the end, as today — the panel re-aggregates from the same `visible` list, unchanged.

The constructor contract does not change: `LibraryTable` takes the same inputs, and the diff needs nothing new — the filter, the injected `show_rows`, and the saved layout already provide everything. `ROW_INSERT_BUDGET_SECONDS` stays a module constant, not a setting: it is an internal tuning knob, and the diff makes it matter less, not more. The legibility test: "the table shows the filter's visible rows, changing only what differs from what is already showing" — a standalone reader can hold that without the rest of the file.

What the diff does not do: it does not change what a row displays (the 40 values and the tag list are built the same way, in `_insert_batch` and in the in-place update path, from one shared helper returning `(values, tags)` so the two cannot drift — on tags as well as values, so a sync that changes difficulty or selection state cannot leave the tint behind); it does not change the filter, the sort, or the delivery; and on a cold refresh — first load, or a full parse — the tree starts empty, so the diff inserts everything and the insert costs what it costs today. The win is the warm case, the sort click, and the filter change, which is where the library is already loaded.

## 5. What Does Not Change

- The worker, the parse, the manifest, and the snapshot: P1's and P2's territory. The `("loaded", ...)` delivery gains no kwarg, and `_loaded` and the status line are untouched.
- The filter, the sort keys, the column order and widths, and the dropdown rebuild (`set_choices`): the diff consumes their output, it does not change how they compute it.
- The distribution panel's push: `_show_rows(visible)` is called once per refresh with the same list, and the panel's getter-callback unification (theme 3) is untouched.
- The display-order seam for theme 3 (Previous/Next, issue #263): the order still comes from the `visible` list `refresh_table` computes, never from a Treeview read-back. The diff must not introduce one — a later theme will share that list, and a diff that derived order from the tree would foreclose it.
- Theme 2 (pack and series view): the table will gain a Series column/grouping there; the diff compares row identity, not the formatted values, so a new column is a display change, not a reason to re-insert. A row whose series data arrives later is a content change by key, handled by the in-place update.
- Theme 5 (library writing): an edited row changes its content, which the diff detects by key and updates in place. Nothing in this design assumes rows are immutable — only that their keys are stable, which is D3's question.
- The table's public surface: `selected_rows()`, `library_rows()`, `layout_state()`, and the sort/column APIs keep their signatures. The batching constant stays a constant.

## 6. Test Plan (for the implementation PR)

- **Measure first, on the owner's machine (before the implementation is judged).** A Tk driver script modelled on `tools/mockup_driver.py` opens the real app on the owner's library and times, separately: `filter_rows` + sorts; `tree.delete` of all items; `tree.insert` per row (steady-state, and the first paint); the `after(1, ...)` batch overhead (vary `ROW_INSERT_BUDGET_SECONDS` across 12/50/200 ms); and the distribution redraw. The script reports the split and the per-row insert cost; if the split contradicts §2's inference (e.g. the redraw dominates), the design is revisited before implementation — see §7 Q3.
- **Pin current behaviour before the diff (headless, `tests/test_library_table.py`).** The existing `_insert_batch` tests stay and keep passing unchanged. New tests, all with the Treeview mocked as today: a refresh whose rows are unchanged inserts nothing and deletes nothing; a changed row's values are updated in place; a new row is inserted at its sorted position and a deleted row is removed; a re-sort moves rows without re-inserting them (subject to Q2); selection is preserved by key across a diff; a filter narrowing keeps the surviving items; a sync re-scores cells in place (driven through the real sync path, where `merge_scores` mutates the shown rows in place — the diff must detect the change from its saved display tuples, not from the row dicts); a superseded generation inserts nothing. A full-library equivalence test: the tree contents after a diffed refresh equal the tree contents after today's rebuild, row for row and in order, on the fixture library with a changed, a new, and a deleted file.
- **Live smoke (owner, Windows).** Load / refresh on the real library, then a sort click, then a filter change: the table shows the same rows in the same order, the count label settles, and the refresh timing script's incremental pass is re-run so the worker and the insert are reported separately.
- **Full suite:** `python -m unittest discover -s tests` green (1000 tests, 74 skipped headless, at the merged head).

## 7. Open Questions for Reviewers

- **Q1.** Is `("Course path", "Type", "Difficulty", "Chart")` a unique key for a chart row — i.e. does the engine allow at most one chart per (StepsType, Difficulty) in a song except Edit charts, which the description distinguishes? (Recommendation: yes, with the song-group re-insert fallback in §4 if it is not. Needs the notes/engine check before implementation.)
- **Q2.** On a re-sort, are the rows moved with `tree.move` or deleted and re-inserted? (Recommendation: moved — but only if the owner's-machine measurement shows `move` is cheaper than delete+insert per row. If it is not, a re-sort does a full re-insert as today, and the diff's win is the refresh and filter cases only. The measurement in §6 decides.)
- **Q3.** The go/no-go: if the §6 measurement shows the 14 s is *not* dominated by per-item insert cost — for example the distribution redraw or the batch scheduling dominates — does the design change? (Recommendation: the diff is still built, because it also fixes the sort-click and filter-change cases, but the implementation PR then also takes the measured dominant term: a redraw deferral for the panel, or a larger batch budget.)
- **Q4.** Should `ROW_INSERT_BUDGET_SECONDS` become a setting? (Recommendation: no — it stays an internal constant. If the measurement shows the budget is the lever, that is evidence the diff is working (fewer batches because fewer inserts), not evidence the user should tune it.)
