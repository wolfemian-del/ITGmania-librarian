---

In plain language: of the five windows the app builds itself on top of the main window (Build a course, Advanced Search, the song page, Data paths and About; Windows' own message boxes and file pickers are not among them and are not touched), none chooses where to appear. Each leaves the position to Windows, and on the owner's machine Windows puts every one of them at the top-left corner of the screen, whatever the main window is doing. This proposal makes every one of them open centered over the main window, the first time and any later time the owner has not deliberately moved it. Once the owner moves or resizes Build a course, Advanced Search or the song page, the app remembers that place, and the song page — the one window that forgets on quit today — remembers across restarts like the other two. The rule that decides whether a remembered position is still on screen exists today as two word-for-word copies (issue #103), and the song page would have been a third, so the rule moves into one tested place first.

Three choices were the owner's to make by feel, and all three were decided as recommended on 2026-11-19: whether a dialog you never touched keeps following the main window (D3), what the song page remembers when you move it (D4), and whether windows must stay clear of the taskbar (D6). Each is written as a plain question in §3. The review also found that centering done naively would make the taskbar problem worse than it is today, which is why D6 exists.

## Amendment (2026-11-20, issue #244)

After the proposal completed (PRs #242–#246), Greptile's review of PR #243 found, confirmed by measurement, that the §4.1 cap does not account for a window's minimum size: on a work area smaller than the minimum plus the frame, the capped size is below the minimum, so the window opens at its minimum instead — larger than the size the position was clamped for — and can hang off the work area. The rule now takes the window's minimum size as an input: the cap is floored at the minimum, and the position is clamped for the enforced size. §4.1 (signature, rule 1, three vectors), §4.2 (constructor input 6) and §4.5 are amended; nothing else changes.

## 1. Background and Goal

Issue #103 filed a deliberate duplication: the on-screen check that decides whether to reopen a window where it was exists in `CourseBuilder` and `AdvancedSearch`, "identical today", to be shared "when a third dialog needs geometry memory". Proposal 0013 §5 recorded that the song page was not that third dialog because its memory was session-only, and that any persistence follow-up "should do the #103 extraction". The owner has now asked for first opens to be centered rather than upper-left, and for a move of the song page to persist; this is that follow-up.

Owner decisions already taken (2026-11-19): center over the main window, not the screen; apply the placement through shared logic to all the dialogs; a move of the song page persists.

Scope: the five windows the app builds itself as `tk.Toplevel`. The native message boxes and file pickers (`messagebox`, `filedialog`) are positioned by Tk and Windows and are not touched. The main window's own opening position stays under the window manager; only its size is set (`LibraryApp._init_window`).

Modularity: this change adds one small component, `window_placement.py` (a helper each window holds; it is not a window and imports no Tkinter), adds pure functions to `library_geometry.py`, adds two optional inputs to `SongPage`'s constructor, and persists one new settings key. Each is a proposal trigger under AGENTS.md. It amends earlier proposals on the points in §5.

Done means:

- Every secondary window opens centered over the main window unless the owner has deliberately placed it. Every placement the application chooses itself (centering, a size cap, a position-only restore shifted back on screen) keeps the window's whole frame inside the monitor's work area, so its bottom edge is never under the taskbar, provided the work-area lookup succeeds (D6). A place the owner deliberately dragged to is restored where it was, as today, even if part of it is under the taskbar.
- The on-screen rule exists once, with direct unit tests.
- The song page keeps a deliberate placement across restarts under a new `song_page_geometry` key.
- The deliberate changes in §5, and nothing unrelated, differ from today.

## 3. The Decisions

**D1. Where the shared logic lives. Recommended (unanimous across the review): pure functions in `library_geometry.py` plus a small helper, `WindowPlacement`, in a new `window_placement.py`.** The pure functions decide the geometry; the helper owns what would otherwise be copied into three windows: reading the main window's box, holding the current saved value, holding the geometry the window opened with (the "opening baseline", defined in D3), and saving only a deliberate change. Alternative: the pure functions only, with that state left in each window. Lane B's trace showed the state, not the arithmetic, is what drifts: record once per open, compare on close, reset, guard against a destroyed window. Three copies of that would recreate issue #103.

**D2. The centering convention (owner-decided: over the main window), now measured.** A window opens centered over the main window's client area. The anchor is one reading, `winfo_x`, `winfo_y`, `winfo_width` and `winfo_height` of the main window, used whether it is `normal` or `zoomed` (maximized): [RAN] (Codex) for a normal window these equal the `geometry()` offset and size, and for a maximized one they are right where `geometry()` is stale (158 px right and 108 px down of the visible center in Codex's probe). When the main window is minimized or withdrawn there is no anchor, and the window is centered in the work area (D6) of the primary monitor. A dialog that is already open is not moved when the main window later moves, minimizes or restores. The centered position is then clamped so the window's whole outer box, frame included, lies inside the work area.

**D3. Should a dialog you never moved keep following the main window?** If you leave Build a course or Advanced Search where it first opened, it opens centered over the main window again next time, even if you have moved the main window; if you move or resize it, that placement is remembered instead. Recommended: yes, for all three remembering windows. In everyday terms: when a window finishes opening, the app notes where it is and how large it is (the **opening baseline**); when the window closes, it compares the two. If they differ, the change is remembered; if the window is back exactly where it started, or was never touched, nothing is recorded and the next open centers again. Today the two dialogs save on every normal close; once windows are centered, a dialog closed untouched would save its centered position and keep appearing there after the main window moved to another monitor. The song page already saves only a deliberate change, and the helper extends that rule to the dialogs. Two edges, both small: a dialog moved away and then dragged back to exactly its opening spot records nothing, so if the main window has also moved meanwhile the next open re-centers; and because a plain close no longer saves, a saved position that has become unusable (an unplugged monitor) stays in the settings file until the owner next moves the window. It does no harm — the on-screen test rejects it on every open, and the window centers — but it is not refreshed as it is today. Also, the settings file is still rewritten for other reasons; the change is only that a plain close writes no new geometry. This amends Proposal 0003 §4 and issue #98's close-time save.

**D4. After you move or resize the song page, what should happen to its size on later songs? Decided: option B.** Three terms first: **content sizing** means the app sets the window's height from the song it shows (the chart list's length); **position-only** means remembering where the window is without its width and height; the **opening baseline** is the size and position measured once the window has finished opening.

*What B does.* One setting, `song_page_geometry`, in two forms. `WxH+X+Y` means the owner resized the page: size and position are restored and content sizing is off. `+X+Y` means the owner only moved it: the position is restored and the page still sizes itself to each song, shifted up if a taller song would run past the taskbar. The save rule, compared against the opening baseline when the page closes:

1. If the current size differs from the baseline size, store the full form of the current geometry (a resize; a resize that also moved the window stores the new position too).
2. Otherwise, if only the position differs: when the saved value already has a size, store the full form with the saved size and the new position (so a moved page that was earlier resized to 910 px stays 910 px tall, and a size capped by a smaller monitor is not lost); when it does not, store the position-only form.
3. Otherwise store nothing.

The three dialogs have no content sizing, so for them any difference is a full-form save. Backward compatibility is the sharp edge in B's history: a full geometry written by an earlier approach (A, or today's session-only value) still parses, but it can never reveal whether its size came from a deliberate resize or from a move frozen by A — which is why B is chosen now, before any value is persisted.

*The rejected alternative, A: one saved geometry, Proposal 0013's session rule carried across restarts.* Any move or resize saves position and size, so a page you moved while a one-chart song (580 px tall) was showing stays 580 px tall for a sixteen-chart song (910 px needed), with a scrolling chart list. It reuses the existing key shape and validator unchanged. The sharp edge is not a one-time cost: songs have between one and many charts, so a frozen size fits one kind of song; fixing it by resizing breaks the other (resized to 910 px, every one-chart song opens in a tall, mostly empty window), and the only way back to content sizing is deleting the setting. The edge exists today within a session; persistence would make it permanent.

Why the recommendation changed from A to B: Muse's Lane C showed the recurring cost described above, which my first draft called a one-time edge; and showed that my claim "B can be added later without breaking A's key" is true only in the narrow sense that the value still parses, because once A stores a full geometry nobody can tell a deliberate resize from a size frozen by a move. Proposal 0013 §3 considered the nearest alternative — sizing the height on every `show()` and taking only position and width from the saved geometry — and rejected it because it would discard a deliberate resize; B keeps a deliberate resize, which is the objection's point. Three reviewers (Codex, Gemini, ChatGPT-6) preferred A, Codex and ChatGPT-6 conditionally: both said they would switch if the frozen height looked wrong in use, and Lane C's description is exactly that case. It was a close call, made by the owner by feel. B amends Proposal 0013 §3's rule (a move no longer freezes the size, also within a session). Cost: one position-only parse and validator, one branch in the helper's save and one in the opening rule, and a constructor flag (`content_sized`, input 5 in §4.2).

**D5. The fallback and the key.** When a saved position is no longer on the desktop (an unplugged monitor), the saved size is kept (capped to the work area) and the window is centered, instead of the size-only handoff to the window manager that the two dialogs do today. The song page's key is `song_page_geometry`, optional, omitted from the settings file until the owner has deliberately placed the window. Validation has two paths, because the two forms differ: a full `WxH+X+Y` value goes through `_valid_window_geometry` against `theme.SONG_PAGE_MIN_SIZE` (560 by 420), which accepts only a full geometry [CODE: `library_stores.py:220` calls `parse_course_geometry`, which rejects `+X+Y`]; a `+X+Y` value goes through `parse_window_position`, which accepts exactly two signed offsets (`+100+50`, and `+-8+40` or `-8+40` for a negative one), rejects everything else — including the size-only `1000x620`, a mixed or trailing-garbage string, and non-strings — has no minimum size to check (it has no size), and returns the canonical `+X+Y` spelling with `+-8` for a negative coordinate. A value on neither path is dropped at startup, as an invalid one is for the other keys. Reading across versions: a file from an earlier version has no such key and opens as today; a file written by this version and read by an earlier one loses the key on that earlier version's next save (`_save_settings` writes a fixed set of keys), so the song page forgets its place. That is acceptable for one optional UI value, and no migration is proposed.

**D6. Should windows be kept clear of the taskbar? Decided: yes (W1) — fit them to the work area of the main window's monitor.** The **work area** is the part of a monitor Windows makes available to ordinary windows, which excludes reserved areas such as the taskbar. [RAN] (Codex) On the owner's machine the work area is 1920×1032 under a 48 px taskbar, and a screen-height window reached y=1092, 60 px past the work area. The song page's cap (`winfo_screenheight()`, Proposal 0013 Q1) does not prevent that today, but today a size-only window sits at `+0+0`, so any page up to about 1000 px tall clears the taskbar. Centering changes that: [RAN] (the reference run in §4.1) a sixteen-chart page, 760×910, centered over a main window at +100+250 and clamped to the whole desktop, ends with its outer bottom at y=1080, covering the bottom 48 px, where the song page's button row sits (it is built first and packed at the bottom of the window); the same page clamped to the work area ends at y=1032. So the first draft would have made a case that works today fail.

- **W1 (decided): clamp and cap to the work area.** The pure function takes the work-area box; the song page's height cap reads it instead of the screen height, minus the frame (this amends Proposal 0013 Q1); `work_area_of(hwnd)` in `library_geometry.py` asks Windows for the work area of the monitor holding the main window (`MonitorFromWindow` and `GetMonitorInfoW`, via `ctypes`, which that module already imports for DPI awareness; the handle is the main window's `winfo_id()`), returns the primary monitor's work area when given no handle (which is what D2 uses when the main window is minimized), and returns None on any failure or off Windows, in which case the caller uses the virtual desktop. Like `declare_dpi_awareness`, it must return before touching `ctypes.windll` when `sys.platform != "win32"`, and catch `(AttributeError, OSError)`, so importing the module on another platform still works. [RAN] (Codex) the lookup works for a normal, maximized and minimized root at 100%. [UNVERIFIED] on two monitors.
- **W2 (rejected): keep the whole desktop.** Simpler, but the taskbar problem stays, now reachable by centering.

What W1 does not do: the on-screen test for a *saved* full-form position keeps using the whole virtual desktop, as today, and returns it as it is. A window the owner deliberately dragged partly under the taskbar is restored where it was, and §4.1 states this as a separate rule.

## 4. Recommended Design in Detail

**4.1 The pure functions (`library_geometry.py`, layer 0, no Tkinter).** One-sentence description: given the geometry saved last time, a default size, the main window's box, the desktop and the work area, it returns the geometry string a window should open with.

PR 1 contract (no behavior change):

```
opening_geometry(saved, size, desktop, scale) -> str
```

`saved` is the canonical `WxH+X+Y` string or None; `size` is the default as a physical `(width, height)` pair; `desktop` is `(left, top, right, bottom)` of the virtual desktop in physical pixels; `scale` is the display factor. If `saved` parses and passes today's visibility test it returns the scaled geometry with no size cap; otherwise it returns the size alone as `WxH`, so the window manager places it. [RAN] This reproduces `CourseBuilder._geometry_for_open` on 228 cases (four scales, three desktop shapes including negative origins, the threshold boundaries), and Grok reproduced it independently on a 17-case boundary table (99/100 px, 31/32 px, title bar −16/−17, 125%/150%/200% scaling, a negative-origin desktop) with no mismatch; Grok's ten-case table, in which seven cases diverge between the PR 1 contract and the final rule, shows the same fact from the other side.

Final contract (PR 2):

```
opening_geometry(saved, size, desktop, scale, *, anchor=None, work=None, frame=(16, 39), min_size=(1, 1)) -> str
```

`saved` is now a canonical string in either form — full `WxH+X+Y` or position-only `+X+Y` — or None. `anchor` is `(x, y, width, height)` of the main window or None; `work` is the work-area box (default: `desktop`); `frame` is the window frame's extra width and height in canonical 100% units, the measured 16 and 39. Units are physical pixels except `saved` and `frame`. Python's `//` on a negative number floors toward negative infinity (`-7 // 2` is `-4`, not `-3`); every division below is that floor division. The frame components are scaled independently: `frame width = scale_pixels(16, scale)` and `frame height = scale_pixels(39, scale)`.

Four rules govern the result; they are separate because they treat a deliberate placement and an application-chosen one differently:

- **Rule 1, the cap.** The usable size is capped to the work area less the frame, and floored at the window's minimum size (`min_size`, canonical units like `frame`; the song page's is 560×420, Advanced Search's 480×520, Build a course's 700×440; a window with no minimum uses 1×1): width at most `work width − frame width` and at least `min width`, height at most `work height − frame height` and at least `min height`. With the default minimum the size never goes below 1 (when the work area is smaller than the frame the size collapses to 1×1 and the left and top edges win in the clamp). When the work area is smaller than the minimum plus the frame, the size is the minimum — the window is larger than the work area, and the position is clamped for that enforced size, so its left and top edges stay on screen. The cap comes before any visibility test, and the size in rules 2–4 is this capped size: capped, then floored at the minimum, so every clamp and centering is computed for the size the window will actually have.
- **Rule 2, a full-form saved position is restored as it is.** If `saved` is a full geometry, its four numbers are scaled with `scale_pixels` (Python's `round`, as today), its size is capped (rule 1), and if the capped box passes today's visibility test against `desktop`, the result is the capped size at the saved position, formatted with `format_geometry` (so a negative offset reads `+-8`) and returned without any clamp. The test, exactly as today's code: the visible width `min(x + w, right) − max(x, left)` is at least `scale_pixels(100)`, the visible height `min(y + h, bottom) − max(y, top)` is at least `scale_pixels(32)`, and `y ≥ top − scale_pixels(16)`. This is D6's carve-out: a place the owner dragged to is not second-guessed, so a saved `900x900+30+100` returns as it is, with its outer bottom 7 px past a 1032-px work area (100 + 900 + 39 = 1039).
- **Rule 3, a position-only saved position is restored shifted back on screen.** If `saved` is `+X+Y`, the size is the `size` argument, capped (rule 1); `size` is what the window needs for its content (§4.2). The position is scaled with `scale_pixels`; if the capped box at that position passes the same visibility test, the position is kept but shifted, if necessary, so the outer box (size plus frame) lies inside `work` on all four edges, and the geometry is returned. This is why a taller song shifts a moved page up rather than under the taskbar (D4).
- **Rule 4, otherwise center, then clamp.** In every other case (nothing saved, an unparseable value, or a saved box that is no longer visible, whether the capped saved size or the content size) the usable size is the capped saved size for a full form and the capped `size` otherwise, and it is centered. With an `anchor`, the position is `anchor x + (anchor width − width) // 2` and `anchor y + (anchor height − height) // 2` (the dialog and the main window have the same frame, so their client areas share a center). Without one, the window's outer box is centered in `work`: `work left + (work width − (width + frame width)) // 2`, and the same for the top. The position is then clamped so the outer box lies inside `work` on all four edges: `x = max(left, min(x, right − (width + frame width)))`, and the same for `y`. The clamp applies only here and in rule 3; a restored full-form position (rule 2) never reaches it.

`parse_window_position(text)` decides which form `saved` has: a string that `parse_window_geometry` accepts is full; one that it rejects and `parse_window_position` accepts is position-only; anything else is treated as nothing saved.

**4.2 The helper (`window_placement.py`, layer 1; it imports no Tkinter and works on the window objects it is handed, as `library_filter` does at layer 2).** One-sentence description: given its owner window, the display scale and the geometry saved last time (if any), it says what geometry a window should open with, remembers the geometry the window actually opened with, and reports a new geometry only when the owner has moved or resized the window.

Constructor, enumerated:

1. `parent`: the owner window the placement is relative to (today always the main window; the contract does not assume it). The helper reads its box through `winfo_x`, `winfo_y`, `winfo_width` and `winfo_height` and its state through `state()`, and takes the window handle for `work_area_of` from `parent.winfo_id()`.
2. `dpi_scale`: the display scale factor.
3. `saved_geometry` (default None): the canonical geometry saved last time, in either form. From construction on, the helper owns the current value; the windows' own `_saved_geometry` attributes go away.
4. `report_geometry` (default None): called with the canonical string when a new geometry is to be stored.
5. `content_sized` (default False): the window sizes itself to its content, so a pure move is stored as `+X+Y` when no size is saved yet (D4).
6. `min_size` (default (1, 1)): the window's minimum size in canonical units; the cap (rule 1) never sizes below it, so the position is clamped for the size the window will actually have (issue #244).

Methods and their contracts:

- `geometry_for_open(default_size_text)`: takes the canonical size string from the theme (`"1000x620"`), scales it with `parse_window_size` and `scale_pixels`, reads the anchor (D2), the desktop and the work area (D6), and calls `opening_geometry`.
- `geometry_for_content(width, height)`: the same for a window whose size is known only after it is built (physical pixels). The song page calls it from its content branch, with `width` the scaled theme default's width (760 at 100%) and `height` its content height; these two numbers are the `size` that rule 3 uses, so a position-only saved value always combines with the current content-sized height and never with a stale saved size.
- `has_saved_size`: read-only; true when the saved value is a full geometry. The song page's content sizing runs only when it is false (the test `_saved_geometry is None` at `song_page.py:234` becomes this).
- `record_opening(window)`: called exactly once per open, after the window's final geometry has been set and, for a window built while withdrawn, after `deiconify()`. It clears any earlier baseline at once, then schedules an idle callback that records the geometry the window has once placed. The callback does nothing if the window is gone or a baseline is already set, so duplicate scheduled callbacks, and a minimize and restore that nothing re-triggers, can never overwrite it. The protection is against duplicate callbacks, not against repeated explicit calls: a second explicit call clears the previous baseline before scheduling another capture, so callers call it once per open. The baseline is cleared only by the next `record_opening`, not by a close. It must come after `update_idletasks()`, which runs pending idle callbacks: scheduled before the song page's content sizing, it would record the 760×1000 opening geometry, and every plain close would then look like a resize.
- `save(window)`: returns if the window is gone or its state is not `normal`. From PR 3 it also returns unless a baseline exists and the current geometry differs from it. When it stores, it applies D4's rule — a full-form store when the size differs from the baseline, or the window is not `content_sized`; for a content-sized window whose size equals the baseline, the saved size with the new position when the saved value has a size, otherwise the position-only form — updates `saved_geometry` first, so that closing and reopening within one session reuses the new place, then calls `report_geometry`. The baseline of a tall song's shifted-up geometry is the geometry the window actually has after the shift, so closing it untouched stores nothing and the original saved position survives. Until PR 3 the helper is used only for the opening half; the windows keep their own save logic (§6).
- `saved_geometry`: read-only property for the current value.

A window with no memory (Data paths, About) constructs it with only the first two inputs; `save` then reports nothing.
