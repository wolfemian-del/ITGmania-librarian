In plain language: double-clicking a chart opens a song page — one window for the whole song, showing its banner, background and jacket, its title, artist and pack, its music file with length and preview window, and all of its charts with meter, BPM and scores. From there you can play the song's preview and open the song's folder on disk. The page starts dependency-free for images (Tk reads PNG natively). The two real decisions are audio — an in-app preview needs pygame, while the no-dependency alternative opens the file in your default player and plays the whole song instead of the preview window — and how the song folders are found, since the cache records only a virtual path and the folders live wherever the game was told to look (see §2). Everything else in this proposal is staging those choices so they can be made late.

## 1. Background and Goal

This is the feature Ian chose as the next target once the ground settled: Proposal 0010 is complete, v1.3.0 is released, and the docs pass (#184) is merged. His sketch (2026-11-15) is the spec in outline — a new window opened from a given chart, maybe via double-click, showing the song's associated data from the cache file, with all charts for that song pointing to an identical song page, and the preview playable from there. "Done" means a double-click on any chart opens that song's page, the page shows the media the cache already records, the preview plays the game's sample window, and the folder button opens the song's folder — with the page degrading gracefully when a pack has been rotated out and the folder is gone, since the cache keeps records of songs no longer on disk.

This change creates a new component boundary (`song_page.py`, following the 0009 dialog pattern), adds a constructor contract for it, and has two or more defensible designs where the choice constrains later work (image and audio dependencies, how the media reaches the page). It therefore needs a proposal under the workflow rule. It persists one new settings key (`song_roots`, §4) and changes no file format in the recommended design.

## 3. The Decision: a new song-page component, media carried in the row, dependencies decided late

The recommendation is a new `song_page.py` component following the 0009 dialog pattern (geometry in, callbacks out), opened by double-clicking a chart row through a new optional `on_row_double_click` callable input to `LibraryTable`, on the `show_rows` precedent. The song's identity is its `"Course path"`: the app hands the page every row sharing that value, so all charts for the song open the identical page. The media fields are carried as hidden row keys at parse time, on the "Score description" precedent — they are already in hand when the row is built, they survive the snapshot verbatim, and the page then works from snapshot-restored rows with no file re-read.

Folder resolution is a small Tk-free pair in `library_sources.py`, on the course builder's "Songs location(s)" precedent (course:11.3): `song_roots(cache_dir)` returns the ordered root list — the `AdditionalSongFoldersWritable` entries from `Preferences.ini` (comma-split, reverse order within the list, since later mounts win), then the `AdditionalFolders` entries (each plus `/Songs`), then the user-data `Songs` — and `resolve_media_file(song_dir, filename, roots)` probes each root in that order and returns the first file that exists, or `None`. The install `Songs` cannot be derived from the cache dir, so it comes from the persisted setting (§4, Q7). Resolution is per file, not per folder, because the engine's priority is per file — a split pack can take its banner from one root and its music from another, and the page must show the same files the game would. Where no root holds the file, the page shows the media it has and disables the folder and play buttons for what it does not.

Images start dependency-free: `PhotoImage` for PNG, a placeholder for anything else, with Pillow as a named later enhancement for JPEG backgrounds and smooth scaling — not a v1 dependency. Audio is staged last, and the recommendation there is pygame for the in-app preview (play from `SAMPLESTART` for `SAMPLELENGTH`, with Stop), imported lazily inside a small player seam so the page still opens without it; if pygame's offset playback does not verify on Windows, the fallback is the external player, which plays the whole song. The alternatives, and why they are not the recommendation: carrying nothing in the row and re-reading the cache file when the page opens avoids widening the snapshot, but it needs the cache file present at open time and re-parses on every open for data the parse already held; Pillow from the start buys JPEG and scaling a step earlier at the cost of a dependency the banner does not need; the external player as the only playback is the Python-only option and the simplest code, but it does not play the preview window, which is the feature; deferring playback entirely ships the page sooner but leaves Ian's sketched "play the preview from there" undone; resolving folders by guessing `<root>/Songs` then `<root>/AdditionalSongs` was the first draft's design and is wrong — it finds nothing for a library that lives entirely in an additional folder, which is the owner's own install.

Staging, in order: (1) parse the seven media tags into hidden row keys; (2) roots plus resolution plus Open song folder; (3) the page with images; (4) playback. Each stage is independently green; stages 1–2 are invisible on their own, stage 3 is the visible unit, stage 4 is where the pygame decision lands.

## 4. Recommended Design in Detail

The boundary is explicit. `library_sources.py` owns parsing the media tags and resolving media files — `song_roots(cache_dir)` and `resolve_media_file(song_dir, filename, roots)` — both Tk-free, both tested without a window. `song_page.py` owns display only: it is given the song and its already-resolved media and it calls back for everything else. The shell wires it: it reads the roots (from the `song_roots` setting, seeded by detection from `Preferences.ini`), resolves the song's media files through the helpers, and hands the page the record. The page must not reach into the filter, the loader, the snapshot store, or the settings; it must not import pygame at module top (lazy import inside the player seam, so a missing pygame degrades the Play button instead of breaking the page).

Constructor contract for the song page — geometry in, callbacks out, on the `data_paths_dialog.py` pattern:

1. `parent` — the window the page opens from.
2. `song` — title, artist, pack, and the song's charts: the list of rows sharing its `"Course path"`, each with difficulty, meter, BPM and scores, as the table already holds them.
3. `media` — the resolved media record: banner, background, jacket and CD-title image paths (or `None` where no root holds the file), the music path (or `None`), the music length, and the sample window (`SAMPLESTART`, `SAMPLELENGTH`). The shell builds this record with `resolve_media_file` before constructing the page; the page never resolves a path itself.
4. `on_play` / `on_stop` — callables the page invokes for preview playback; the app supplies the player.
5. `on_open_folder` — a callable the page invokes for the folder button.
6. `dpi_scale` — the display scale factor, as every dialog takes it.
7. `button_factory` — makes a themed button (`LibraryApp._button`), as every dialog takes it.

The legibility test, the project's standing guideline: a song page shows one song's media and charts and plays its preview; it is given the song's rows and its resolved media paths and calls back for play, stop, and open-folder. A reader can hold that sentence and then read the file.

What the page shows, top to bottom: the banner across the top (PNG via `PhotoImage`, integer subsample to fit; placeholder where the banner is missing or not PNG); title, artist and pack; background and jacket and CD title alongside; the music file with its length and sample window; the song's charts — all difficulties with meter, BPM and scores. Buttons: Play preview, Stop, Open song folder. Play is disabled when there is no music file or no player; the folder button is disabled when the folder is gone. The page opens at a default size from a new `SONG_PAGE_MIN_SIZE` in `theme.py` and does not persist its geometry in v1. The one new settings key is `song_roots`: the ordered list of song-folder roots, seeded at first run by detection (the `AdditionalSongFoldersWritable` entries from `Preferences.ini` plus the user-data `Songs`), user-editable, with a Detect button on the course builder's pattern (course:11.3) for a non-standard cache location. Double-click is the only new binding: single click, selection, column drag, sort and Ctrl+A are untouched.

## 5. What Does Not Change

One new settings key: `song_roots` (list of song-folder roots, §4). No snapshot schema bump (schema stays 4; old snapshots load, missing media keys mean "no media recorded"). No `HEADERS` change — the media fields are hidden row keys, never columns. No existing row field changes value. No change to table sorting, filtering, the distribution panel, the course builder, or the search language. `requirements.txt` is unchanged through stage 3; pygame enters it only at stage 4, and only if Q2 goes that way. The snapshot file format is unchanged. A double-click on a chart row is the only new input binding.

## 7. Open Questions for Reviewers

- **Q1. Images — dependency-free PNG first, Pillow later?** Recommendation: yes. The banner is PNG in the real cache and `PhotoImage` reads it with no dependency; Pillow buys JPEG backgrounds and smooth scaling as a later enhancement, not a v1 dependency. The cost is a placeholder for JPEG backgrounds in v1.
- **Q2. Audio — pygame in-app preview, external player, or defer?** Recommendation: pygame, staged last, with the external player as the fallback if offset playback does not verify on Windows. Pygame is the only option that plays the sample window in-app; the external player plays the whole song; deferring leaves the sketched playback undone.
- **Q3. Media carriage — hidden row keys, or re-read the cache file at open?** Recommendation: hidden row keys at parse time, on the "Score description" precedent. It needs no schema bump (snapshot validation requires only `HEADERS` plus `"Course path"`), and the page works from snapshot-restored rows. Re-reading avoids widening the snapshot but re-parses on every open and fails when the cache file is gone.
- **Q4. Entry — double-click only, or also a menu or keyboard route?** Recommendation: double-click only for v1, via the new `on_row_double_click` table input. A menu entry would help discoverability and keyboard users; if reviewers want it, it belongs in stage 3, not as a second entry invented later.
- **Q5. Geometry — persist the song page's size and position, or fixed default in v1?** Recommendation: fixed default, no geometry settings key (the one new key in this proposal is `song_roots`, Q7). The course builder and Advanced Search persist theirs; the song page can follow in a later step if the window earns it.
- **Q7. Roots — persist `song_roots` as a setting, or derive the roots on every launch?** Recommendation: persist, seeded by detection from `Preferences.ini`, on the course builder's precedent (course:11.3). Deriving on every launch cannot supply the install `Songs` root, which nothing in the app can find on its own, and re-reads `Preferences.ini` for data that changes only when the game is reconfigured. The cost is one new settings key and a Detect button for a non-standard cache location.
- **Q6. Review — Grok sole reviewer, or the full four-model panel?** Recommendation: Grok alone, continuing Ian's 2026-11-15 decision for the remaining 0010 steps — the pattern is settled (0009 dialog shape, 0010 staging) and the reviewable part is the six decisions above. The full panel, as on proposal PR #169, is the alternative if Ian wants independent eyes on the dependency calls.
