# Architecture

This is the map of the code for a reader who wants to change it. The user
guide stays in `README.md`.

## Launch

Run `launch.py` from the repository root (`python launch.py`). It is the
file you run: it imports `main` from
`itgmania_library.library_librarian` and calls it. The other 21 modules
live in the `itgmania_library` package and are imported by it (directly or
through each other), by their absolute package names
(`from itgmania_library.library_sources import ...`). `python -m
itgmania_library` from the repo root launches the app too, through the
package's `__main__.py`, and is the same entry point by another name.

## Layers

A module only imports modules in lower layers. The layering below was
measured from the import graph (no cycles) at main `5fc8d47` (v1.4.0), not
drawn from intent; it was extended with `library_fonts.py` at layer 0 in
the Proposal 0017 implementation, which the layer test verifies on every
run.

```
5  library_librarian.py — the shell (LibraryApp)
4  library_table.py
3  library_loader.py · library_stores.py · advanced_search.py
   distribution_panel.py · data_paths_dialog.py
2  library_filter.py · course_builder.py · library_sources.py
   library_dialog_query.py · library_distribution.py
   library_media.py · song_page.py
1  library_format.py · library_search.py · row_tints.py
   window_placement.py
0  library_constants.py · library_geometry.py · library_course.py · theme.py · library_fonts.py
```

Read top to bottom as "built from". The shell builds the UI components, the
components read the data modules, and the data modules depend only on each
other and on the standard library.

The table is enforced, not just measured: `LAYERS` in
`tests/test_layer_enforcement.py` holds the same numbers, and the suite
fails if a module has no layer, if a layer names a module that no longer
exists, or if any module imports a sibling that is not in a strictly lower
layer (same-layer imports included, in every import form). The same file
fails on an import cycle and on any change to the eight window modules that
import Tkinter. When it blocks an import, pass the dependency in or move the
shared piece down. Edit the diagram and `LAYERS` together whenever a module
is added, renamed or moves layer, and re-date the line above. The test does
not compare the diagram text with `LAYERS`, and it does not require a module
to sit at the lowest layer it could, so keeping the two in step stays a
manual check.

Two naming facts to know before you trust the prefixes:

- The `library_` prefix does **not** mean Tk-free. The ten Tk-free data
  modules are `library_constants`, `library_format`, `library_sources`,
  `library_geometry`, `library_course`, `library_search`,
  `library_dialog_query`, `library_stores`, `library_distribution` and
  `library_media`.
  `library_loader`, `library_filter` and `library_table` are UI components
  that carry the same prefix: the loader and the table import Tkinter, while
  the filter does not import it (it works on the widgets it is handed, so a
  Tk-free stand-in can drive it in tests). `window_placement` follows the
  filter's pattern one layer down: it is not a window, imports no Tkinter,
  and works on the parent window it is handed. Fourteen of the twenty-two
  modules import no Tkinter at all — the ten data modules above, plus
  `library_filter`, `window_placement`, `row_tints` and `theme` — so
  "Tk-free" and "data module" are not the same list, and the eight that do
  import Tkinter are exactly the window code plus the loader.
- The UI components without the prefix are `advanced_search`,
  `course_builder`, `data_paths_dialog`, `distribution_panel` and
  `song_page`; `row_tints`, `theme` and `window_placement` also lack the
  prefix but are shared foundations, not UI components.

## Kinds of modules

The layers above say what a module may import. They do not say what job a
module does, and the same kind of module sits at several layers: the
game-data kind spans layers 0 to 2, presentation spans layers 2 to 4. So
read the two views together — layers for the import direction, kinds for
the job. A module has exactly one kind; where a module sits between two
kinds, the call is recorded under "Between kinds" below, so the next reader
does not have to re-argue it.

Tk use is a third axis, separate from kind: most presentation modules import
Tkinter, most domain modules do not, and the loader and the filter are
Tk-adjacent without being presentation — the loader drives the status line
and the progress bar, the filter works on the widgets it is handed. The ten
Tk-free data modules are listed under "Layers" above.

| Kind | Modules | What it holds |
| --- | --- | --- |
| Shell | `library_librarian.py` | The window, the menu, the entry point: it builds every component and wires them together. |
| Presentation | `library_table.py`, `song_page.py`, `distribution_panel.py`, `course_builder.py`, `advanced_search.py`, `data_paths_dialog.py` | A window, a dialog, a panel, or a widget tree the user sees and touches; everything it needs arrives through its constructor. |
| Application services | `library_loader.py`, `library_filter.py` | A cross-cutting workflow or a piece of live UI state, run across several modules and reported to the window through callbacks and notifications. |
| Game-data domain | `library_sources.py`, `library_search.py`, `library_distribution.py`, `library_dialog_query.py`, `library_course.py`, `library_format.py`, `library_media.py` | Tk-free reading, interpreting, aggregating, formatting and resolving of ITGmania's own data — cache rows, Stats.xml scores, song folders, search text, `.crs` text. |
| Persistence | `library_stores.py` | The app's own files on disk: the snapshot, the refresh manifest, and the settings, with their validation, migration and atomic write. |
| Shared foundations | `library_constants.py`, `theme.py`, `row_tints.py`, `library_geometry.py`, `window_placement.py`, `library_fonts.py` | Small Tk-free vocabulary, appearance, geometry and font helpers many modules read and none of them owns a workflow. |

Module by module: `library_librarian.py` is the shell (it builds and wires everything, and `main()` is the entry point); `library_table.py` is presentation (it owns the Treeview, its columns, sort keys, selection and row insertion); `song_page.py` is presentation (one window for a song's media and charts); `distribution_panel.py` is presentation (the chart panel beside the table); `course_builder.py` is presentation (the Build-a-course dialog and its queue); `advanced_search.py` is presentation (the Advanced Search dialog); `data_paths_dialog.py` is presentation (the Data paths dialog); `library_loader.py` is an application service (the load/sync engine: scan and sync workers, result queue, generation counters); `library_filter.py` is an application service — the filter state store (it holds the rows and the five filter variables, decides which rows pass, and notifies its subscribers — see "How the pieces fit"); `library_sources.py` is game-data domain (it reads Stats.xml and the cache and joins the two); `library_search.py` is game-data domain (the search language); `library_distribution.py` is game-data domain (the meter, difficulty and BPM aggregation the panel draws); `library_dialog_query.py` is game-data domain (the Advanced Search dialog's query conversion, with no window of its own); `library_course.py` is game-data domain (the `.crs` text format); `library_format.py` is game-data domain (formatting and sort-key helpers); `library_media.py` is game-data domain (song-folder roots, media-file resolution, the song's charts and media record, and the preview-player seam); `library_stores.py` is persistence (the snapshot, manifest, and settings stores); `library_constants.py` is shared foundations (the shared column and grade tables); `theme.py` is shared foundations (every colour, font and fixed size the window uses); `row_tints.py` is shared foundations (the difficulty row tints, shared by the table and the course builder); `library_geometry.py` is shared foundations (window geometry and DPI helpers); `window_placement.py` is shared foundations (where a secondary window opens — it gathers the inputs for the pure opening-geometry decision, it is not a window); `library_fonts.py` is shared foundations (per-process loading of the bundled fonts — it registers them with the operating system for this process only and reports which families resolved; Proposal 0017).

### Between kinds

Four modules sit between kinds, and each call is settled here rather than left to guesswork. The loader (`library_loader.py`) looks like presentation — it imports Tkinter and drives the status variable, the progress bar and the Load button — but it owns no window and its job is a workflow spanning the sources, the stores and the threads, so it is an application service and the Tkinter use is its reporting surface. The stores (`library_stores.py`) look like domain — the snapshot store validates rows — but the validation serves a file the store owns, so it is persistence. The media module (`library_media.py`) looks like presentation — its whole purpose is serving the song page, and it carries the `SongPreviewPlayer` pygame-ce seam — but its bulk is Tk-free resolution of the game's folders and cache rows, and the shell holds the one player, so it is game-data domain; a reader who wants playback starts at the shell and then reads the player section here. The sources module (`library_sources.py`) looks like persistence — it reads files from disk — but it reads the game's files, read-only, and writes nothing, so it is game-data domain; the rule is that reading the game's files is domain and owning the app's files is persistence. Two more placements are worth naming so they are not misread: `window_placement.py` is foundations, not presentation, because it is not a window and imports no Tkinter; and `library_distribution.py` is domain, not presentation, because the chart arithmetic is pure and Tk-free while the Tk side is the panel.

## Rows, songs, and media

A row is one chart, and it is a plain Python dict — not a class or a dataclass. There is one row per chart block in a cache file, and a chart block that lacks `#STEPSTYPE` or `#DIFFICULTY` is dropped and counted in `skipped_blocks` instead of becoming a row. The dict has 52 keys: the 40 columns in `HEADERS` (`library_constants.py`, which is the authoritative column list) plus 12 hidden keys that are never columns. The columns are Title, Subtitle, Artist, Pack, Type, Difficulty, Meter, Time, BPM, Chart, Score, Grade, Best %, Plays, Last played, Peak NPS, Taps/Holds, Jumps, Holds, Rolls, Mines, Hands, Lifts, W1, W2, W3, W4, W5, Miss, Max combo, and the ten tech counts (Crossovers, HalfCrossovers, FullCrossovers, Footswitches, UpFootswitches, DownFootswitches, Sideswitches, Jacks, Brackets, Doublesteps). Every column belongs to exactly one group under View > Columns ("Song & chart", "Score", "Tap judgments", "Chart counts", "Tech counts"), and Subtitle is the one default-group column that starts hidden.

The hidden keys are `Course path`, `bpm_min`, `bpm_max`, `Score description`, `Music`, `SongMusic`, `Banner`, `Background`, `Jacket`, `CDTitle`, `SampleStart`, and `SampleLength`. `Course path` is the song's identity (see below). `bpm_min` and `bpm_max` are the numeric BPM range behind the `BPM` display string, and they are what the search and the distribution charts compare against — never the display string. `Score description` is the scoring key the sync reads back, so a sync looks up the same Stats.xml entry the parse did. The other eight are the raw media filenames from the cache: `Music` is the chart's effective `#MUSIC` (a chart-level override wins, otherwise the song's), `SongMusic` is the song's own `#MUSIC` carried on every chart row, and the rest are the song-level media and sample tags. Hidden keys travel with the row through the snapshot, but the CSV export writes only `HEADERS`, so they are dropped on export.

Value types are mixed, and missing values have no single marker: text fields are strings, `BPM` is a display string rather than a number, most counts and `Meter`, `Time`, and `Peak NPS` are floats, and a missing value reads as `""` in some fields and `0.0` in others (an unscored chart has an empty `Score`, `Grade`, `Best %`, and tap judgments, but a `Plays` of `0.0`). Code that reads rows is written to tolerate that mixture, so a new reader should not "fix" it into uniformity without checking the consumers.

A chart is identified for scoring by its normalized song path, its chart type, and its difficulty, all compared case-insensitively, plus the Edit description when there is one. The song path is the path below `Songs/` or `AdditionalSongs/` (so `Pack` is simply its first component), and it is normalized the same way on the cache side and the Stats.xml side. For an Edit chart the description is part of the key: `#DESCRIPTION` is the key, `#CHARTNAME` is only a fallback for older caches, and the parse carries the chosen description in `Score description` so the sync repeats the same lookup. An Edit chart with no description gets a merged fallback instead — the best score, the highest play count, and the latest last-played date across that song's Edit entries — because it cannot be matched to one described Stats entry. A song is identified by `Course path` alone: every row sharing a `Course path` is one of that song's charts. Title, Artist, and Pack are display fields, never keys. Note that a `.crs` course file can express less than a row knows: a `#SONG` line records only the course path and a difficulty word, not the chart type or which Edit, so the course builder flags entries that could mean two charts.

Rows are built fresh on every full load, in a background worker that reads Stats.xml once into an index and then parses each cache file. Only startup reads the snapshot (Load / refresh never does): a valid snapshot restores rows from disk instead of a scan, and a startup that finds no usable one leaves the table empty with a status line telling the user to click Load / refresh (or, when there is no snapshot yet, to choose File → Data paths… first) — the rebuild is manual, never automatic. The finished list is delivered on the main thread, the loader replaces its rows wholesale, and the filter holds that same list — it stores the list it is given, it does not copy it — so the table, the distribution panel, and the course builder all read the one list through the filter. A scores-only sync does not rebuild rows: it re-reads Stats.xml and rewrites the score fields of the rows already in memory, then re-saves the snapshot. After a sync the table refreshes with the selection preserved; after a load the dropdowns reset and the song page closes either way, so a stale page never shows old scores. Old rows are discarded by being replaced, and results from a superseded load or sync are dropped by a generation counter.

Rows are shared mutable dicts, but only the score fields may be rewritten, and only by the score merge. The single place that assigns into a row after creation rewrites exactly `Score`, `Grade`, `Best %`, `Plays`, `Last played`, the six tap judgments, and `Max combo`, blanking them when there is no Stats entry; it runs once per row during the parse and again per row during a sync, and the sync never adds or removes rows — a song added to the cache still needs a full refresh. Everything else about a row is read-only after the parse, and no code copies rows: the filter's filtered list, the song's chart list, and the opened-chart-first list are all new lists of the same dicts. That sharing is load-bearing: because the filter and the loader hold the same list, a sync's in-place rewrite is visible to the table without re-setting the rows, and a sync that built a fresh list would leave the filter showing old scores.

The snapshot is `library_cache.json`, owned by `SnapshotStore`, at schema version 6. Its payload is the schema version, the two source paths, `refreshed_at`, the scan counters, and the row dicts written verbatim as compact JSON, atomically. Reading it has five outcomes — missing, unreadable, invalid, paths mismatch, or loaded — and a snapshot that fails any check is discarded, never repaired. Row validation requires every `HEADERS` key plus `Course path`, and every value to be a JSON scalar; it does not require the hidden keys, so a snapshot missing `bpm_min` or `Score description` still loads, and the sync then falls back to the `Chart` field for the score lookup while a BPM search against such a row simply never matches.

Beside it sits `library_cache_manifest.json`, owned by `ManifestStore` (proposal 0018), at format version 1. Its payload is the two source paths, the Stats.xml mtime and size the scan recorded, and one record per cache file — name, mtime in nanoseconds, size, song directory, row count, skipped-blocks count — written as compact JSON, atomically, sorted by file name. Reading it has the same five outcomes as the snapshot, and a manifest that fails any check means a full parse, never a repair. The refresh worker uses it to decide, per file, whether to re-parse or reuse the snapshot's rows; validity is by coverage (the manifest's song directories exactly cover the snapshot's row groups), not timestamps, so a scores sync never invalidates it, and a changed Stats.xml re-derives scores over the reused rows instead of forcing a re-parse.

The media record is separate from the row, and it is the one data model in this area that is a real type: `SongMedia`, a frozen dataclass in `library_media.py`, built fresh every time the song page opens and never cached. Its nine fields are `banner`, `background`, `jacket`, `cd_title`, and `music` — each a path to a file that exists, or `None` where no root holds the file — plus `music_length`, `sample_start`, and `sample_length` in seconds (or `None`), and `folder`, the highest-priority root where the song's folder is a directory (or `None`). The record is assembled from the song's chart rows with the opened chart first: its music is the opened chart's effective `Music`, and the length and sample window are included only when that music is the song's own music, so a chart with its own `#MUSIC` override carries that file with no length and no sample window. Each image is resolved per file across the song-folder roots in priority order, accepting only the engine's extension allowlists, and the roots are derived from `Preferences.ini` and the cache directory on every open. Media inside Packages zips is out of scope for v1, so a song whose media lives only in a zip shows placeholders. The song page receives the record through `show(song, media)` together with a small dict of the song's title, artist, pack, and chart rows; it reads the images, the music path, the length and sample window, and the folder from the record, renders one line per chart row (type, difficulty, meter, BPM, and score), and holds the record only while the page is open.

## How the pieces fit

**The filter is the filter state store: it holds the rows and the criteria, decides which rows pass, and tells the table when something changed.** The loader hands the loaded rows to the filter; the table reads the rows through the filter; the main window subscribes its refresh to the filter's change notification. The filter owns the five filter variables, the search box and the three dropdowns it resets, the variable traces and the search debounce, and the batched update that turns one chart click into one refresh — but it does not own the Treeview, the stores, or the status line, and it never renders a row: the table owns the sort keys, the column order and widths, and the row tinting, and exposes the layout and the selected and library rows the main window reads back.

**Dialogs and the panel persist differently by design.** A dialog's geometry
is a value passed in and a callback reporting it back out, while the panel's
variables are shared objects, because the View menu and the settings save
both bind them directly.

**The shell is thin.** `LibraryApp` builds the components and wires them
together, then keeps only thin `load_data` / `sync_scores` delegation to the
loader. If a behaviour needs the window, it lives in a component; if it does
not need the window, it lives in a Tk-free data module with tests in `tests/`.

The filter, the table, the Data paths dialog, the song page and the distribution panel never write it. | Nothing. The next load or refresh rewrites it. |

Three splits deserve a sentence each, because they are the places a reader would otherwise guess wrong. The rows have two holders, not one: the loader owns the loaded list and the filter is the UI's single holder of the same list object, and the sync's in-place re-score is the invariant that keeps the two from drifting. The settings file has two owners as well: the store owns the file, the baseline and the write, while the shell owns which keys exist and when a save happens — and the table owns the layout values themselves, which the shell reads back through `layout_state()` because a sort or a layout reset rebinds them. And the media preview is split across the shell, the page and the player on purpose: the player knows nothing about length, so the page owns the stop timer; the shell owns the player, so the page can never outlive it; and the load path closes the page, so a stale page never plays old scores.

## Runtime walkthroughs

The sections above say what each piece holds and where it sits. The walkthroughs below say what actually happens, step by step, in the three flows a reader is most likely to trace: the app starting, the library loading, and a search query reaching the table. Each step names the module and function so the next reader can jump straight into the code.

### Startup

1. **The entry point.** `launch.py` imports `main` from `itgmania_library.library_librarian` and calls it (`library_librarian.py: main`). `main` declares DPI awareness on Windows (`library_geometry.py: declare_dpi_awareness`), then loads the bundled fonts (`library_fonts.py: load_fonts`) and switches the theme to the sets that loaded (`theme.py: apply_fonts`), then builds the `LibraryApp` on a fresh `tk.Tk` root (`library_librarian.py: main`).
2. **The app builds itself in a fixed order.** `LibraryApp.__init__` calls eight steps in turn: `_init_window` (the title, the DPI scale factor, the default `1500x850` size from `theme.py`, the minimum size, and the background), `_init_stores` (migrates the config dir once, builds the snapshot and settings stores, and loads the settings into `saved_settings`), `_init_variables` (creates the Tk variables for the library paths and the search/filter controls, seeded from the saved settings), `_declare_late_state` (declares as `None` every attribute a later step fills in), `_init_dialog` (builds the Data paths dialog, before the loader that drives it), `_style` (the ttk theme and the table and dropdown styling), `_build` (creates every component — the filter, the table, the distribution panel, the status label — wires them together, and builds the menu), and `_init_loader` (builds the loader last, reports any discarded settings, and starts the loader).
3. **Settings load.** `_init_stores` calls `SettingsStore.load` (`library_stores.py: SettingsStore.load`), which either returns the persisted settings or discards a broken file for defaults and remembers the failure on the store; the discarded-settings note is reported once the window is built, by `_report_discarded_settings` in `_init_loader` (`library_librarian.py: _report_discarded_settings`). The settings seed the path variables and filter controls in `_init_variables`, and the geometry attributes and table layout in `_build` (`library_librarian.py: _init_variables`, `_build`).
4. **Components wire up.** In `_build`, the app creates the filter, table and panel, and subscribes the table's refresh to the filter's change notification (`library_filter.py: subscribe`, `library_librarian.py: _build`). It also creates the single `SongPreviewPlayer` (`library_media.py: SongPreviewPlayer`). The loader is built after `_build`, in `_init_loader`, so the components exist before the loader that drives them.
5. **The main loop starts.** `main` calls `root.mainloop()`, which maps the root window onto the screen and enters the Tk event loop (`library_librarian.py: main`). The first screen to appear is the empty main window, not the data.
6. **The snapshot load starts 50 ms later.** `LibraryLoader.start` runs the root's `after(50, ...)` so that the window gets a chance to paint before the library arrives (`library_loader.py: start`). The delay is deliberate: reading and rendering a large saved library takes a moment, and doing it before the event loop starts would leave the user watching an unpainted window with no explanation. The loader also sets up a 75 ms poll (`library_loader.py: start`) that checks the workers' queue and reschedules itself for the life of the window.
7. **When the timer fires.** `_load_initial_snapshot` (`library_loader.py: _load_initial_snapshot`) runs `load_cached_data`, which either restores the snapshot (and then appends the moved-paths and newer-Stats.xml notes) or sets the failure status and calls `on_nothing_loaded`, which only repaints the empty table (`library_librarian.py: _on_nothing_loaded`). It then stops the progress bar, re-appends any discarded-settings note, and calls `dialog.maybe_show_first_run` (`data_paths_dialog.py: maybe_show_first_run`): when no snapshot was restored and the cache folder or Stats.xml is not usable, the Data paths dialog opens once for the session, with a dead-paths note if saved settings had path keys and a first-run note otherwise. A damaged or mismatched snapshot with usable paths opens no dialog, only the status line. A Load / refresh pressed before the timer fires supersedes the restore (`_load_generation` is already non-zero).

### Data load

1. **Load versus sync.** Two different entry points. `LibraryLoader.load_data` (`library_loader.py: load_data`) starts a load: scan the cache directory, re-parse the files that changed and reuse the snapshot's rows for the rest (proposal 0018), join Stats.xml scores, and save a new snapshot and manifest. `LibraryLoader.sync_scores` (`library_loader.py: sync_scores`) starts a scores-only sync: re-read Stats.xml and rewrite the score fields of the rows already in memory, then re-save the snapshot. Both run in a background thread; the work inside them is otherwise identical in shape.
2. **The background worker does the reading.** The loader's `_load_worker` (`library_loader.py: _load_worker`) reads Stats.xml once into an index (`library_sources.py: stats_index`), builds the once-per-run Edit fallback index, then walks the cache folder once with `os.scandir` and decides per file: an unchanged file whose song directory is claimed by no other file reuses the snapshot's rows for that song, and every other file is passed to `parse_cache_file` (`library_sources.py: parse_cache_file`) and its fresh rows collected. A changed Stats.xml re-derives scores over all rows with `merge_scores` instead of forcing a re-parse. A file that cannot be read or parsed at all is skipped and counted ("skipped N unreadable") and is not recorded in the manifest, so it is retried on every refresh; a chart block that lacks `#STEPSTYPE` or `#DIFFICULTY` is dropped and counted in `skipped_blocks` instead of becoming a row; a file with no charts is counted separately. This worker belongs to Load / refresh only. At startup, `load_cached_data` (`library_loader.py: load_cached_data`) instead restores rows from a valid snapshot without parsing anything, and when there is no usable snapshot it leaves the table empty and asks the user to click Load / refresh (see the snapshot paragraph in "Rows, songs, and media").
3. **The main thread receives the result.** The finished rows are delivered on the main thread through `_loaded` (`library_loader.py: _loaded`), which replaces `self.rows` wholesale and hands the list to the app through the `on_library_changed` callback (`library_librarian.py: _on_library_changed`). The filter holds that same list — `set_rows` stores the list it is given, it does not copy it (`library_filter.py: set_rows`).
4. **The filter tells the table.** The shell's `_on_library_changed` calls `filter.set_rows` inside `filter.batch()` (`library_filter.py: batch`, `library_librarian.py: _on_library_changed`), so the table refreshes exactly once for the whole load.
5. **The table renders by diff, in batches.** The table's `refresh_table` (`library_table.py: refresh_table`) asks the filter for the rows that pass the current filters (`library_filter.py: filter_rows`), then makes the Treeview show exactly those rows by changing only what differs from what is already showing (proposal 0019): rows are identified by their chart key (`Course path`, `Type`, `Difficulty`, `Chart`), deletes and in-place value updates run synchronously, and inserts and moves run in time-boxed batches (`library_table.py: _apply_diff_batch`): each batch places rows until a 12 ms deadline (`library_table.py: ROW_INSERT_BUDGET_SECONDS = 0.012`), always at least one row so the loop cannot stall, then schedules the next batch 1 ms later, so a large library streams in without freezing the window. On the first load the tree starts empty, so the diff is a full insert and still streams in through the existing inserter (`library_table.py: _insert_batch`). Selection is carried by chart key, not by row identity, and the display values a row was last shown with are kept per item, so a sync that re-scores cells in place is detected even though the row dicts are the same objects the merge mutated. A large placement — more than 50 rows to place, inserts plus displaced rows (`library_table.py: SET_CHILDREN_PLACEMENT_THRESHOLD`) — goes through one `set_children` call instead of per-item `tree.index`/`tree.move` and insert-at-index, which are O(n²) and slower than the rebuild at library size; a handful of placements still go one by one. The trigger counts inserts as well as displaced rows because a filter widen inserts thousands of rows while displacing no survivor, and it is where the insert arm is slowest (§6: a widen took 358 s before this, against ~15 s for a rebuild). On a large placement new rows are appended at the end and the single `set_children` puts them in place; the order list mirrors the tree throughout (a new row is appended to both), so a refresh that supersedes a half-finished walk still reads a true tree order. The order list is rebuilt in one pass from the survivors after the delete loop, never edited key by key — removing each deleted key from the list is O(n) per key, and a narrow that drops 31,591 rows spent 10 s on that alone. The chart key is built once per row dict per refresh and the later lookups are cache hits: the diff asks for the same row's key a dozen times per refresh (§6 profile: 508,500 calls for 42,375 rows on a Title click, a fifth of the click), and the cache lives only for its refresh, so a freed row dict's id cannot return a stale key. Selection is carried by exact item, never expanded across a colliding key: a block re-insert destroys the selected item's identity, so the selection drops for that key instead of landing on every row that shares it. The saved display tuple does not know about the white tag the selection handler writes directly onto the tree item, so the update rewrites every item the tint tracker or the selection touches even when its saved tuple matches — otherwise a refresh that clears the selection would leave the row white. And a refresh with nothing to insert or move shows no "Loading …" progress text: the walk still visits every position, but the count label stays on the settled count.
6. **The status line explains the result.** The loader's `_loaded` (`library_loader.py: _loaded`) reports the result to the status line (`library_librarian.py: status`): after a scan, the load summary — how many files were scanned, rows parsed, files skipped, files with no charts, blocks dropped — plus a "Snapshot refreshed" or "Local snapshot not saved" suffix; on a manifest-assisted refresh where at least one file was reused, the base segment instead names the re-parsed count ("Scanned N files · re-parsed K · M charts in total"), and a full parse keeps the old text; after a snapshot restore, "Showing saved library snapshot · N charts · last refreshed …"; and a hint to select the flat Cache/Songs folder when a scan finds no files. Two extra reports ride along after a successful snapshot restore — they run in `load_cached_data`, not in `_loaded`: a moved source path, which says the saved cache folder or Stats.xml no longer exists and points at File → Data paths… (it names the missing side; it does not find a replacement, `library_loader.py: _report_moved_source_paths`), and a newer Stats.xml ("Stats.xml is newer than the saved library. Choose File → Sync scores from Stats.xml to refresh scores.", `library_loader.py: _report_newer_stats_file`).
7. **A scores-only sync is the same flow, shorter.** The sync worker (`library_loader.py: _sync_scores_worker`) re-reads Stats.xml, calls `merge_scores` (`library_sources.py: merge_scores`) over the rows already in memory, and re-saves the snapshot with the merged rows; the in-memory list object is the same one before and after. After a sync the table is refreshed with the selection preserved; after a load the dropdowns reset, the course builder is told the library changed, and the song page is closed either way so a stale page never shows old scores (`library_librarian.py: _on_library_changed`). Old rows are discarded simply by being replaced — there is no disposal step — and results from a superseded load or sync are dropped by a generation counter (`library_loader.py: _load_generation`, `_load_is_stale`, `_loaded`).
8. **A stale snapshot is never a silent failure.** If the snapshot's schema version does not match, or a row fails validation, the snapshot is discarded and the app leaves the table empty with a status line telling the user to click Load / refresh to rebuild it (`library_loader.py: load_cached_data`). If the paths in the snapshot no longer match the loaded library, the snapshot is discarded and the app reports the mismatch. The snapshot's five-branch read — missing, unreadable, invalid, paths mismatch, or loaded — is covered in "Rows, songs, and media".

### Search

1. **The user types.** The search entry is a Tk variable (`library_librarian.py: search_var`), created in `_init_variables` (`library_librarian.py: _init_variables`) and bound to the search box (`library_librarian.py: _build`).
2. **The filter watches the variable.** The filter's `__init__` (`library_filter.py: __init__`) installs traces on the five filter variables — search, pack, type, difficulty, scored — so a change to any of them calls `_refresh_unless_batching` (`library_filter.py: _refresh_unless_batching`), which refreshes the table at once unless the filter is inside a batch.
3. **Search keystrokes are debounced.** A search keystroke does not refresh at once: it schedules a refresh 200 ms after the last keystroke (`library_filter.py: SEARCH_DEBOUNCE_MS = 200`, `_schedule_search_refresh`), so typing a six-character query does not rebuild the table six times. The pending refresh is cancelled and re-scheduled on each keystroke (`library_filter.py: _schedule_search_refresh`).
4. **The query is parsed.** The search text is parsed by `parse_search_query` (`library_search.py: parse_search_query`), which splits the text into free-text terms and field directives (`type:`, `meter:`, `bpm:`, `time:`, `grade:`, `score:`, `percent:`, `plays:`, `peak_nps:`, `taps:`, `jumps:`, `holds:`, `rolls:`, `mines:`, `hands:`, `lifts:`, and the ten tech counts). A free-text term matches across Title, Subtitle, Artist, Pack, Chart, Type, and Difficulty (`library_search.py: match_chart_query`). The field directives cover meter (`Meter`), BPM (the hidden `bpm_min`/`bpm_max` range, by overlap — not the `BPM` display string), time (`Time`), title, artist, pack, chart, difficulty, type, grade (ranked through `GRADE_RANK`), score (`Score`), percent (`Best %`), plays (`Plays`), peak NPS (`Peak NPS`), the radar counts (`Taps/Holds`, `Jumps`, `Holds`, `Rolls`, `Mines`, `Hands`, `Lifts`), and all ten tech counts (`library_search.py: SEARCH_FIELD_ALIASES`, `NUMERIC_SEARCH_FIELDS`, `match_chart_query`, `_compare_bpm_bound`).
5. **The filter decides which rows pass.** `filter_rows` (`library_filter.py: filter_rows`) applies the pack, type, difficulty, scored and search criteria, parsing the search text through `parse_search_query` and matching through `match_chart_query`, and `ignore_metric` leaves out one chart's own filter so a distribution chart keeps showing every bar after a click. The table calls it on every refresh (`library_table.py: refresh_table`, `visible = self._filter.filter_rows()`), and the distribution panel receives it as a callable (`filter_rows=self._filter.filter_rows`) and calls it with `ignore_metric` (`library_librarian.py: _build`, `DistributionPanel(...)`; `distribution_panel.py`, row-pull method).
6. **The table re-renders.** The table's `refresh_table` (`library_table.py: refresh_table`) calls `filter_rows` and diffs the passing rows against the Treeview (see Data load, step 5 for the batching): unchanged rows stay where they are, so a sort click moves rows instead of re-inserting them and a filter change keeps the surviving items. The row count label updates, and the distribution panel re-aggregates its charts from the same filtered rows (`library_distribution.py`, `distribution_panel.py`).
7. **A chart click is one refresh, not two.** `apply_chart_filter` (`library_filter.py: apply_chart_filter`) sets two variables at once — the difficulty and the search text — inside a batch (`library_filter.py: batch`), so the table rebuilds once, not twice. `batch()` counts nesting depth so one chart click that sets two variables rebuilds the table once (`library_filter.py: batch`).

## External boundaries and failure handling

The app reads files it does not own — the game's song cache, the player's scores, and the song folders — and writes only its own snapshot, its own settings, and course files the user asks for. It never edits the game's files. `README.md` tells the user what happens when those files are broken; this section tells the next person changing the code where each boundary lives, what can go wrong there, and which failures the app treats as fatal, which it recovers from, and which it refuses outright.

### Where the app touches the outside world

**The song cache** is a flat folder of cache files (`Cache/Songs`, not the `Songs/Pack/Song` tree), read by `library_sources.py` (`parse_cache_file`) under the scan worker in `library_loader.py`. Each file is UTF-8 simfile text: song tags, then one `#NOTEDATA` block per chart. A chart needs `#STEPSTYPE` and `#DIFFICULTY` to appear; the media tags (`#MUSIC`, `#BANNER`, `#BACKGROUND`, `#JACKET`, `#CDTITLE`, `#SAMPLESTART`, `#SAMPLELENGTH`) ride along as hidden row keys, and a chart-level `#MUSIC` wins over the song's. The cache is the only place chart data comes from — the app never reads the song folders for chart data.

**The player scores** are one file, `Stats.xml`, read by `library_sources.py` (`stats_index`) and joined to the cached charts by normalised song directory, steps type and difficulty, with Edit charts matched by description as well. Scores are read-only in both directions: the app never writes `Stats.xml`, and a scores-only sync (`library_loader.py`, `sync_scores`) re-reads it and refreshes just the score columns of rows that already exist — a song added to the cache still needs a full load, because there is no row to merge into.

**The snapshot** is `library_cache.json` beside the settings file, owned by `library_stores.py` (`SnapshotStore`, schema version 6 at v1.4.0). It is a cache of the parse, not a source of truth: it stores the rows, the scan's summary counters, and the two source paths it was built from. Old schemas are never migrated — a snapshot whose version does not match is discarded, and rebuilt the next time the user loads, which is how the Edit-description fix (version 4) and the media keys (versions 5 and 6) shipped.

**The settings** are `settings.json` in the same folder, owned by `library_stores.py` (`SettingsStore`) and validated where each key is used in `library_librarian.py`. There is no version field, so there is nothing to migrate: the file holds the two data paths, the filter selections, the column order, visibility and widths, the sort keys, the distribution panel state, and the remembered window geometries, and a key that is missing or invalid simply falls back to its default. Both files are written atomically, through a temp file moved into place with `os.replace`, so a crash mid-write cannot leave a half-written file.

**Course files** are `.CRS` text, owned by `library_course.py` (formatting, parsing, validation) and driven by `course_builder.py`. A new course is a `#COURSE:title;` line followed by one `#SONG:path:difficulty:;` line per queued chart. Appending preserves the existing file's bytes exactly, including its newline style, and only adds lines. A `.CRS` line records the song and a difficulty word — not the chart type, and not which Edit chart — which is why the builder warns about entries the line cannot pin to one chart instead of silently writing an ambiguous one.

**Song media** is resolved by `library_media.py` and shown by `song_page.py`. The song-folder roots are derived from `Preferences.ini` and the cache dir on every page open and never persisted, in mount order with later mounts outranking earlier ones. Resolution is per file, first root wins, and a filename from cache text must be song-relative under the pack folder and inside the engine's extension allowlist (images `.png` `.jpg` `.jpeg` `.gif` `.bmp`, audio `.ogg` `.oga` `.mp3` `.wav`) or it reads as not found. Media inside Packages zips is out of scope for v1 and shows placeholders. The page itself only displays PNG images — a JPEG background resolves fine and still shows the placeholder — and preview playback goes through the `pygame-ce` mixer, which is optional: without it Play is disabled and everything else works.

**The OS window system** is touched in exactly three places across two modules: the work-area lookup through `ctypes` (`work_area_of`, Windows only, used by `window_placement.py`) and the DPI-awareness declaration (`declare_dpi_awareness`, before the first window exists), both in `library_geometry.py`, and the font registration (`load_fonts` in `library_fonts.py`, Windows only, also before the first window exists). Everything else about windows — parsing a saved geometry, scaling pixels, deciding where a window opens — is pure arithmetic in `library_geometry.py` and `window_placement.py`, which is why it is testable without a display.

### How failures are handled

**Fatal to the operation.** A malformed or unreadable `Stats.xml` stops the whole load or sync with an error box, because scores join to every row and there is no partial score set worth keeping. Invalid data paths when Load / refresh or Sync is pressed open the Data paths dialog instead of an error box, because the fix is in the dialog (at startup the same dialog opens through the first-run check, described under Startup). An unreadable cache folder also ends in an error box. These are the input failures that stop everything.

**Recoverable, and counted.** A sync whose `Stats.xml` changed while it was running still applies its merged scores in memory and refreshes the table, but skips the snapshot write and says "Local snapshot not saved: Stats.xml changed during the sync. Sync again for current scores."; because the snapshot's stamp is left behind, the next startup shows the newer-Stats.xml hint. One bad cache file never kills a load: the scan worker catches any failure parsing a single file, skips it, and counts it in the load summary ("skipped N unreadable"), alongside files with no charts and chart blocks skipped for missing metadata. The same habit runs through the values: a non-finite or missing tempo reads as a blank BPM cell, a duration over 99:59:59 reads as blank, a tag value ending in a stray backslash is dropped and its callers fall back, and a missing or non-PNG media file shows a placeholder. A song whose folder is under no known root has no folder and no media, never a crash, and the page says so with the folder button disabled. A window whose saved geometry no longer parses, or whose monitor has been unplugged, opens centred instead; a window that would run under the taskbar or past the screen edge is shifted back on screen, and one taller than the usable screen is shortened to fit, floored at its own minimum size. Off Windows the work-area lookup returns nothing and the caller falls back to the virtual desktop, and a DPI probe that reads nonsense is treated as a scale factor of 1.0.

**Refused, changing nothing.** Two guards refuse an operation rather than let it silently destroy good data. A sync refuses a `Stats.xml` with no scores at all, or with scores for none of this library's songs — merging either would blank every score and report success. Appending to a course that ends with `#MODS` or `#GAINSECONDS` after its last entry is refused, because the directive could change what the appended entries mean in the game, and the file is left untouched. The course builder's other warnings work the same way: mixed chart types and ambiguous entries are ask-first warnings, and declining abandons the save.

**Tolerated corruption, and its limit.** The files the app reads are written by another program and sometimes edited by hand, so the app tolerates a bad value inside a well-shaped file: mis-encoded cache text, missing tags, non-numeric numbers, scalar mistypes in a snapshot row, a non-string score description, wrong types and out-of-range values in individual settings keys. What it does not tolerate is a bad shape: a snapshot row that is not a dict, a row missing a column, a row holding a list or dict, a wrong schema version, or a settings file that is not a JSON object each fail the whole file, and the user is told to rebuild it or run on defaults. A bad value is tolerated; a bad shape is not.

**Defensive patterns to preserve.** Four recur across the boundaries. Numbers that reach the screen or the speakers pass through helpers that return a default or a blank instead of raising (`number`, `parse_bpms`, `format_duration` in `library_format.py`, `_finite_float` in `library_media.py`). Writes are atomic with a stale-baseline retry, so a failed settings save is retried on the next gesture rather than lost. The loader guards concurrency with generation counters that drop results from superseded scans and syncs, a lock that serialises the generation check with the snapshot write so an older scan cannot overwrite a newer snapshot, and a one-way guard between a scan and a sync: a sync refuses to start while a scan or another sync is running, while a Load started during a sync supersedes it by generation. And media paths are sandboxed: a filename from cache text can never open an arbitrary file, because it must resolve lexically under the pack folder and inside the extension allowlist or it reads as not found.

## Component construction

Each component is built by the main window with the few things it needs.

- **Build-a-course dialog** (`course_builder.py`): its parent window, the
  status variable, the button factory, a way to read the table's selected
  rows, a way to read every row in the library, the remembered window
  geometry, a callback that reports the geometry when the window closes, and
  the display scale factor.
- **Advanced Search dialog** (`advanced_search.py`): its parent window, the
  three widget factories, the search variable it edits, the remembered window
  geometry, a callback that reports the geometry when the window closes, and
  the display scale factor.
- **Distribution panel** (`distribution_panel.py`): the button factory, the
  four variables it shares with the window (the search and difficulty
  variables, its show/hide variable, and its metric selector), a way to pull
  rows when the chart's own metric is the active filter, a callback that
  applies a chart click or Clear as one batched filter change, the settings
  save, and the display scale factor.
- **Data paths dialog** (`data_paths_dialog.py`): its parent window, the two
  path variables it edits, a zero-argument load callback, the settings save,
  the entry and button factories, the display scale factor, and a callable
  that reports whether the paths match the loaded snapshot.
- **Song page** (`song_page.py`): its parent window, the play and stop
  callbacks (None when pygame-ce is not installed, which is how the page
  knows to disable Play), a callback that opens the song folder (None off
  Windows, where `os.startfile` does not exist), the display scale factor,
  the button factory, and two optional inputs for the place it was last
  moved or resized to: the saved geometry (`"WxH+X+Y"` after a resize,
  `"+X+Y"` after a move alone) and a callback that reports a new one. It
  owns the window, built once and re-raised by
  `show()`; the shell holds the media record and the preview player, which
  reach the page through `show()` and the play and stop callbacks.
- **Load/sync engine** (`library_loader.py`): the snapshot store, the two
  path variables, the status variable, the progress bar, the Load button, a
  callable that enables or disables File → Sync scores, the callbacks that
  report a finished load or sync and a load that found nothing, the Data
  paths dialog, the settings save, the root window, a callback that reports
  discarded settings, and whether saved settings contained path keys. It owns
  the loaded rows, the snapshot-summary counters, the scan/sync workers, the
  result queue, and the generation counters.
- **Filter state store** (`library_filter.py`): the five filter variables, the
  search entry, the three dropdown widgets, and the root window. It owns the
  rows it filters, the variable traces, and the search debounce.
- **Song table** (`library_table.py`): the table frame, the filter, the
  display scale factor, the column and group visibility objects the View menu
  binds, the saved column order, widths, and sort keys, the count label, the
  settings save, and a callable that pushes the visible rows to the
  distribution panel.
