## What this is

There is one user today, so this document exists to keep the work coherent, not to promise anything to anyone. It records where the app is headed, what it will not do, and which decisions are settled — so the next proposal can be written against a known direction instead of discovering the direction mid-review.

Proposal 0016 is why this document exists. It had to amend Proposal 0013 in three places (session-only sizing, no new module, no new settings key) and Proposal 0003 in one (session-only geometry), because those proposals were written as if the surrounding design were settled and it was not. The amendments were recorded, so the system worked — but late, and at the cost of a review cycle spent finding them. A proposal that overturns this document says so in its §5, the same way 0016 did for 0013. This document is not law; it is the thing a departure has to name.

It is written at the level of direction and boundaries, not design. It says "windows share one placement rule"; it does not say how the helper is constructed. A line in this document that names a design is a line that will have to be fought later, and should be challenged when it is written.

## Boundaries — what the app will not do

- **It stays read-only on the Songs tree through the read-only themes (1–4).** It reads the cache and Stats.xml and never touches the game folders. That is a deliberate design choice, not a missing feature. The one existing exception is course files: the course builder already writes `.crs` files, so library writing is not an absolute about-face — it is a later theme (theme 5), not a reversal. Cache cleanup splits the same way: the read-only variant — scan the cache against the real Song and Course folders and log what no longer exists — is a candidate inside the read-only themes, and the removal step waits for theme 5 and its proposal.
- **No download, update, or discovery integration.** Finding and installing packs belongs to other tools.
- **Windows-first, for any Windows ITGmania user.** Other platforms are not a goal; the narrowest scope is any Windows ITGmania user, not one person's library — nothing is kludged to the owner's setup, and the clean Python repo stays portable.

## Themes

Undated, in the order they will be worked. A theme is a paragraph, not a plan; the proposals inside it still do the designing.

**1. Unified windows — complete (Proposal 0016; v1.4.0 shipped 2026-11-20, closes #103, closed).** One placement rule shared by the song page and the dialogs: windows center over the main window unless deliberately moved, and a deliberate move or resize is remembered. Four PRs: extract the rule, center through the helper, save only on a deliberate move or resize, the song page remembers. Shipped as v1.4.0.

**Immediate next step: the font update — scoped, not a theme.** Barlow Condensed for all body and UI text, Wendy on four title labels only — the strings the app controls (main app title, About dialog title, Advanced Search heading, "Build a new course" heading). Barlow was picked blind over Miso in a mockup comparison (2026-11-22); the song-page title stays Barlow, because Wendy on user data would need a controlled fallback for accented titles and the amendment dropped that whole question. Scope: `docs/fonts-barlow-wendy-scope.md`. A short proposal first (new font-loader module, bundle-plus-per-process-load), then one implementation PR; the Windows smoke check is the owner's, since the loading path is Windows-only. It sits ahead of theme 2 because it is one scoped update, not a theme, and it is ready to write.

**Next after the font update: faster refresh — scoped, not a theme.** The refresh is measured now, not guessed: a warm Load / refresh is ~40 s end to end (~26–29 s parsing the cache files, 14 s inserting the rows), a cold one 106 s, most of the cold time being disk reads. The work, in the order the measurements dictate: P1 first, a manifest-based incremental refresh — a persisted record of each cache file's mtime and size, so a warm refresh re-parses only changed files and the worker drops to ~1 s (proposal first: a new persisted format with invalidation rules; the manifest's walk is the same walk the read-only cache-cleanup scan needs, so it leaves that candidate's ground clear). Then P5, chunked result streaming, which attacks the 14 s insert — earlier first paint is certain, a total-time reduction is the open question. Then P2, process-pool parsing, for the full-parse case (many files changed), where the parse is still ~29 s single-threaded on an 8-core machine. P3 and P4 are dead by measurement (Stats.xml 0.05 s, discovery 0.08 s). All three come from DeepSeek's 2026-11-12 load-efficiency review (`docs/research/deepseek-load-efficiency-review.md`), verified against the owner's real numbers 2026-11-22 (7,499 files, 42,375 rows; timing script `tools/time_refresh_parse.py`).

**2. A pack and series view — proposed.** **Owner decides:** scope, but the order is settled: this is the next theme after the immediate steps above, because it is a view over data the app mostly has rather than a new signal to invent. Everything in the app is chart-centric today; a large collection wants pack stats and series awareness. A Series is a named bundle of packs: a pack joins one by having a `Series=` line in its Pack.ini, in the root of the pack folder. The proposal for this theme answers where that metadata comes from — the cache carries no Series, so the app reads Pack.ini per pack folder (still read-only, but a new read alongside cache and Stats.xml) — and whether series banners are shown, under the game's rules (the first pack in byte order whose SeriesBanner resolves wins, else the alphabetically first pack's banner). It is a v1.3.0 engine feature, so the view is defined by the files, not by whether the game in use honors it. Verified 2026-11-22 against the v1.3.0 engine source (Claude's report: `docs/research/pack_series_view_research.md`): a Pack.ini is ignored entirely unless its `[Group]` section carries a non-empty `Version=`; Series text is byte-exact, so case variants are different series; a SeriesBanner "resolves" when a directory listing finds an entry by that name, file or folder, with no image check; a one-pack series still gets a parent row in v1.3.0. The read is a separate step after the scan, not snapshotted, so no schema change, and the same read yields DisplayTitle and SortTitle for free. The proposal's biggest question, the root gap, is answered by the owner's direction (2026-11-22): locate the install Songs folder by finding `ITGmania.exe` under `Program/` and taking `Songs/` beside it — the two are siblings at the install root — with a file dialog as the fallback when the exe is not found. The proposal still has to say where the search looks; the found path lives in settings, alongside the other paths, which is a new settings key.

**3. Scores, profiles, and the song page — proposed.** **Owner decides:** the order inside the theme, but the theme itself is the player-facing half of the scores the app already reads: switching between profiles (each profile has its own Stats.xml — and its own favorites), reading the machine's high scores, showing favorites, and rebuilding the song page so each chart shows Grade and Best % for the loaded profile and for the machine. The order follows the dependencies: profile switching first, since favorites are per-profile (each profile has its own Stats.xml and its own favorites.txt); the machine read next — its format is now settled (Save/MachineProfile/Stats.xml, same shape as the player file, readable with the existing stats_index(); only confirmation on the real file remains) — and it does not depend on profile switching, since the machine file is shared across profiles, so its position in the order is a sequencing choice, not a dependency; the dance-type labels next, since the song page's Type column needs them; favorites next (issue #258 — one read of the profile's `favorites.txt`, a column and a filter); the song page overhaul last (issue #259 — an aligned grid of labels, charts sorted by dance type then difficulty), since it consumes the labels and the machine columns; song-page Previous/Next navigation by song in table order sits with the overhaul as a small issue of its own (issue #263); the distribution panel's boundary unification comes just before the multi-select exploration — the panel is the other holder of the filter variables, and unifying its read path to getter callbacks first (liveness preserved, since the panel's inputs stream in) keeps the multi-select work from having to unwind the panel when the filter representation changes; the multi-select exploration for the library page's three dropdowns closes the theme, since finding the charts is part of showing them. GrooveStats read-only display is a candidate inside this theme (Grok, 2026-11-22, verified against the v1.3.0 engine source, the notes' cache spec, and Simply Love v5.9.0; report: `docs/research/groovestats-readonly-hash-research-brief.md`): the cache already carries the 16-character chart hash per chart, so no hash reimplementation is needed — but it needs a proposal (snapshot schema, network layer, UI placement) and GrooveStats contacted first, and the tags are confirmed on the owner's real cache files (Butterfly, 2026-11-22: `#GROOVESTATSHASH:1ef26ceecfea0c2b;` + `#GROOVESTATSHASHVERSION:3;`, after `#NOTEANNOTATIONS`, before `#STEPFILENAME`). The #STEPSTYPE survey (Grok, 2026-11-22, verified against the v1.3.0 engine source; report: `docs/research/STEPSTYPE-display-labels-research.md`) found 18 values the engine recognizes — six dance, five pump, six techno, one lights — with kb7, ez2, and para absent; an unrecognized value stays Invalid and is never defaulted to dance-single, and the label mapping is display-only, the raw value staying in the Stats join and course files. The proposed non-dance labels (Pump Single, Techno Single 4, Lights) are the owner's call, and hiding non-dance rows likely needs a short proposal. Favorites also answers part of the playlists question below: a favorite is a list that lives as a file the game reads, not in the app. The Playlists folder, same format, is the follow-on, and the read integration is settled: a playlist dropdown filter in the filter row (its values read from the folder, so it tracks the open set), with membership shown on the song page — a column per playlist does not scale, since the set is open, while Favorites keeps its column because it is one set. Creating playlists is not here; that is library writing, theme 5.

**4. "Courses and lists" — proposed.** **Owner decides:** whether this theme exists after the scores theme. The course builder today is bare-bones: a queue of concrete charts that writes `#COURSE` plus one `#SONG:path:difficulty:;` line per chart and appends to existing files. The course-builder survey (Grok, 2026-11-22, verified against the v1.3.0 engine source and the notes' course format reference; report: `docs/research/course-builder-research-report.md`) found the engine honors far more than the builder writes: course-level `#BANNER`, `#LIVES` (battery, `max(n,0)`), `#GAINSECONDS` (sticky across every later entry), `#REPEAT` (endless when the value contains "yes"), `#METER` (Regular/Difficult names only — Medium/Hard are logged and skipped), and per-entry `#SONG` third-field keywords (`showcourse`, `noshowcourse`, `nodifficult`, `awardN`), plus `#SONGSELECT` criteria courses (TITLE, GROUP — case-sensitive — ARTIST, GENRE, DIFFICULTY, METER, BPMRANGE, DURATION, SORT, GAINLIVES, GAINSECONDS, MODS) and timed `#MODS` in `KEY=VALUE` form only (the colon-separated forms in the engine's own doc produce zero attacks, silently). A `#SONG` line stores only path and difficulty, and the game picks one matching chart at random — no chart-type preference — which is what the builder's ambiguity warning is about. The work, in dependency order: queue helpers and validation preview first (dialog-internal, no proposal); open-and-edit of existing courses with unknown directives preserved verbatim on rewrite; course-level metadata; per-entry settings; course management (a courses directory is a new settings key, so a proposal); queue persistence (an owner behaviour call, not a research finding). Playlists no longer sit here: their read side is in theme 3 and creation is library writing, theme 5. A Simply Love follow-up (Grok, 2026-11-22, verified against v5.9.0 @ dd06138; report: `docs/research/simply-love-courses-research-brief.md`) found the theme adds no second contract: it reads the engine's Course/Trail objects, shows banner, title, entry count, length, and meter, records description/scripter/translit in its SL-Scores JSON, and shows ?????????? for unresolved entries — so the builder writes engine tags only, and validation preview is where an unresolvable entry gets caught. Open issues are #258 (favorites), #259 (song page overhaul), #261 (the `library_media` import-surface pin), #262 (machine high scores), and #263 (song-page Previous/Next navigation); theme 1 is complete and #103 is closed.

**5. Library writing — proposed, later.** **Owner decides:** this comes after the read-only themes (1–4), and it is the most dangerous feature domain the app could take on, so the terrain gets scouted very clearly before anything is built — a proposal first, not an issue. It is not an absolute about-face: the course builder already writes `.crs` files, so the app writes to the game folders in one place today. What changes is the blast radius: anything here can damage a hard-built song library, so the theme's rules are set up front. Destructive actions get reasonable safety confirmations ("you are about to delete X files from the cache — continue?"), and writing is fully disableable through a settings toggle, so a user can ensure the app is not a threat to their library. Cache cleanup's removal step lives here: scan the cache against the real Song and Course folders and offer to remove the records of what no longer exists. A full cache rebuild in ITGmania does not notice deleted songs and courses, so they persist indefinitely — that is the problem this answers. The read-only variant (scan and log only) is the safer first implementation and sits in the open candidates below, since it is the same work minus the danger. Playlist creation lives here too: the profile's Playlists folder files are hand-authored today, and writing them from the table's selection is a natural role for this theme — while reading them stays in theme 3.

**6. "What should I play next" — proposed.** **Owner decides:** this is the last theme, by the owner's call (2026-11-22): it is the fussiest of the ideas, the kind many users would quibble with no matter how it is done, and the more objective features come first. It is thorny in a way the other themes are not. The app already knows the library, the filters, and the scores; what it does not do is answer "charts near my skill I have not cleared," with recency weighting and progress over time. The thorn is that meter — the closest thing to a difficulty rating — is not a portable signal. DDR scales it 1–10 or 1–20, InTheGroove arcade 1–13, fan charts use any of those or none, and there is no objective way a meter is determined: an online ITG player's 7 can be like a 13 on the DDR X scale, and nothing communicates that. The owner's fork has a derived rating for this: a ridge regression on 16 features, all computed from cached chart statistics, fit to 5,581 officially rated DDR charts (song-grouped cross-validation, mean error 0.62 of a foot, about 95% within one foot), deployed as a Lua script in the Simply Love theme from `tools/difficulty/` in itgmania-notes. Its output is 1–19, with 20 deliberately unused — the training corpus has no label above 19. The rating is computable from the same cache the Librarian already reads, which makes it a real candidate signal for this app. But it imitates the DDR X scale, it was trained and tested only on DDR-style dance singles, and its features do not see stops, warps, hold-footwork interactions, or when in the chart the hard parts occur — so it mis-rates exactly the fan-made stamina content it would most need to get right. So the proposal for this theme has to answer its first question before anything is built: what is "next" computed from? The candidates are the player's own score history (the one signal calibrated to the player rather than to a scale), the derived rating (cross-pack comparable, DDR-normed), meter used only within a pack where the scale is at least self-consistent — and it has to say what each one breaks on. It could also be scoped down to score-history recommendations only. Theme 3 feeds it two things: a loaded profile to compute from, and favorites as a player-stated signal.

**Open candidates, not themes yet.** Preferred lists beyond courses and playlists (stamina set, tech set, unplayed, tournament shortlist) — the gap is real, but it overlaps the course builder, which theme 4 above would absorb. Playlists themselves are settled: they live as files the game reads, read in theme 3 (a dropdown filter) and created in theme 5. What is still open is whether these other lists live in the app or as files. It becomes a theme when that question has an answer.

Cache cleanup, read-only first: scan the cache against the real Song and Course folders and generate a log of the records whose files no longer exist. A full cache rebuild in ITGmania does not notice deleted songs and courses, so they persist indefinitely — the log is the answer to that, without touching anything. It is the same work as the removal step minus the danger, so it is the safer first implementation, and it can land inside the read-only themes. The removal step waits for theme 5. Careful with how ITGmania itself checks cache integrity; the scan reads only.

## Settled decisions

- The song page exists and is the window host; dialogs share its placement rules (0016).
- A deliberate move or resize is remembered; anything else is not (0016, D3/D4).
- Scores sync refreshes scores only, never the library (v1.3.0).
- The song page shows Grade and Best % for the loaded profile and for the machine, in an aligned grid; its charts sort by dance type (Single, Double, Couple, Solo, Three-panel) then difficulty.
- The dance-type display labels are Single, Double, Couple, Solo, Three-panel, Routine; the v1.3.0 engine recognizes 18 #STEPSTYPE values and the mapping is display-only — the raw value stays in the Stats join and course files (verified 2026-11-22).
- The snapshot schema bumps when a fix changes what a snapshot means; old snapshots rebuild once.
- The app is one flat package, `itgmania_library`, launched by `launch.py` (0012).

## Open decisions

- Pack and series view: mirror the game's byte-exact Series grouping or tidy case variants; v1.3.0 or beta behaviour for one-pack series; where the exe search looks (the found path lives in settings); whether banners are shown; folder name or DisplayTitle as the pack label.
- Dance labels: the proposed non-dance labels, and whether hiding non-dance rows gets its own proposal.
- Cache cleanup: the read-only scan-and-log variant is unparked as a candidate (see Open candidates); the removal step waits for theme 5 and its proposal.
- What "what should I play next" means, and whether the remaining lists (beyond favorites and playlists) live in the app or as files.
- Whether the distribution panel, the course builder, or anything else gets a second pass once the themes above land. Nothing is scheduled.

## What a version means — proposed

**Owner decides:** a version ships when a theme completes, plus the fixes that landed with it; a fix-only batch ships as a patch release when it is worth naming. That is mostly naming what already happens: v1.3.0 was the scores-sync theme, v1.2.1 was a fix batch. Under this rule the Unreleased section shipped as v1.4.0 when 0016 landed, since unified windows is a new capability, not a fix. Nothing ships on a date.

## The Project

The GitHub Project mirrors this document. Its Theme field takes the theme names above plus "Unthemed"; its Roadmap view groups by Theme; its Backlog is the next theme's queue, not a pile. Pull requests are board items too, because a PR is a step toward a theme and the board should show theme progress. The app bot reads Projects v2 via GraphQL (verified live 2026-11-20) and has write permission, so creating the Project, its fields, and its items is Muse's job on the owner's go-ahead — the first write is still unproven, so creation is the first job, not moving elements. Whether the views can be set up the same way gets confirmed when the Project is created; if not, that part is a web-UI job.

## How this changes

Amended by proposal, like any other decision — a proposal that moves a theme, adds one, or overturns a boundary says so and updates this file in the same PR. When a proposal closes, its theme status here is updated in the same pass. The roadmap is also the checklist for leaving the ground clear: work in an earlier theme is checked against the themes after it, and a proposal or PR that would foreclose a later theme's option, or force a choice that theme should make, says so here the same way a departure does. The song page's Previous/Next is the live example of the check — a display-order accessor shared with the table's refresh is a seam theme 3's multi-select exploration and theme 6's recommendations will both need, where reading the order back from the Treeview would have baked in a widget dependency instead. The distribution panel's boundary unification, staged in theme 3 just before the multi-select exploration, is the same check from the other direction: the panel is the other holder of the filter variables, so its read path is unified before the filter representation changes underneath it. If this document grows past a page, it has stopped being a roadmap and should be cut back.
